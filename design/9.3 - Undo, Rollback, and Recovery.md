## 9.3 Undo, Rollback, and Recovery

Three mechanisms, three different mistakes, three different scopes. They are deliberately
not one system, and the reason is that they answer questions a user asks in different
words: *"put that cell back"*, *"that action shouldn't have run"*, and *"something ate my
profile"*. A single mechanism stretched over all three ends up too coarse for the first and
too casual for the third.

|                | undoes                    | scope            | invoked by        |
| -------------- | ------------------------- | ---------------- | ----------------- |
| **Undo**       | one edit *you* made       | one gesture      | Ctrl+Z            |
| **Rollback**   | everything a step wrote   | one action step  | run report, explicit |
| **Snapshots**  | the whole database        | a point in time  | automatic, restore is manual |

The layering that matters: **each is the fallback for the one above it.** Undo cannot help
once the app has closed; rollback cannot help with something you typed; a snapshot can
always help, but at the cost of the work since it was taken.

### The asymmetry this exists to correct

Packsmith defends the data it *generates* extremely well — staging buffers, dry runs,
ownership records, per-step rollback, hard-blocks on files it does not own. For a long time
none of that covered the data a person **typed**, which is the expensive kind. §5.3 is
explicit that recommendations narrow candidates and a human decides; those decisions are
thousands of individual judgments that no heuristic reproduces.

Re-running an action costs seconds. Re-deriving a filled blueprint costs weeks. The cheap
data had three safety nets and the expensive data had none.

### 9.3.1 Snapshots

A consistent copy of `profile.db` in `profiles/<name>/backups/`, named by timestamp and
reason. Taken on profile open and before the operations that can destroy a lot at once:
deleting a blueprint, an instance, or a tag definition, and any slot removal or retype whose
impact is destructive.

- **SQLite's backup API, not a file copy.** A database at rest can be more than one file —
  the rollback journal sits beside it — and copying them at slightly different instants can
  produce something that is not a database.
- **Coalesced.** A snapshot taken moments ago stands in for the ones that would follow, so
  deleting forty instances leaves one copy of the state *before* the batch rather than forty
  copies of the demolition. The last of those would be the least useful thing to keep and
  would have evicted everything worth having.
- **A rebuild never runs without one.** `_rebuild` drops every table when the schema has
  drifted. It now snapshots first and *refuses* if that copy cannot be taken. An unusable
  database can be repaired; an erased one cannot. Empty databases still rebuild freely —
  refusing there would brick a fresh profile over a worthless file.
- **Not a version-control system.** Retention is a fixed number of recent copies. Restoring
  one is all-or-nothing and loses everything since. That coarseness is the point: it is the
  last resort, not the first.

### 9.3.2 Rollback

Specified in §3.3 and §6.1 and already built. One committed step, reversed across every
engine it touched — L2 assignments, blueprint bindings and instances, and file bytes plus
ownership. A step whose writes cannot all be undone refuses rather than half-undoing, or
"rolled back" becomes a lie about the state of the pack.

Its inverse records are the foundation the next section builds on.

### 9.3.3 Cell-level undo

**Supersedes the per-view `EditStack` sketched in §5.1.** That design put an undo stack
inside the registry table, which implies a second one inside the blueprint editor, which
implies two implementations of the same reversal and two chances to get staleness wrong.

**It is one system.** The inverse records rollback already stores are the same shape for
both engines:

```
tags                                     blueprint bindings
{"key": (registry_type, entry, tag),     {"key": (blueprint, instance, slot_path),
 "existed": bool, "value": ...,           "existed": bool, "value": ...,
 "owner_kind": ..., "owner_ref": ...}     "owner_kind": ..., "owner_ref": ...}
```

Only the key tuple and the store method differ. That is not a coincidence — it is what "L2
is a closed world of owned cells" (§3.2) already buys. So the dispatch currently living
inside `rollback_step` becomes a shared `apply_inverse(records, stores)`, used by both
rollback and undo, and a view contributes only two things: producing a record when it edits,
and refreshing when something is reversed underneath it.

**Ownership travels with the value.** `owner_kind` and `owner_ref` are part of the record,
so undoing a user edit over an action-owned cell restores the action's claim, not just its
value. Undo that dropped ownership would silently convert action-owned data to pristine and
break the next run's conflict check.

#### Scope: per tab

Ctrl+Z reverses the last edit *made in that tab*. Global undo would reverse something the
user cannot see, and tags and bindings genuinely interleave while working. Two tabs can show
the same data, so reversing in one must refresh the others — the same refresh path a job run
already triggers.

#### Grouping: one gesture, one entry

A batch is whatever one `db.transaction()` wrote. Filling forty cells is one undo, not
forty. The transaction boundary already exists and already means "these succeed or fail
together", which is the same grouping undo wants.

#### Staleness: the rule that makes this safe

An entry claims a cell was X before this edit made it Y. If anything else has since made it
Z — an action run, another tab — then applying the inverse would silently clobber Z.

> **Before reversing an entry, the cell's current value must still equal what that edit
> produced. If it does not, the undo is refused and says which cell and why.**

This is the file hard-block discipline (§6.1) applied to L2: an undo that quietly overwrites
someone else's write is worse than no undo at all. It is also the single strongest argument
for one implementation rather than one per view — this check is easy to omit and its absence
is invisible until it corrupts something.

#### What does not go on the stack

- **Action writes.** They have rollback: explicit, per-step, surfaced in the run report.
  Behind Ctrl+Z, a stray keystroke would silently reverse a whole job run. They must,
  however, *invalidate* overlapping undo entries by the rule above.
- **Files.** Open-world (§6.1), the text editor has its own undo, and file writes already
  carry ownership and rollback.
- **Schema mutations, including deleting a tag definition.** The rule is that **undo
  reverses values and never reverses schema**, which is the line §3.2 already draws between
  definitions and assignments, and between a blueprint's slots and its bindings. §3.2.2's
  "Revert Schema" is a specific escape from an orphaned state, not general undo, and it
  says so.

  Deleting a definition cascades to every assignment of it. Two things follow. Reversing
  that cascade would mean the staleness check clearing hundreds of cells at once, refusing
  the whole batch on any single drift — an undo that usually refuses teaches you not to
  trust it. And an operation that large should be *deliberate* to reverse, not reflexive:
  §9.3.1 now snapshots before the deletion, so it is recoverable without being one
  keystroke away from resurrection.

  This is only fair if the user is told at the time. **A confirmation for an operation
  outside undo must say that it cannot be undone, and name the snapshot that can recover
  it.**

#### Not persisted

The stack is session-scoped. Persisting it means a second history system beside
`step_runs`, with its own staleness problem across restarts, to answer a question §9.3.1
already answers less precisely but far more cheaply.

### Live Questions

**Redo.** Assumed symmetric with undo and not specified. The staleness rule applies to it
unchanged, but whether a redo stack survives an intervening edit is not decided.

**Undoing across a profile switch.** Closing a profile discards the stack. Whether that
should be silent, or should warn when the stack is deep, is undecided.
