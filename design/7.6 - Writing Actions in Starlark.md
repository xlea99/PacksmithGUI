### 7.6 Writing Actions in Starlark

This section covers the Starlark-specific authoring conventions — how actions are
structured as Starlark code, what's allowed and what isn't, how to share code across
files and packages, and the patterns that PackSmith's static analysis and execution
model expect.

#### Action Shape

An action is a single top-level function in a Starlark file. The function takes
exactly one argument — `pack` — which is the capability API object (§7.3) injected
by the runtime. The manifest (§3.3) declares the action's file and function by name:

```toml
[[actions]]
id = "nuke"
file = "nuke.star"
function = "run"
```

```python
# nuke.star
def run(pack):
    removal_tag = pack.step.mappings["target_items"]
    for item in pack.tags.read(tag=removal_tag, value=True):
        _hide_from_emi(pack, item)
        _remove_recipes(pack, item)
        _add_to_obliterator(pack, item)

def _hide_from_emi(pack, item):
    # ...

def _remove_recipes(pack, item):
    # ...
```

The entry point receives `pack`; helper functions inside the same file also receive
`pack` explicitly when they need capability access. No ambient capability — see
below.

#### Helpers Receive `pack` Explicitly

A helper function that needs capability access must receive `pack` (or a
capability-scoped sub-object) as an explicit parameter:

```python
def run(pack):
    _do_work(pack, some_arg)   # explicit pass

def _do_work(pack, arg):
    pack.log("info", "working")   # helper uses pack normally
```

There's no global `pack` binding. Actions cannot stash `pack` in module-level state
to use later from a helper — because that would make capability access ambient, which
breaks the static-analysis guarantee that every capability call is locatable in the
source (§7.2).

This rule extends to `load`-imported helpers across packages:

```python
# removal_suite/nuke.star
load("@emi_utils//hiding.star", "hide_item")

def run(pack):
    hide_item(pack, "quark:rope")
```

```python
# emi_utils/hiding.star
def hide_item(pack, item_id):
    file = pack.filesystem.resolve("emi.json")   # emi_utils knows EMI's config sits at the pack root
    file.write_key("hidden_items", pack.append_if_absent(item_id))
```

`@emi_utils` doesn't have its own `pack`; it gets one from the caller. This keeps the
capability flow explicit: a helper has exactly the authority its caller hands it.

#### The `load` Statement

Starlark's `load(...)` imports symbols from other `.star` files. PackSmith restricts
`load` paths to two forms:

- **Intra-package**: `load("//utils.star", "normalize_name")` — relative to the
  current package's root. No parent-directory escape, no absolute filesystem paths.
- **Cross-package**: `load("@package_name//file.star", "symbol")` — the
  `@package_name` resolves through the declared dependency list in `manifest.toml`.
  Importing from a package not in the dep list is a load-time error.

Absolute filesystem paths (`load("/some/path.star", ...)`), URLs, and un-prefixed
paths (`load("foo.star", ...)`) are all errors.

Cross-package imports trigger the static analyzer to walk the imported package's
graph as well — a helper's capability set is folded into the importing action's
capability set (§7.2).

#### Banned Primitives

Starlark has no ambient filesystem, network, clock, or syscall access by default.
PackSmith explicitly does not register these builtins either:

- **`open`** — not registered. The only way to touch the filesystem is through
  `pack.filesystem` or a provider-routed resolver.
- **`print`** — not registered as a free builtin. Use `pack.log(...)` instead.
  (Optionally: `print` could be redirected to `pack.log("debug", ...)` for
  author-convenience during development. TBD.)

Starlark's language design also excludes (by default, in the `starlark-rust`
implementation):

- **`while` loops** — actions must terminate; only `for` over enumerable data is
  permitted.
- **Unbounded recursion** — the interpreter caps recursion depth; stack overflow is
  a load-time or runtime error depending on the call shape.
- **Exceptions / `try`** — error handling uses `fail(reason)` plus sentinel return
  values. See §3.3's "No exceptions" note.
- **Classes / OOP** — records are modeled as dicts or `struct(...)` values.
- **Dynamic attribute access** — no `getattr` with runtime-computed names, no
  `setattr`. This is what makes capability inference tractable.

#### Transactional Semantics (Author-Facing)

Writes via `pack.*` handle operations stage to the step's scratch area and commit
atomically on successful completion (§7.3, §3.3). From the author's perspective, the
API is synchronous — they write, they read, they see their own writes, everything
works. Under the hood, nothing hits disk until the step's code returns normally.

If the action calls `pack.fail(reason)` or exits via an unhandled error, all staged
writes discard. The filesystem is never in a partial state.

This means authors don't need to think about flush order, two-phase commit, or
recovery. The only rule is: **do all your writes within the action step; don't
expect side effects to persist if you `fail()`.**

#### Patterns

A few recurring shapes worth naming:

**Enumerate-and-write.** The common structure for tag-driven actions:

```python
def run(pack):
    items = pack.tags.read(
        tag=pack.step.mappings["target_items"], value=True
    )
    for item_id in items:
        _handle(pack, item_id)
```

The static analyzer sees `pack.tags.read`, `pack.*.resolve`, and write operations
inside `_handle`; infers the full capability set without running the code.

**Query-then-bind.** For blueprint-driven actions:

```python
def run(pack):
    blueprint = pack.step.mappings["stone_types"]
    for instance in pack.blueprints.instances(blueprint):
        _generate_recipes(pack, instance)
```

**Capability-branching.** For actions that optionally use a capability:

```python
def run(pack):
    _do_main_work(pack)
    if pack.capabilities.has("kubejs.script_write"):
        _add_kubejs_hook(pack)
```

Static analyzer still infers `kubejs.script_write` as a potential capability — but
since the author declared it `optional=true` in the manifest (§7.2), satisfaction
check passes without KubeJS.

#### Debugging and Dry-Run

Every run is a dry run first (§3.3's ask-policy convergence loop). Authors see all
their `pack.log(...)` output in the Job Results tab (§4.1) before the step commits.
If something looks wrong in dry-run, resolving any `ask`-policy conflicts or aborting
the step before commit leaves the filesystem untouched.

For pure debugging during authoring:

- Use `pack.log(...)` liberally. Output appears in Logs during dry-run and real runs.
- `fail(reason)` terminates loudly; use it to assert expectations early in the action.
- Authored packages appear in the Actions panel (§4.1 A icon); standalone runs
  (§3.3's ephemeral one-step jobs) are the quickest way to iterate on a single
  action without spinning up a full job definition.
