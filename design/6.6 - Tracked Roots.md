## 6.6 Tracked Roots

Everything in §6 so far assumes one place: `<instance_root>`, baked into `FileStore` as a
single path and into `file_ownership.path` as a bare relative string. That held for as long
as Packsmith's job ended at the instance.

It stops holding the moment the pack's content is *generated*. A glue mod's assets —
blockstates, models, loot tables, lang, and the textures beside them — are authored in a
source repo that is not inside the instance and never will be, because it is a Gradle
project under version control. §3.2.2 already anticipated the shape of this and stopped
short of it: actions can *"compile 'you need to go build these in your glue mod' lists"*.
Tracked roots are what let the sentence end differently.

**This supersedes §6.2's "External Directories" Live Question**, which decided *yes, but
opt-in* and deferred the rest. Everything it asked for is answered below; one of its
requirements turned out to be satisfied by a mechanism that already exists.

### Two consents, not one

§6.2's sharpest point: *"let me edit here" is not "let downloaded code write here."* It
asked that action access be a second, explicit, per-root opt-in — never acquired for free
by adding a folder.

That is exactly what a **binding** is (§3.3, principle 5). So:

| act | grants |
| --- | --- |
| Adding a tracked root | it appears in the file browser; you may open and edit its files |
| Binding it to a step | *that step's action* may write into *that root* |

An action can no more reach an arbitrary tracked root than it can reach an arbitrary
resource pack. It declares that it needs somewhere to write; the user chooses where, per
step. Adding a root grants a *person* a view. Binding grants *one action* a target.

### Namespaces

Every tracked root has a name. `minecraft` is seeded, points at the instance, and cannot be
renamed or removed — a profile without its instance is not a profile.

**Paths are unqualified and mean `minecraft`.**

```python
pack.filesystem.resolve("config/reliable_remover/packsmith_remove.json")   # the instance
pack.filesystem.resolve("src/main/resources/...", root=target)             # a bound root
```

**There is deliberately no `minecraft:` prefix form.** A second spelling of one path is a
cost with no benefit — but the real objection is that the grammar would advertise a
capability that must never exist. If `minecraft:config/x` parses, the next thing an author
writes is `deep_end_tweaks:src/...`, which is precisely the hardcoded coupling this design
prevents. A syntax whose only legal value is one literal is not a syntax; it is a trap with
one safe input.

The rule underneath, which §7.3 already applies to packs:

> **A namespace may be written literally if and only if its meaning is universal.
> Otherwise it must be bound.**

`config/reliable_remover/...` is a fact about a mod, true in every profile that has it —
hardcoding it couples the action to nothing. `deep_end_tweaks` is one person's folder on one
machine. This is the same line §7.3 draws between `pack.filesystem` (literal config paths,
fine) and `pack.datapacks` (bound, because *which pack* is personal).

**The qualified form is an output, never an input.** Storage keys on `(root, path)`; the
file browser and run report *display* `tweaks / src/main/...`. Nothing parses a qualified
string back into a root, so there is no second spelling to drift.

### Handles, not paths

Anything handing a path back to an author must hand back a **handle**. `pack.datapacks.owned`
and `pack.resourcepacks.owned` already do (built 2026-08-20); folders follow.

A bare path has to be re-resolved by hand to be used —
`pack.filesystem.resolve(path)` — and that round trip is only correct while there is exactly
one root the path could mean. With two, the same relative path names two different files and
the re-resolve silently picks the wrong one. A handle never stopped knowing where it lives.
It also carries `.root` beside `.path`, so an action can report where its output landed.

### Schema

```sql
CREATE TABLE tracked_roots (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,
    name  TEXT NOT NULL UNIQUE,      -- a LABEL; `minecraft` is seeded and locked
    path  TEXT NOT NULL
);
-- file_ownership: PRIMARY KEY (path) becomes (root_id, path)
```

**`id` is identity, `name` is a label** — §3.2.1's rule, and §3.2.2 relearned it the hard
way with instance names. Ownership rows and step bindings key on `id`, so renaming a root is
a one-row update that orphans nothing.

`file_ownership.path` is a bare `TEXT PRIMARY KEY` today, which means
`assets/deep_end/lang/en_us.json` under two roots is *the same row*. That is a correctness
hole rather than a preference, and closing it is a **`SCHEMA_VERSION` bump plus a
migration** — existing rows take the `minecraft` root. `FileStore(db, mc_path)` becomes
`FileStore(db, roots)` with a per-root containment check.

### Guards

Consent settles *scope*. It does not dissolve these, and each one is a correctness
requirement rather than a matter of taste.

- **`userdata/` is unreachable, in both directions.** §6.2's guard, and the subtle half is
  that checking `path != userdata` is not enough — adding userdata's *parent* defeats it.
  **No root may contain, or be contained by, `userdata/`.** Reaching `.star` sources through
  the browser would edit code by a door that applies none of §3.3.1's provenance rules.
- **No root may overlap another.** If one contains the other, a file has two identities and
  two ownership rows, and the hard-block stops composing: an action blocked under one name
  writes freely under the other. Refused when the root is added, when it is the only moment
  the check is cheap and the answer is actionable.
- **A missing root fails loudly.** A moved repo or an unplugged drive must not be treated as
  an empty folder to write into.
- **Blast radius is not symmetric.** The instance is regenerable — reinstall the pack, re-run
  the jobs. A mod source tree is months of Java. The protections are identical because they
  were never rooted in the path: ownership, staging, dry run and rollback are all
  root-agnostic already, and the root only ever answered *"where may I look at all."*

### Narrow the root until the guarantee is structural (2026-08-25)

*Resolves the Live Question this section used to carry about where generated output may land.*

A root is not merely "where you let it look" — it is the **shape of what cannot be reached**,
and a narrower one converts a promise about the code into a fact about the boundary.

The worked case: a mod source tree. Tracking the repo root would put `build.gradle`, `.git`
and `build/` inside the blast radius. Tracking **`src/main`** does not, and the reason it
costs nothing is worth generalising:

- everything the generator writes lives under it — `java/…` and `resources/…` are siblings
  there, and `META-INF/mods.toml` with them;
- everything it must never touch lives outside — and `build.gradle` is *provably* outside its
  needs, because `blockRef` resolves donors from the live registry by string rather than
  importing their classes, so the Gradle dependency list is fixed and never derived.

So the right question when adding a root is not "where is the project" but **"what is the
smallest folder containing everything this will write?"** Excluding `build.gradle` there is
not a limitation; it is a guarantee. It also disposes of this section's other Live Question
about `.git` — a browser pointed at `src/main` never meets it.

The cost is real and should be stated: anything under such a root is compiled or packaged.
There is no harmless corner to drop a working file into — which is one of the reasons §3.3.4
forbids reaching for one.

### Live Questions

**The browser meets `.git`.** Tracking a repo root means rendering tens of thousands of
objects under `.git/`, plus `build/`. Needs ignore rules and lazy expansion; §6.2's tree
assumes an instance-shaped directory. Narrowing the root (above) avoids this in the case
that prompted it, but only because `src/main` happens to sit below both — it is a reason the
question is not urgent, not an answer to it.

**Interaction with the symlink rule.** §6.2's other Live Question notes that `FileStore`
resolves before checking containment, so a symlink out of the instance is already rejected.
Whether a tracked root may *be* a symlink, or contain one pointing at another root, is
undecided and interacts with the overlap guard above.
