### 1.1 The MVP Target

The rest of these docs describe PackSmith *whole*. This section describes the **first
version worth building and dogfooding** — what's in it, what's deliberately left out,
and the one architectural decision that shapes both.

The guiding principle: **the MVP must prove the entire loop, not half of it.** PackSmith's
whole thesis is "documentation and action are the same problem — check a box, files
change" (§1). The documentation half (tag entries, browse, filter) is the part a Google
Sheet already does; the reason PackSmith earns its existence is that checking the box
*does something*. An MVP that can tag but can't act demonstrates the prerequisite, not the
product. So the MVP is **one thin vertical needle through all three layers** — L1 read,
L2 tag with real ownership, L3 action that writes a real file — rather than a
fully-built L1+L2 with L3 postponed.

#### The decision that shapes everything: actions are temporarily plain Python

The full design runs actions as sandboxed Starlark (§3.3, §7). But Starlark is only doing
two jobs: sandboxing the action *body*, and being statically analyzable for capability
inference (§7.2). Neither is load-bearing for *proving the loop*. Everything else in
Layer 3 — the `pack` capability object, staging, ownership claims, conflict policy, jobs
and steps, run history — is host-side Python that exists no matter what language the action
body is written in.

So for the MVP, the action body is **a plain Python callable** instead of a Starlark
function. The swap point is a single function:

```python
def invoke_action(action_ref, pack):
    action_fn = load_action(action_ref)   # MVP: import a Python callable
                                          # future: compile a Starlark function
    action_fn(pack)                       # identical call convention either way
```

`load_action` and the sandbox are the *only* things Starlark changes later. The `pack`
object the action receives — and every host-side mechanism wrapped around the call — is
built for real now and does not move when Starlark lands. This is what makes the whole
L1↔L3 / L2↔L3 interface (the genuinely load-bearing part) real and exercised from day
one, instead of validated by a single throwaway stub. It is the same move §3.4 already
blesses for plugins: hardcode against the real registration surface first, swap the
runtime underneath later, "the refactor is mechanical, not architectural."

#### The honest-gentleman rule

Python actions are unsandboxed — nothing stops one from calling `open()`, importing `os`,
or stashing `pack` in a module global. The MVP does **not** try to enforce or lint this;
these are test-scaffold actions written by the tool author, for the tool author. Instead
there is one voluntary discipline: **write Python actions as if they were Starlark.** Only
ever touch the world through `pack`; pass `pack` explicitly into helpers; no ambient
filesystem, network, or imports; no module-level `pack`. Actions that honor the rule port
to Starlark for free; actions that cheat are rework later. The rule is the entire price of
the shortcut, and it's cheap.

#### Ownership becomes real here

Ownership (§3.2.1, §6.1) is defined entirely in terms of actions — so with no Layer 3 at
all, it is untestable dead code. This is exactly why the thin action harness is the right
MVP and not an afterthought: `pack.tags.write(...)` is the precise line where
action-ownership is claimed, so ownership gets exercised the first time any action writes a
tag. Ownership is built *into* the write path of the capability API, not bolted on
afterward.

MVP ownership scope covers **both ownership engines** — they look alike but work
differently, and both are in (see §6.0 for why they are separate):

- **L2 ownership (closed-world).** Every tag assignment is user-owned or action-owned per
  §3.2.1's state model (including the pristine/unset distinction and loud transfer), and
  the registry table renders the ownership states (§5.1). When an action writes an
  already-owned cell, the conflict resolves by declared policy — **`overwrite` / `skip` /
  `fail` only**, all synchronous. The `ask` policy, the dry-run convergence loop, and the
  conflict-resolution tab (§3.3) are deferred until the synchronous path is proven.
- **File ownership (open-world), whole-file only.** Files an action writes are owned whole
  (§6.1); user-owned files are hard-blocked from action writes and surfaced loudly, per
  §6.0's open-world engine — *not* the `overwrite`/`skip`/`fail` policies. **Per-key
  ownership is deferred** — no round-trip parsers, no key-level merge in the first cut
  (that's its own rabbit hole).

#### Staging, commit, and rollback

Two problems bundle under this name, and only one needs a real mechanism choice.

**Staging and per-step atomicity — free, already the model.** During a step, every write —
L2 assignments and file writes alike — goes to an **in-memory per-step scratch buffer**;
reads check the buffer first (read-your-writes), so nothing touches disk mid-step. On clean
completion the buffer commits (SQLite `COMMIT` for L2, bytes written for files); on `fail()`
the buffer is dropped. A failed step therefore touches nothing, for free — no mechanism
required.

**Rollback of a *committed* step is in the MVP**, and splits by engine:

- **L2 rollback is trivial** — replay the inverse assignment ops (restore old value over
  new), the exact old/new pattern the existing `EditStack` already uses. Persist those
  inverse ops per `step_run`. No snapshots.
- **File rollback uses a deliberately quick-and-dirty store-by-path snapshot.** Before a step
  overwrites a file, copy its old bytes into a per-step scratch keyed by `step_run` id, and
  rollback restores them. This is a *degenerate blob store* — no content-addressing, no
  dedup — and is **explicitly flagged to be replaced by the full content-addressed blob store
  (§6.1) later.** The disk cost that makes plain copies wrong only bites at scale (a job run
  hundreds of times); at MVP scale (one action, a handful of files) it's nothing, and the
  swap hides behind an unchanged capture-bytes / restore-bytes interface — the same "naive
  now, smart later, seam unchanged" move as Python-vs-Starlark.

**Crash recovery is deferred.** The §3.3 hash-based startup recovery is a shipping-product
robustness feature; for single-user indev, "crashed mid-write → re-run the step" is a fine
answer. Note the pre-write copies above are exactly the substrate crash recovery would need,
so deferring it burns no bridges.

#### Mappings: basic tag mappings in, blueprints out

The mapping system (§7.1's Mapping System) is the L2↔L3 interface, so a basic version is
in scope: an action declares it needs "a bool tag on `minecraft:item`," the job step binds
the user's own tag into that slot, and the action reads the bound name via
`pack.step.mappings[...]`. Structural typing for `blueprint` / `blueprint_instance`
mappings is deferred along with the rest of the blueprint system.

#### What's in the first cut

**Layer 1 — Game Data.** Already built (packdump load / compare / import / history). No new
work beyond wiring reads into the capability API.

**Layer 2 — User Data.**

- Tags: the existing store, plus **ownership columns and the pristine/unset/owned state
  model** (§3.2.1) — the one net-new L2 concept the MVP must add.
- Registry-table renderer: existing, plus **ownership visualization** (the three-state bool
  rendering, ownership tint — §5.1).
- Basic tag mappings.

**Layer 3 — the new action harness.**

- The `pack` capability object: `log`, `fail`, `registry.*` (L1 read),
  `tags.read` / `tags.write` (ownership-claiming), `filesystem.resolve().read` /
  `write` (whole-file, instance-scoped — the general resolver; mod-specific config
  paths are the author's / a library package's job, **not** a built-in `pack.config`
  registry, which is redundant sugar over `filesystem` and can't cleanly model reality
  anyway — EMI's config sits at `PACK/emi.json`, not under `config/`), `step.mappings`,
  `step.config`.
- Action declaration: a **real §3.3.1 TOML manifest** (`[[actions]]` — id, file, function,
  mappings, configuration, conflict_policies), *not* a Python decorator or dict. The manifest
  is host-side and language-agnostic — the exact artifact Starlark packages will use — so
  it's durable, not scaffolding. Build the manifest *format* only; the package system around
  it (dependency resolution, cross-package `load`, the store) stays deferred.
- `load_action(action_ref)` is the **one Python-specific seam** — `importlib` the module and
  grab the `function`, vs. compiling a `.star` later (~10 lines, swapped with nothing above
  it moving). Manifest parsing, binding resolution, the `pack` object, ownership stamping, and
  staging/rollback are all durable host-side machinery.
- Step→`pack` wiring: resolve a `job_step`'s stored bindings against the manifest's declared
  slots into `pack.step.mappings`, feed `pack.step.config`, and carry the action's manifest
  id so `pack.tags.write(...)` stamps `owner_action_ref` with it.
- Jobs and steps in SQLite (repurpose the leftover `flows` table into the `jobs` /
  `job_steps` shape from §3.3.3).
- Execution engine: globally serialized, staged, per-step transaction, commit on success /
  discard on `fail()` (§3.3).
- Conflict policy: overwrite / skip / fail.
- Basic run history (`job_runs` / `step_runs`).

#### What's explicitly out (and why)

- **Starlark runtime + capability inference** — the whole point of the seam; swapped in
  later behind `load_action` with nothing above it moving.
- **The package *system* — dependency resolution, cross-package `load`, versioning, the
  community store** — actions use the real §3.3.1 action-manifest *format* (that's in — see
  the L3 harness above), but the machinery *around* packages is deferred; actions are
  registered in-process for the MVP and distribution is a later concern.
- **`ask` policy, dry-run convergence loop, conflict-resolution tab** — the most complex
  piece of §3.3; ship the synchronous policies first and add `ask` only once its necessity
  is actually felt.
- **Per-key file ownership, round-trip parsers, the content-addressed blob store, crash
  recovery** — whole-file ownership first; per-key parsing is its own rabbit hole. File
  *rollback* ships as a minimal store-by-path snapshot (see Staging above), so the
  capability is in — it's the full content-addressed versioning and the crash-recovery
  startup logic (§3.3 / §6.1) that are deferred.
- **Capability gating (the satisfaction check, §7.1)** — the `pack` surface is the interface
  that matters; declaring/inferring/enforcing required capabilities sits on top and doesn't
  move the seam.
- **Integrations / capability providers (Paxi, KubeJS routing, §7.5/§8)** — the MVP uses
  raw `filesystem` writes and a hardcoded config-path map; provider routing arrives with the
  plugin runtime.
- **Blueprints and the View / filter-query system** — deferred; the query-language grammar
  (§3.2.3's Live Question) is its own design task that must land before the View system is
  built.
- **Threading niceties, profile-switching UI, global search, settings** — polish, not loop.

#### Definition of done

The MVP is done when this loop runs end to end against real Deep End data:

1. Open the item registry table.
2. Check `remove` on a real item (e.g. `quark:rope`) — a user-owned tag assignment with a
   visible ownership indicator.
3. Run a job whose one step invokes a Python "removal" action bound to the `remove` tag.
4. The action reads `remove == true`, writes a real removal file to disk (e.g. an Item
   Obliterator JSON or a KubeJS nuke script) through `pack`, and the write commits
   atomically.
5. The file exists on disk and shows as action-owned; the run appears in history and is
   rollback-able.

That is the full "documentation and action are the same problem" thesis — thin, but
complete: every layer, the real seam, and nothing faked that matters.
