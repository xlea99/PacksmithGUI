### 3.1 Layer 1: Game Data

Game Data is the read registry/game attributes generated by Packdump. It is inherently **read-only, static, and a report, not
a whiteboard.** It represents the actual truth from the game itself. PackSmith reads it,
displays it, but critically never modifies it.

The game told you what exists. You don't get to argue.

#### Profiles

A **Profile** is the top-level organizational unit — one profile per modded Minecraft
instance. It tracks:

- Profile name
- Minecraft instance path
- MC version (e.g., `1.20.1`)
- Mod loader and version (e.g., Forge `47.4.16`) — frozen at creation
- Settings (e.g., `max_packdump_snapshot_count`)
- References to its packdumps and user database

Profiles are stored in `userdata/profiles/{name}/`.

#### Packdumps

A **packdump** is an immutable snapshot of the game's registry state at a point in time.
Multiple packdumps are retained per profile (default ~5), with new ones loaded only when
the registry actually changes.

Key design decisions:

- **Automatic discovery.** When the user creates a profile, they point it at their
  Minecraft instance directory. The Packsmith mod always dumps to `<gameDir>/packsmith/`,
  so PackSmith knows exactly where to look — no user configuration needed for dump
  location. PackSmith won't let you do anything until it loads its first packdump, since
  without game data there's no registry to browse, no entries to tag, nothing to automate.
- **New dumps are adopted automatically, and reviewed afterwards.** This reverses what
  this section originally said — "review the diff before blessing it as the active
  snapshot" — and the reason is that the argument for blessing turned out not to apply.

  It was there to stop transient mod installs "polluting the tag/blueprint data". But
  **importing never touches Layer 2 at all**: orphans are *detected* against the new
  registry, never resolved. There is no pollution for the ceremony to prevent. What
  blessing would actually buy is a window in which the app shows you a registry the game
  no longer has — and stale is the worse failure mode, because staleness produces
  confidently wrong output that looks fine while an unwanted import announces itself the
  moment you look at anything.

  So the review still happens; it happens *after*, and it comes with a real undo. The
  Packdump tab (§4.1) shows what the import did and can **revert to any archived
  snapshot**, archiving the current one on the way so the revert is itself revertible.

  **This is a default, not a law.** `auto_adopt_packdump` in the profile's settings turns
  it off, and then a differing dump waits with a Bless action instead — the workflow this
  section originally described, for anyone who wants it.
- **Adopting a dump is a rebind, not a rebuild — and it must not cost the workspace.** The
  check runs on window focus, so it fires exactly when the user comes back from
  playtesting. A launcher that auto-updated one mod out of three hundred is enough to
  trigger it, which means the user may have done nothing at all. Tearing down every open
  tab for that is a punishment for the loop PackSmith exists to support.

  A packdump change is **not** a profile change. Layer 2 lives in the profile database and a
  new registry does not touch a byte of it, so the database is never closed and the tabs are
  never destroyed. What changes is one Layer 1 object, read by a countable set of holders,
  and each is re-pointed in place.

  **The invariant that makes this safe: every holder implements `set_packdump`, and reads
  its dump lazily inside a refresh method.** Nothing derives-and-caches at construction, and
  no packdump is captured in a closure. A holder that skips the rebind does not crash — it
  answers, confidently, from a registry the game no longer has, which is the same staleness
  this section calls the worse failure, arriving by a different door. A test walks the live
  window and fails on any holder left behind; the closure half of the property has to be
  kept by hand.

  The full rebuild survives as the fallback for a rebind that raises, because a
  half-rebound window is worse than a rebuilt one.
- **Packdumps are diffable.** The `compare()` method generates a structured dict of
  differences between any two snapshots — useful for the review/blessing workflow.
- **Localization uses fallback.** If a display name isn't available in the current locale,
  the raw registry ID is shown.

Storage layout per profile:
```
packdumps/
  latest/           # The blessed/active snapshot
    meta.json
    registries/
    attributes/
  history/          # Previous snapshots, most recent N kept
```

**N is `max_packdump_snapshot_count`, default 10**, and it lives in the *profile's*
settings rather than app config — retention is a property of the pack being worked on, not
of the app. A 300-mod pack's snapshot runs about 4 MB, so the default costs ~40 MB at full
history; that is cheap next to losing the ability to diff against the pack as it was three
updates ago, which is the entire reason history exists.

#### What Counts As A Different Dump

An import is skipped entirely when the incoming dump is *identical* to the current one, so
the definition of identical decides both how often a snapshot slot is burned and how long
stale data can survive. Two dumps are the same when all of these match:

- MC version, loader, loader version
- the mod list — ids, names **and versions**
- every registry's full set of entry **ids**, not merely its count
- every locale's display names

Two of those are deliberate and worth stating, because each looks like over-sensitivity:

**Mod versions count.** A version bump with byte-identical registries still produces a new
snapshot. Versions are displayed as provenance, and history is what lets the user diff
against the pack as it was before an update — a diff that skipped "nothing but versions
changed" updates would have gaps exactly where someone goes looking after a mod update
broke something.

**Localizations count.** They were originally left out, which meant a mod renaming an item
was "identical": no import, and the old display name persisted for the life of the profile
with no way to refresh short of deleting the packdump. Display names are what the user
actually reads — the table shows names, not ids — so staleness there is invisible-by-
construction. The general rule holds: **stale is the worse failure mode.** An extra
snapshot costs 4 MB; a wrong name costs trust in every screen that shows it.

#### The Vanilla Game Files

The packdump describes the *modded* registry. It says nothing about vanilla's own content —
the loot table for `minecraft:oak_leaves`, the recipe for stone bricks, the
`minecraft:leaves` block tag — and those are things a pack developer reads and overrides
constantly. They live in the **Minecraft client jar**, which is Layer 1 data that does not
come from the packdump.

A 1.20.1 client jar holds 5,888 files under `data/`. PackSmith reads them in place, never
extracting (§6.5), so browsing vanilla data costs nothing but finding the jar.

The jar is also the authoritative source for **`pack_format`**, in its `version.json`.
This matters more than it sounds: Minecraft refuses a pack whose format doesn't match, and
the numbers do not follow a pattern — 10, 12, 15, 18, 26, 41 across 1.19→1.20.5, with the
data and resource numbers diverging in some releases. A hardcoded table is therefore wrong
the first time Mojang ships a version nobody has updated it for, and wrong *silently*. Ask
the jar; keep a table only as a fallback.

##### Locating It

Reading the jar is trivial. Finding it is the problem: launchers do not agree, and there is
nothing to ask.

| Launcher | Client jar |
|----------|------------|
| CurseForge | `<root>/Install/versions/<v>/<v>.jar` |
| Vanilla launcher | `<root>/versions/<v>/<v>.jar` |
| Prism / MultiMC / PolyMC | `<root>/libraries/com/mojang/minecraft/<v>/minecraft-<v>-client.jar` |
| Modrinth App | `<root>/meta/versions/<v>/<v>.jar` |

**Three strategies, ending in one that always works:**

1. **An explicit path in the profile's settings.** Tried first and alone — if the user has
   said where the jar is, quietly preferring a detected one would make the setting a
   suggestion rather than an instruction.
2. **Detection**, by walking up from the instance directory (the one location PackSmith is
   certain about) and trying each known layout. Bounded to a few levels: climbing further
   would eventually match an unrelated Minecraft install elsewhere on the disk, and a
   filesystem-wide search is both slow and prone to finding somebody else's.
3. **Nothing, reported honestly.** Features that need vanilla data degrade; nothing invents
   a path.

**The list of launchers will always be incomplete.** That is a permanent condition, not a
gap to close, so the design makes being wrong about one cost a row of data rather than a
new mechanism — and strategy 1 means a user on a launcher nobody has heard of is never
actually stuck. Adding support for a launcher is adding its layout.

**A candidate jar is verified, not trusted.** Its `version.json` must state the version the
profile expects. A filename is a claim; silently loading vanilla data for a game the user
isn't running would be worse than finding nothing, because a missing answer is obvious and
a wrong one isn't.

> **Resource-pack assets are a separate question.** The client jar carries some, but since
> 1.6 much of Minecraft's asset content lives in a content-addressed objects store
> (`assets/objects/` plus an index mapping logical names to hashes) that sits outside the
> jar. Vanilla *data* is available today; vanilla *assets* need that store located too,
> and are deliberately not claimed until it is.

#### Registry Entries, Attributes, and Derivations

A **registry** is a named set of entries (`minecraft:item`, `minecraft:block`,
`minecraft:entity_type`, ...). Everything you can say *about* an entry falls into exactly
one of three kinds, and keeping them distinct is load-bearing — the query engine (§3.2.4)
resolves every field reference through this split:

- **The entry itself.** A registry entry *is* its namespaced id — `alexscaves:galena`.
  That is the whole identity; there is no separate "id field." When you query a registry,
  the entries (these ids) are the rows.
- **Attributes** — optional per-entry data the **packdump provides** alongside the
  registries (dumped under `attributes/`), keyed by `(registry type, entry id)`.
  **Localization** — an entry's display name in a locale — is the first and, today, only
  attribute; future dumps may expose more where the game makes them cheaply available
  (an item's max stack size, a block's hardness, etc.). Attributes are read-only L1 data,
  looked *up* per entry — attached *to* the entry, not part of its identity.
- **Derivations** — values *computed* from the id, stored nowhere. The primary one is the
  **mod / namespace**: the part of the id before the colon (`alexscaves:galena` →
  `alexscaves`). Derivations are pure functions of the id.

These are three genuinely different mechanisms — an identity, an attached lookup, and a
computation — and must **not** be collapsed into one vague notion of "properties." An entry
*is* its id; localization is an **attribute**; the mod is a **derivation**.

#### Multi-Loader Awareness

The GUI itself is largely loader-agnostic — Forge and Fabric registries look the same
once dumped. The Packsmith Java mod will need per-loader versions, but the GUI just tracks
`loader` as metadata. Design for generality, don't over-engineer for it.
