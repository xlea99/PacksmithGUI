### 8.1 Global Datapack & Resourcepack Loader Integration

This is the most foundational integration Packsmith ships, and also the most frustrating:
**Minecraft has no vanilla mechanism for global datapacks or resource packs.** There is
no way to ship a pack that applies to every world without world-specific copying, except
through a mod. Pack developers have been working around this for years with mods like
Paxi, OpenLoader, and Moonlight/Global Packs that scan a known directory and inject its
contents as an active pack at load time.

Packsmith treats these loaders as a single logical capability: "overrides work." An
active loader integration lets Packsmith:

- Show the Datapacks and Resource Packs smart folders in the File Browser (§6.2)
- Enable the save-as-override workflow in the JAR Viewer (§6.5)
- Provide override-target path resolution to actions that need to write datapack or
  resourcepack files — meaning actions become portable across loader choices

Without an active loader integration, global override workflows are disabled. Users can
still edit world-local datapacks (the vanilla `saves/<world>/datapacks/` path) and
per-resourcepack files via normal filesystem editing, but Packsmith's override-centric
flows don't operate. The user is pointed here to install one of the supported loaders.

#### Supported Loaders

**Verified on a real 1.20.1 Forge instance** — all four installed together, launched once,
and read from the folders and configs they generated for themselves.

| Mod | Mod id | Datapack directory | Resource pack directory | Ordering |
|---|---|---|---|---|
| **Paxi** | `paxi` | `config/paxi/datapacks/` | `config/paxi/resourcepacks/` | ✅ both |
| **Open Loader** | `openloader` | `config/openloader/data/` | `config/openloader/resources/` | ❌ |
| **Moonlight** | `moonlight` | configurable, default `moonlight-global-datapacks/` | **none** | ❌ |
| **Global Packs** | `globalpacks` | `global_packs/required_data/` | `global_packs/required_resources/` | ❌ *(see below)* |

This table previously conflated Moonlight with Global Packs as one entry, gave Moonlight a
resource-pack directory it does not have, and placed Open Loader at the instance root. All
three were wrong, and the corrections came from installing the mods rather than reading
about them: **the upstream documentation is wrong for two of the four.** Paxi's CurseForge
page describes a newer `config/_paxi_/` layout, and Open Loader's own README on the 1.20.1
branch points at `.minecraft/openloader/data/`. Either would have written into a directory
the game never reads — failing silently, which is the one failure mode this whole mechanism
cannot tolerate.

**This table is explicitly for Minecraft 1.20.1.** Loaders move their own paths between game
versions — Paxi already has — so a later version needs these re-verified rather than
assumed. Doing that properly means per-version layouts; today it means *check before
trusting*.

Three of the four can be **switched off or relocated in their own config**, so a loader
being installed is not the same fact as its capability being available, and the two kinds
move independently:

- **Open Loader** — `config/openloader/advanced_options.json` toggles `dataPacks.enabled`
  and `resourcePacks.enabled` separately.
- **Moonlight** — `config/moonlight-common.toml`'s `global_datapacks_folder` names the
  folder, and an empty string disables the feature entirely.
- **Global Packs** — the folder is only read because `config/global_packs.toml` lists it
  under `[datapacks].required`. Delist it and the folder is silently ignored.

Capabilities are therefore read from disk per profile, not declared once per loader.

**Global Packs has ordering that Packsmith deliberately does not claim.** Its priority is
the order of the `required` list, and every pack Packsmith writes lives *inside* one entry —
so the packs within it cannot be reordered. Claiming `datapacks.ordering` would let an
action declare a dependency on ordering and then be handed a provider unable to deliver it,
which is exactly the silent-wrong-result the capability split exists to prevent. A future
integration could register each pack as its own config entry and earn the capability
honestly.

**Directories appear lazily.** On a fresh install that has only reached the main menu,
`config/paxi/` contains `resourcepacks/` and its order file and nothing else — `datapacks/`
appears once a world has been loaded. A missing directory therefore means *not yet*, never
*this loader is unavailable*: availability is decided by the mod being installed and its
config, and the directory is created on demand when something is written into it.

#### Enabled and Disabled Packs (2026-08-18)

Minecraft decides whether a folder is a pack by whether it holds a `pack.mcmeta`, and a
folder without one is **not loaded and not complained about**. That makes the file a
switch: rename it to `pack.mcmeta.DISABLED` and the pack goes dark; rename it back and it
returns. Packsmith exposes that as **Disable / Enable** on a pack's row in the File
Browser's smart mode.

**The manifest is renamed, never the folder.** A pack's identity *is* its directory name —
§3.3 makes it the one binding that stores a name rather than an id — so renaming the folder
would break every job step bound to it. Renaming the manifest leaves identity untouched and
changes only whether the game reads it.

This forced a distinction the loader layer did not have, and closing a real hole in the
process. `packs()` listed any directory, so a pack whose manifest had been renamed away
still satisfied the write guard: an action wrote into it, the run reported success, and the
game read none of it — precisely the silent no-op that guard's own message warns about. So:

| | means | used by |
|---|---|---|
| `available(kind)` | packs that would actually **load** | the step editor's picker, the write guard |
| `installed(kind)` | every pack on disk, enabled or not | the File Browser |

A disabled pack is still *listed* — hiding it would make switching it back on impossible —
but it renders dimmed and says so, and binding or writing to one is refused by name
("that pack is disabled") rather than by the generic "no such pack". Two different problems
need two different instructions.

**Zip packs cannot be switched off this way**, and the refusal says why: the manifest lives
inside the archive, and renaming the archive would change the pack's name, which is the
thing this mechanism exists to preserve.

#### Detection

The integration activates when its corresponding mod is present in the current
packdump's mod list (§3.1). Detection is:

1. Scan the packdump's mod list for the loader mod ID.
2. If found, activate the integration's registrations: smart folders, context-menu
   actions, override-target resolvers.
3. If multiple loaders are present (unusual but legal), Packsmith picks one as the
   default override target and surfaces the choice in the save-as-override prompt so
   the user can route individual overrides explicitly. The choice is sticky per
   profile.

If the user adds or removes a loader mod between packdumps, the integration activates
or deactivates on the next packdump blessing. Existing overrides in a now-inactive
loader's directory are not touched; Packsmith just stops offering that loader as a
target.

#### Registrations

The integration registers:

- **Smart folders** in the File Browser (§6.2):
  - `📦 Datapacks` — rooted at the loader's datapack directory, one subfolder per
    installed datapack
  - `📦 Resource Packs` — rooted at the loader's resourcepack directory, one subfolder
    per installed pack
- **Context-menu actions** in those smart folders:
  - "New Datapack..." — prompts for a name, creates the folder structure
    (`<pack>/pack.mcmeta`, empty `data/`) with sensible defaults
  - "New Resource Pack..." — same but for resourcepacks
- **Override-target resolver** consumed by the JAR Viewer's save-as-override prompt
  (§6.5) and by action APIs that write overrides. Input: an internal jar path like
  `data/<namespace>/<file>` plus a target pack chosen by the user. Output: an absolute
  filesystem path where Packsmith should write the content.

#### The Override Semantic

A datapack override is just a file that exists at the same namespace path the mod
provides, inside a pack that loads after the mod's built-in data. The loader puts the
user's global pack into that "after" position. Packsmith doesn't do anything clever
here — it just writes the file to the right place and lets Minecraft's pack layering do
the rest.

The same logic applies to resource packs. The override-target resolver and the File
Browser smart folders treat them symmetrically.

#### Live Questions

##### Loader Auto-Install Suggestion

If the user's packdump contains no global pack loader and they attempt an action that
requires one (save-as-override, certain package actions), Packsmith currently just tells
them they need one. Should Packsmith also suggest installing one? And if so, which —
pick a recommended default, or show the options and defer? The downside of picking a
default is that the "right" loader depends on pack dev preferences Packsmith shouldn't
presume. Probably surface as a recommendation with brief pros/cons, don't auto-install.

##### Multi-Loader Profiles — the Default Chooser (PARTLY ANSWERED, still owed)

Sticky-per-profile was right and is **built**: the loader is chosen in Settings from the
ones actually installed, stored by provider *name* (never a list index, which would point
at a different loader the moment one is installed), and it decides every contested
capability. Preferring a loader only wins it the capabilities it genuinely offers — you
cannot hand Moonlight the resource packs it does not do.

**What is still owed is the case where nothing has been chosen yet.** The fallback is
alphabetical, and alphabetical is arbitrary in a way that bites immediately: on a pack
holding Paxi and Moonlight — which is the author's own — both "Global Packs" and
"Moonlight" sort ahead of "Paxi", so a user who never opened Settings would have overrides
land somewhere they never picked, silently.

Two-loader packs also turn out to be *common rather than unusual*, contrary to what this
section assumed. Moonlight is a general-purpose library whose global-datapack support is
one config key inside it, so packs acquire it as a transitive dependency without anyone
choosing a pack loader at all.

Options for a real default chooser: rank the loaders by capability breadth (Paxi first,
since it is the only one that orders); ask on first detection of more than one; or refuse
to guess and surface a "choose one" prompt before the first override. Undecided.

##### Is a `required` Entry a Pack, or a Folder of Packs?

Global Packs' config lists paths under `[datapacks].required`, and it is not settled whether
each entry names a pack directly or a directory scanned for packs. Packsmith implements the
latter — it matches every other loader, matches the mod's own description ("a folder into
which you can add all the datapacks you want"), and matches the empty container folders it
generates. Worth two minutes in-game to confirm before anything depends on it.
