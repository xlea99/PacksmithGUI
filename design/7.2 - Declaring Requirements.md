### 7.2 Declaring Requirements

An action's **required capability set** is the list of capabilities its code actually
uses. PackSmith needs this set for three reasons:

1. **Satisfaction check** (§7.1) — at install/load time, verify providers exist for
   every required capability before the action is allowed to run.
2. **User-facing disclosure** — the install confirmation dialog, the Actions panel,
   and the Action tab all surface the capability set so users know what an action
   needs and does.
3. **Inferred ownership claims** — the static analysis that produces the capability
   set also produces the action's structural ownership claim shape (§6.1), which
   feeds conflict-detection at install time and surfaces in the pre-run preview.

#### Inferred by Default

PackSmith computes the capability set by **static analysis of the Starlark source.**
Authors write normal code; PackSmith walks the AST, traces `load()` statements across
the package dependency graph, collects every `pack.*` call site, and produces the
superset of capabilities the action could reach.

Starlark is well-suited to this — no `getattr`, no dynamic imports, no `eval`. Every
capability call is a literal attribute access on `pack`, and the analyzer reads them
directly. Dead-branch conservatism means the analyzer may include capabilities that
a specific run never actually uses; that's fine, the alternative (under-declaring)
would be worse.

The inferred set is written into the action's `manifest.toml` at publish time (for
downloaded packages) or save time (for authored packages, kept in sync automatically).
The user never has to type a capability list by hand.

#### Inferring Enum Value Dependencies — a Lint, Not a Declaration

The same analyzer can, in principle, recover an action's **required enum values**
(`requires_values`, §3.3): trace `pack.step.mappings["tier"]`, follow the value read from
it, and collect the string literals it is compared against. Starlark's constraints make
this tractable, though it is a harder class of analysis than capability collection —
dataflow rather than call-site enumeration.

But the output must be treated differently, because **the safe direction of error
reverses.** For capabilities, over-declaring is harmless — a longer install dialog. For
enum values, over-declaring is actively harmful: an action that demands `"end"` it never
truly uses cannot be bound by a user whose enum lacks `"end"`, and that user has no way to
know the requirement is spurious. Dead-branch conservatism, which is *correct* for
capabilities, would manufacture false friction here.

So enum-value inference is a **publish-time lint addressed to the author**, never a silent
auto-declaration:

> `palette:standardize` compares the `tier` mapping against `"late"`, which is not listed
> in `requires_values`. Add it?

The author decides. The manifest declaration remains authoritative — which also leaves room
for the patterns static analysis cannot see (dispatch through a dict, values assembled at
runtime) without pretending they were covered.

#### Optional Author Declarations

Authors can optionally augment the inferred set with metadata in `manifest.toml`:

```toml
[[actions.requires]]
capability = "datapacks.write"
reason = "writes recipe-removal datapack for items flagged for removal"

[[actions.requires]]
capability = "kubejs.script_write"
optional = true
reason = "adds a KubeJS hook if KubeJS is installed; no-ops otherwise"

[[actions.requires]]
capability = "datapacks.write"
min_version = 2
```

Fields:

- **`capability`** (required) — the capability name. Must appear in the inferred set
  or be explicitly allow-listed as "intentionally not inferable" (rare).
- **`reason`** (optional) — user-facing explanation shown in install dialogs and the
  Action tab. Helps users decide whether to trust/install the package.
- **`optional`** (optional, default `false`) — if `true`, the action runs even when
  no provider satisfies the capability; the action's code is expected to handle
  absence gracefully (e.g., by checking `pack.capabilities.has("kubejs.script_write")`
  before calling it).
- **`min_version`** (optional) — minimum provider version required.

Authors who don't add any declarations get a no-metadata capability list that's still
functional — just without the reason strings in the install UI. Adding reasons is
strongly encouraged for published packages but not required.

#### Inferred vs Declared Divergence

The Action tab (§3.3.1) shows both:

- **Inferred capabilities** (from static analysis)
- **Declared capabilities** (from `manifest.toml`)

If they diverge, it's a warning signal in the Action tab — either:

- The author over-declared (listed a capability the code doesn't actually use)
- The author under-declared (code uses a capability that wasn't listed; unusual but
  possible for edge cases like indirect calls through packages)
- The analyzer missed something (a bug to fix)
- A downloaded package's manifest was tampered with (store-side integrity check
  would also catch this)

Most of the time the sets are identical and the divergence display is a no-op.

#### Inferred Ownership Claims

The same static analysis that produces the capability set also produces the action's
**structural ownership claim shape** — for each file-operation call site:

- The capability invoked (e.g., `datapacks.write`)
- The claim kind (whole-file via `handle.write`, per-key via `handle.write_key`)
- The target path/key if arguments are literals, or a structural description
  otherwise ("paths derived from iterating L2 tag `remove` on `minecraft:item`")

This feeds into:

- **Install-time conflict detection.** Two actions claiming file-wide ownership on
  the same file, or overlapping per-key claims, are detected and surfaced before the
  user installs.
- **Pre-run preview** (§3.3). The dry-run convergence loop gives a concrete
  enumeration for a specific invocation — structural inference gives the general
  shape, dry-run gives the specific list.
- **Action tab claim disclosure.** Shown separately from the capability list (per
  the Option A decision in §7.0 / related discussion — see §7.1's "Dotted Naming"
  section for the rationale): capabilities answer "what providers does this action
  depend on?", claims answer "what will this action write to?"

#### Package-Level vs Action-Level

Capabilities are declared at the **action level** — each action has its own required
set. Packages don't declare aggregate capability requirements because different
actions within the same package can have different needs.

Package-level dependencies (`[[package.depends]]` in the manifest) are for **package-
to-package** code reuse (Starlark `load` from another package's `.star` files), not
for capability requirements. The two are independent.

#### What if an Action Can't Be Analyzed?

Cases where static analysis can't produce a complete capability set are rare (Starlark
is deterministic and lacks reflection), but if they arise — e.g., a helper function
dispatches through a dict-keyed by runtime state — the analyzer marks the action as
"analysis incomplete" and the author is expected to declare the missing capabilities
manually.

Until the author resolves this (either refactoring for analyzability or declaring
explicitly), the package fails the store's pre-publish check. For authored packages,
the warning appears in the Action tab but the action can still run locally.
