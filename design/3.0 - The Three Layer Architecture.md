## 3. The Three-Layer Architecture

The architecture is built on three layers. The separation between them is **load-bearing**
— not organizational convenience. Each layer has a strict contract about what it can and
cannot do, and the entire rest of the design (ownership, conflict policies, schema
mutation rules, the mapping system, the job execution model) falls out of keeping those
contracts honest.

```
Layer 1: Game Data     — static, immutable, read-only snapshot of game reality
Layer 2: User Data     — descriptive metadata the user attaches TO game data
Layer 3: Actions       — Starlark functions that read Layers 1+2 and produce/edit
                         real files. Invoked via user-owned jobs (step sequences)
                         living in Layer 2.
```

Each layer answers a different question:

- **Layer 1 — "What exists in the game?"** The packdump. It is a report, not a
  whiteboard. PackSmith reads it and displays it but never writes to it. If the game
  says `quark:rope` exists, that is not open for negotiation.
- **Layer 2 — "What do I, the user, think about what exists?"** Tags, blueprints, and
  views. This is where the user builds their own vocabulary on top of the game's
  registry — marking items for removal, grouping stone types into palettes, defining
  recipe templates. Layer 2 is pure and observable-only: it filters, queries, and
  sorts, but it never writes files or triggers jobs. It is the user's opinion about
  Layer 1, nothing more.
- **Layer 3 — "What should actually happen in the files?"** Actions (Starlark
  declarations of capability) invoked by jobs (user-authored step sequences). This is
  the only layer that writes to the modpack instance on disk. Actions cannot modify
  Layer 2's schema — they work within the vocabulary the user defined.

The flow is strictly one-directional when it comes to authority: **Layer 1 informs
Layer 2 informs Layer 3.** Layer 3 can read freely from both layers above it, and can
write back to Layer 2's *data* (assignments, bindings) subject to the ownership
system — but never to Layer 2's *schema* (tag definitions, blueprint shapes). Schema
is the user's vocabulary; actions speak that vocabulary, they don't get to change it.

#### Why the separation is load-bearing

Collapsing any two of these layers sounds like a simplification and is actually a
disaster:

- **Presenting Layer 1 as writable** would be an inherent lie to the user. A tool 
  could potentially try to abstract our concept of Actions and the registry so that the user
  literally sees themselves "deleting a `minecraft:item`", but this would always be an abstraction
  built around a registry that **is** fundamentally immutable without an actual game mod or change propagated from a mod's config.
- **If Layer 2 had side effects,** the same tag assignment could mean different
  things depending on which job happened to run last. The point of "check a box,
  document intent" collapses: intent and effect would be welded together per-job
  instead of cleanly separated, and the same tag could never drive multiple actions.
- **If Layer 3 could mutate Layer 2's schema,** an installed action could rename the
  user's tags, change their types, or delete blueprint slots out from under other
  actions. The user's vocabulary would stop being theirs. Every package update would
  be a potential schema migration.

Keeping the layers strictly separated is what lets the same `remove` tag feed a
dozen different removal jobs, lets blueprints describe relationships without
*doing* anything with them, and lets strangers' action packages run on a user's
machine without being able to reach outside their declared capabilities.

#### How the layers meet

The three layers meet at two specific, well-defined seams:

1. **Layer 2 → Layer 1** via **references.** Tag assignments and blueprint
   bindings point at registry entry IDs from the packdump. When a new packdump is
   blessed and an entry disappears, the reference becomes an **orphan** — flagged,
   surfaced, never silently cleared.
2. **Layer 3 → Layer 2** via **mappings.** Actions never hardcode the user's tag or
   blueprint names. They declare structural contracts ("I need a bool tag on
   `minecraft:item`") and the user binds their own artifacts into those slots when
   configuring a job step. The action's code sees the binding; it never sees the
   user's vocabulary directly.

Everything that follows in §3.1, §3.2, and §3.3 is an elaboration of these contracts
— what each layer contains, how it behaves, and how the seams between them stay
honest under change.
