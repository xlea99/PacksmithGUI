### 6.4 NBT Editor

**PARTLY BUILT** — the reader/writer and a value-editing tab exist; the rest of this
section is still a sketch to be worked through separately.

**What is built.** PackSmith owns its NBT reader and writer (`core/nbt.py`), verified
byte-exact against thousands of real files, and the tab is a tree with **typed value
editing**: change what a tag holds, save with Ctrl+S. The existing tag decides how its
replacement is parsed, so an edit can never change a value's type and one that doesn't fit
the type's range is refused rather than wrapped — a byte silently promoted to an int is a
corrupted save that still loads.

The **NBT payload** round-trips byte-identically; the **gzip container** does not, and
cannot. Minecraft's Java writer stamps `XFL=0` in the gzip header where Python's stamps
`XFL=2`, and two different compressors won't agree on the deflate stream regardless. What
makes that harmless is that a save with nothing changed writes nothing at all, so an
untouched file keeps its original bytes.

**What is not built: structural editing.** Adding, deleting, renaming and reordering tags
are out, and that boundary is not arbitrary — the open questions below (list addressing in
particular) are *about* structural editing. `MyList[3]` is a fragile handle precisely
because something can reorder the list. Value editing needs none of it settled.

**Ownership is whole-file for now**, per §1.1's deferral of per-key claims, not per-path as
described below. A file an action owns is read-only in the tab until taken in the Files
panel; a file inside a jar is read-only permanently and points at save-as-override (§6.5).

The NBT Editor is the PackSmith surface for inspecting and editing binary NBT files
(`.dat`, `.nbt`, and related). NBT is a binary tree of typed compound/list nodes — not
text — so it can't use the Text Editor (§6.3). Instead, it has its own tab type: a
tree viewer with expandable nodes and typed value editors, similar in shape to
NBTExplorer.

Ownership is **per-path**, not per-file. NBT is structured data — a tree of addressable
compound paths — and treating it as opaque blobs would create synthetic conflicts
between actions that touch unrelated branches. An action rewriting a village's loot
tables at `Data.Structures.Villages.<id>.LootTable` doesn't conflict with an action
rewriting `Data.Structures.Villages.<id>.Inhabitants`. The ownership model is identical
to TOML/JSON/YAML: actions claim specific compound paths, the tree viewer surfaces
per-node ownership indicators, and edit attempts against action-owned paths prompt the
standard ownership-transfer flow (§6.1).

The wrinkle specific to NBT is that lists (as opposed to compounds) are trickier to
address stably — `MyList[3]` is a fragile handle when the list can be reordered. Path
addressing within lists is a round-trip parser concern, not an ownership-model concern.

Open design work — scope (which NBT file kinds are in scope), editor ergonomics, list
addressing, structure preview for `.nbt` structure files, integration with the file
versioning system — all deferred until we sit down and design it properly.
