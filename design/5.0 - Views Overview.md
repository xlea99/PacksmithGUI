## 5. Views

The Views section describes the concrete **view renderers** — the UI widgets that
actually display what a View's config describes. The Views concept itself is defined in
§3.2.3: a View is a named **(query, renderer, renderer config)** tuple stored in the
profile database. This section answers the other half of the question: what are the
available renderers, what does each one display, and how does each one surface editing?

Views are the primary surface a user spends their time in. Most of a pack dev's session
looks like "open a View, scan/filter/edit, close the View, open another View." The
registry-table renderer dominates in practice — it's what virtually every tag-driven
workflow uses — but other renderers exist for data shapes that don't fit into rows and
columns, and the system is explicitly designed to accept new renderers additively.

### Renderer Dispatch

When a View is opened, PackSmith reads its `renderer` field, instantiates the
corresponding widget, and hands the widget the View's query result plus renderer-specific
config. The widget knows nothing about Views as a concept — it just knows how to display
its data shape and surface edits through the appropriate delegates.

Current renderers (v1.0):

- **Registry Table** (§5.1) — tabular display of registry entries with editable tag
  columns. The workhorse renderer.
- **Blueprint Node View** (§5.2) — node/graph display of blueprint schemas and
  instances. The renderer you use when data has structure and relationships rather than
  a flat list shape.

Future renderers (post-v1.0, speculative): timeline views for dated entries, schema-diff
views for comparing blueprint schemas, clade/tree views for hierarchical data, heatmap
views for tag coverage across registries. None are committed; they illustrate the kind
of thing a new renderer can be.

### Widget Reuse Outside the View System

The renderer widgets themselves are more general than the View concept — some parts of
PackSmith instantiate a renderer widget without an underlying View. These are **not
Views**; they reuse the widget for rendering convenience.

Known cases:

- **Conflict-Resolution Tabs** (§3.3) — the `ask` policy conflict UI reuses the
  registry-table widget to display one-conflict-per-row data. The tab is not a View
  (it's ephemeral, step-scoped, and doesn't live in the `views` table); the widget is
  just the most natural shape for the content.
- **Packdump Diff Review** — when a new packdump is imported and the user is reviewing
  additions/removals/changes before blessing it, that surface reuses the registry-table
  widget.

This is deliberate: the widget is a reusable UI primitive, the View is an L2 artifact.
Keeping them separable means ephemeral UI can borrow the widget without polluting the
views table with non-persistable entries.

### Adding a Renderer

Adding a new renderer in the future is additive — it doesn't touch any existing renderer
or any existing View. A new renderer registers its type identifier, its config schema,
and its widget factory; the View editor's renderer picker grows by one option.

Existing Views keep working because they reference their renderer by type identifier,
not by position. Existing renderer-config schemas are unchanged. No migration is
required.
