### 7.3 The Capability API

The capability API is the surface an action's Starlark code calls to interact with
the world. Every call site maps to one capability. The entire API lives under the
`pack` object, which is injected into the action's entry-point function by the
runtime.

#### Resolver → Handle → Operation

The core pattern is three-step, though usually written as a fluent one-liner:

1. **Resolve** a file target via a resolver function. Returns a handle.
2. **Operate** on the handle with a read/write method.
3. **(Implicit)** PackSmith stages writes, commits at step end.

```python
def run(pack, step):
    # Resolve + operate in a chain
    pack.datapacks.resolve(pack_name="my_gen", namespace="minecraft",
                            path="recipes/stone_axe_removal.json").write(recipe_json)

    # Or separate the steps for reuse
    config = pack.config.resolve(mod="quark", variant="common")
    config.write_key("[Wraith Sounds].wraith_entities", user_entity_list)
    config.write_key("[Enchantments To Begone].list", user_enchant_list)
```

Resolvers handle the pathing question (via smart routing through integration
providers when applicable, or raw paths for `filesystem`). Handles carry enough
metadata (absolute path, detected format, provider provenance, capability-specific
extras) for the operation methods to do their work correctly.

#### Resolver Namespaces

The built-in and integration-provided resolver namespaces:

| Namespace           | Resolver signature                                    | Capability               |
|---------------------|-------------------------------------------------------|--------------------------|
| `pack.datapacks`    | `.resolve(pack_name, namespace, path)`               | `datapacks.read/write`   |
| `pack.resourcepacks`| `.resolve(pack_name, namespace, path)`               | `resourcepacks.read/write` |
| `pack.kubejs`       | `.resolve(phase, name)` (phase = `server`/`client`/`startup`) | `kubejs.script_read/write` |
| `pack.config`       | `.resolve(mod, variant=None)`                        | `config.read/write` (built-in) |
| `pack.filesystem`   | `.resolve(path)` (absolute, within instance root)    | `filesystem.read/write`  |

Datapacks, resourcepacks, and kubejs resolvers are **provider-routed** — the actual
on-disk path is computed by the active integration provider at resolve time. Config
resolves the mod name to a known path via PackSmith's built-in config target registry
(a map of `mod → config file path`, populated for commonly-seen mods; extensible by
integrations). Filesystem is **raw** — the author passes an absolute path, PackSmith
only verifies it's inside `<instance_root>`.

All resolvers error if:

- The requested provider isn't active (for provider-routed namespaces)
- The target name isn't known (for `pack.config` with an unregistered mod)
- The path escapes the instance root (for `pack.filesystem`)

Resolvers do NOT check whether the target file exists. That's the write operation's
job.

#### Handle Operations

A handle exposes this uniform operation surface, regardless of which resolver
produced it:

| Method                                          | Reads | Writes | Ownership claim         |
|-------------------------------------------------|-------|--------|-------------------------|
| `handle.exists()` → `bool`                      | ✓     | ✗      | None                    |
| `handle.has_key(key_path)` → `bool`             | ✓     | ✗      | None                    |
| `handle.read_all()` → `str` or parsed structure | ✓     | ✗      | None                    |
| `handle.read_key(key_path)` → value             | ✓     | ✗      | None                    |
| `handle.write(content, *, file_must_exist=False)` | ✗ | ✓    | **Whole-file**          |
| `handle.write_key(key_path, value, *, file_must_exist=True, key_must_exist=True)` | ✗ | ✓ | **Per-key** on `key_path` |
| `handle.delete_key(key_path, *, file_must_exist=True, key_must_exist=True)` | ✗ | ✓ | **Per-key** on `key_path` |

Reads never claim ownership. Writes always do — the method name encodes the claim
kind (§6.1's ownership model is physically realized by this distinction).

#### Existence Flags

The `file_must_exist` and `key_must_exist` kwargs guard the write at the moment of
the call:

- `file_must_exist=True` — the write fails if the target file is not on disk.
  Typical for `write_key` (you're editing an existing structured file).
- `file_must_exist=False` — the write creates the file if missing, overwrites if
  present. Typical for `write` (the action is producing its own output).
- `key_must_exist=True` — `write_key`/`delete_key` fail if the specified key path
  doesn't exist in the file. Typical when editing mod configs where the key should
  be there.
- `key_must_exist=False` — create the key if missing. Useful when the action is
  adding new structure to a file it's editing in place.

When a flag check fails, the write raises a structured error. The step halts; the
user sees the resolution options in §6.1's Write-Time Existence Checks (Revert /
Accept / Release).

Defaults are chosen so the common case needs no kwargs:

```python
# "I'm producing output" — file_must_exist defaults to False
handle.write(generated_content)

# "I'm editing existing structured state" — both defaults to True
handle.write_key("foo.bar", new_value)
```

Authors flip a default when their intent differs:

```python
# Paranoid output: fail if the file went missing between runs somehow
handle.write(new_content, file_must_exist=True)

# Additive per-key: add the key if it doesn't exist yet
handle.write_key("foo.new_feature", value, key_must_exist=False)
```

#### Key Path Grammar

`write_key` / `read_key` / `delete_key` / `has_key` take a **key path** that
addresses a specific location in a structured file. PackSmith defines a unified
grammar; each format's parser translates to its native shape:

- Dotted compound access: `foo.bar.baz`
- Array/list index: `foo.bar[0].baz`
- Section-scoped: `[section_name].key` (TOML-style, equivalent to `section_name.key`
  in the unified grammar)

Each format supports a subset of the grammar:

- JSON / YAML: full grammar
- TOML: full grammar (sections map to top-level compound paths)
- NBT: full grammar (compounds + list indices)
- `.properties` / `.cfg` flat: no nesting, no indices — just flat keys
- CSS (e.g. EMI's config): selector-block + property (grammar extension for this case
  is TBD)

Calling `write_key("foo[0]", v)` on a `.properties` handle errors with a clear
message: "properties files don't support array indices in key paths." No silent
coercion.

See Live Questions below — the grammar details are sketched, not formally specified.

#### Value Types

`write_key` accepts a value. Format-specific validation rejects incompatible types:

- JSON/YAML/TOML: scalars (string/int/float/bool), lists, dicts/objects (recursive)
- NBT: typed primitives (`int8`, `int16`, `int32`, `int64`, `float32`, `float64`,
  `string`, byte arrays, typed lists, compounds). NBT's typed primitives need a
  Starlark-friendly wrapper API (`pack.nbt.int32(42)` etc.) — see Live Questions.
- `.properties` / `.cfg`: strings only

Setting an incompatible value type errors at the operation. The handle's format
determines what's valid.

#### Transactional Semantics

Every write on a handle **stages** to the per-step scratch area (§3.3's
"Transaction Scope and Rollback" section). The action's code appears to see immediate
writes — read-your-writes works inside the action — but no on-disk commit happens
until the step completes successfully.

```python
handle.write_key("foo.bar", 42)
current = handle.read_key("foo.bar")   # returns 42, from the staged write
# ... action continues ...
# Step ends successfully → stages commit atomically to disk + ownership DB.
# Step fails via pack.fail(reason) → all stages discarded, disk untouched.
```

Authors don't see or call any `commit()` or `flush()` — staging and commit are handled
by the runtime. The API is synchronous-looking; the atomicity is free.

#### Provider-Specific Extras

Handles produced by provider-routed resolvers may expose additional methods if the
active provider supplies extra sub-capabilities. For example:

```python
file = pack.datapacks.resolve(pack_name="my_gen", namespace="minecraft",
                              path="recipes/stone.json")

if file.has_capability("datapacks.ordering"):
    file.set_load_order(priority=50)   # only works if Paxi is the provider
```

Actions that require the extra can declare it as a required capability
(`datapacks.ordering`); actions that want to use it opportunistically check
`has_capability` and gracefully skip otherwise.

#### Non-File Capabilities

Not every capability is a file operation. The `pack.*` namespace includes:

- **Logging**: `pack.log(level, message)` and structured variants (see §7.4)
- **Layer 1 access**: `pack.registry.read(...)`, `pack.registry.localized_name(...)`
- **Layer 2 access**: `pack.l2.tags.read(...)`, `pack.l2.tags.write(...)`,
  `pack.l2.blueprints.read(...)`, etc.
- **Capability introspection**: `pack.capabilities.has(name)`,
  `pack.capabilities.version(name)`

These follow the same "method call = capability invocation" pattern but don't use
resolver+handle because there's no pathing question for them. See §7.4 for the full
(placeholder) catalog.

#### Live Questions

##### Key Path Grammar Formal Spec

The grammar sketch above (`foo.bar[0]`, `[section].key`) is informal. Needs a real
grammar definition: operator precedence, escaping rules for keys containing `.` or
`[`, error messages for malformed paths. Probably a small PEG grammar. Not blocking
for MVP but blocking before we ship a per-key-ownership stress test.

##### NBT Value Wrappers

NBT's typed primitives (`int8`, `int16`, `int32`, `int64`, `float32`, `float64`,
`byte_array`, typed lists, compounds) need a Starlark-friendly API. A Python int in
Starlark doesn't inherently know whether it should be written as `int32` vs `int64`
to NBT. Probably `pack.nbt.int32(x)`, `pack.nbt.list("byte", [...])`, etc. Needs
design when we do the NBT Editor section (§6.4).

##### Staging Size Cap

A write-heavy action could accumulate a large staging area before step end commit.
Probably fine for any realistic workload, but worth surfacing: do we cap staging
size, stream to temp files above a threshold, or just rely on process memory being
generous? Not MVP-critical; single-digit-GB pack dev workflows are nowhere near
concerning.
