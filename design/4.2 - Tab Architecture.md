### 4.2 Tab Architecture

The main window uses a **single Qt-owned tab bar** (QTabWidget or QTabBar) where every
tab — regardless of content type — lives side by side as peers. Some tabs are pure Qt
widgets (View tabs running the registry-table or blueprint-node renderer, §5; NBT
Editor tabs, §6.4; job editors; conflict-resolution tabs, §3.3). Some tabs are Text
Editor tabs (§6.3) backed by Monaco. From the user's perspective, they're all just
tabs:

```
Tab 1: [RegistryTable View]         ← pure Qt
Tab 2: [Text Editor → config.toml]  ← shared WebEngine, Monaco model A
Tab 3: [Blueprint Node View]        ← pure Qt
Tab 4: [Text Editor → startup.js]   ← same WebEngine, Monaco model B
Tab 5: [Text Editor → loot.json]    ← same WebEngine, Monaco model C
Tab 6: [JAR Viewer → quark.jar]     ← pure Qt
```

**One Chromium process, one QWebEngineView, one Monaco instance serves every Text
Editor tab.** Monaco natively supports multiple "models" — lightweight text buffers
that hold content, undo history, cursor position, and dirty state independently.
Switching between Text Editor tabs swaps the active Monaco model via a JS call through
QWebChannel. The swap is instant. The single QWebEngineView is reparented or
shown/hidden as the user switches between Text Editor tabs and Qt-native tabs.

This means 10 open text files cost essentially nothing beyond their Monaco model
memory. No 10-Chromium nightmare. Monaco assets are **bundled locally** (not loaded
from CDN) to eliminate network dependency.

See §6.3 Text Editor for the full treatment of Monaco as backbone and the Text Editor
surface built on top of it.

---

**Split panes — DEFERRED PAST 1.0 by decision, 2026-08-13.** Two tab groups side by side,
IntelliJ-style. Not blocked, and the architecture does not forbid it — the "one instance"
rule above is about *tabs*, and panes are a different axis.

For Qt-native tabs it is mostly mechanical: the workspace becomes N tab groups in a
splitter, and closing, retitling and icon-setting already work by widget rather than by
index, so they route to "the group holding this widget" without changing meaning.

The cost sits in the editor. One reparented `QWebEngineView` cannot appear in two places,
so a split showing two documents needs a second view — which is affordable in a way a view
*per tab* was not: the measured ~119 MB is then paid per **pane**, of which a human makes
two or three, rather than per open file. The work is splitting `EditorHost` into policy
(sources, locks, ownership signals) and per-page state (`_ready`, `_pending`, `_opened`,
`_locked`, its bridge and channel) — which is the risky kind of refactor rather than the
tedious kind, because that bookkeeping is what §6.1's lock and transfer rules ride on. It
also needs a ruling on the same document open in two panes: two pages means two buffers
that can diverge, so the answer is to refuse and focus the existing tab, as opening an
already-open document does today.

Doing it with a second *window* instead is worse, not easier: §6.3's host notes that moving
the native view between top-level windows forces Qt to recreate the window handle, which
reads as the whole application re-creating itself.

If the underlying want is comparing two files, a **diff view** is a far cheaper answer —
`createDiffEditor` inside the single existing view, needing none of the above.
