### 6.2 File Browser

The File Browser is the sidebar panel (F icon) that lets the user find files in the
modpack instance. It is NOT a dumb directory listing — it's a **semantic file browser**
that understands Minecraft folder conventions and presents files by *purpose*, not just
by path.

Minecraft instance directories are dense forests of wildly different file types scattered
across deeply nested structures. A pack dev constantly navigates two mental hierarchies
simultaneously — the physical file path AND the conceptual purpose — and they frequently
diverge. "Am I in asset packs or data packs right now?" "Am I in server scripts or
client scripts?" A raw tree view doesn't solve this.

Packsmith is uniquely positioned to do better because it already has the packdump — it
knows which mods are installed. Mod-specific integrations (§7) register **smart folders**
and path-resolution logic that the File Browser uses to present a clean, purposeful
hierarchy over whatever mess the underlying filesystem looks like.

#### Basic, Smart, and Tracked Folders

**Three subtabs, not a mode toggle** (2026-08-20). The panel used to carry a dropdown at the
top; Basic and Smart are two ways of *looking*, and a dropdown above the tree made them read
as a filter applied to it. They are separate browsers behind separate tabs now, which also
means a browser IS smart or IS NOT — there is no state in which one is in the wrong mode for
its loader, or aimed at a tracked root where its categories describe nothing.

The third tab is **Tracked Folders** (§6.6): the places Packsmith may look at all. It lives
here rather than in a sidebar slot of its own because it is a list you configure once and
then browse *through* — a top-level slot would have put a rarely-touched settings list
beside the six things you use daily. It belongs next to the browser it configures.

"Honest Mode" is called **Basic** in the UI. The old name described what it was *not* doing,
which is only meaningful once you already know about the other one.

The two browsing tabs:

**Smart** — files organized by purpose (Basic is what you land on):

```
📦 Datapacks              ← provided by §7.1 Global Pack Loader Integration
📦 Resource Packs         ← provided by §7.1
📜 KubeJS                 ← provided by §7.2 KubeJS integration
   ├── Server Scripts
   ├── Client Scripts
   └── Startup Scripts
⚙️ Mod Configs            ← built-in, covers config/
📁 Everything Else        ← the remaining instance root
```

The smart categories are not static — they come from the integrations that are
active for the current profile. If no global datapack loader is installed, the
Datapacks and Resource Packs categories don't appear (or show an empty-state hint
pointing at §7.1). If KubeJS is installed, the KubeJS subtree appears with its
three script folders. Other integrations can be installed to provide further
functionality here.

**Basic** — raw directory tree rooted at whichever tracked root is selected (§6.6);
the Minecraft instance unless you pick another.
No abstractions, no reordering, just the filesystem. Useful when the smart mode's
opinions get in the way, or when the user is looking at something that doesn't
fit any registered smart-folder category.

Both modes share the same underlying selection state — switching modes doesn't
lose the user's place if the current file exists in both views.

#### Path Resolution as an Integration Contract

This also directly supports the action contract: an action doesn't say "write to
`config/paxi/datapacks/my_pack/data/minecraft/recipes/stone.json`." It says "write this
recipe JSON for namespace `minecraft`, recipe `stone`." The active Global Pack Loader
integration (§7.1) resolves the actual path based on the profile's detected configuration.
Actions become portable across loader setups — a job that ran against a Paxi-using
profile will run against an OpenLoader-using profile without editing.

This is also what powers the JAR Viewer's save-as-override workflow (§6.5): given an
internal jar path like `data/quark/recipes/foo.json`, the loader integration knows
which user-facing datapack directory to write into.

#### Tracked vs. Untracked Rendering

Every file Packsmith has an ownership record for — user-owned or action-owned — renders
normally. Files the ownership system has never touched (untracked) render with a muted
visual treatment: slightly desaturated text, dimmer tint, or a subtle marker. They are
not hidden — hiding them would make the browser useless — but the muted rendering makes
the tracked/untracked distinction visible at a glance.

Editing an untracked file in the Text Editor (§6.3) auto-claims user ownership on the
first keystroke; the file transitions to tracked and renders normally on the browser's
next refresh. No modal prompt, no ceremony — editing is the gesture that tracks it.

The claim fires on first edit rather than on open, which this originally specified. A
claim is not free: it blocks actions from writing the file (§6.1), so claiming on open
would mean that opening a file to *read* it silently locks an action out of its own
output. Reading is not a claim. "Editing is the gesture that tracks it" was always the
rule; the trigger now matches the sentence.
See §6.1's External Modification Detection for what tracking actually buys the user
(drift detection, versioning, the ownership-transfer flow).

#### Context Menu Actions

Context menus in Smart Mode are integration-aware. A right-click in the Datapacks
category offers "New Datapack" (from §7.1); a right-click in KubeJS > Server Scripts
offers "New Server Script" (from §7.2). Basic shows a standard filesystem
context menu (New File, New Folder, Rename, Delete, Reveal in Explorer).

Every integration that registers a smart folder can register context-menu actions for
it — see §3.4 for the registration API.

The filesystem actions all touch ownership, and each answers it differently:

- **New File** claims the file for the user on creation. It's the one claim that needs no
  prompt: the user just made the file, so there is no prior owner to take it from.
- **Rename** *carries* ownership to the new path. Ownership belongs to the artifact, not
  to the string naming it — dropping the record would launder an action-owned file into
  an untouched one, which is precisely the transition §6.1 refuses to make quietly. A
  rename does break the link between an action and the path it writes, so renaming
  something an action manages warns first: the action will recreate the old path on its
  next run. It warns rather than blocks; nothing is being destroyed.
- **Delete** drops the record along with the bytes. Keeping it would leave the next file
  to take that name pre-owned by a stranger — and if that stranger were an action,
  hard-blocked for a reason nobody could explain. A folder's confirmation counts the
  tracked files beneath it and how many of them actions write, because "delete config/"
  means something very different depending on the answer.

Deleting an action's output does **not** stop the action; the next run recreates it. The
confirmation says so, since "delete the file" is a natural but wrong way to try to undo an
action's work — the right lever is the job, not the file.


#### Live Questions

##### External Directories — *answered in §6.6 (2026-08-20)*

Specified as **§6.6 Tracked Roots**. Every requirement below is carried into it, and the
hardest one turned out to need no new machinery: the "second, explicit, per-root opt-in"
this section asks for is a **binding**. Adding a root grants a *person* a view of it;
binding it to a step grants *one action* a target. The original text is kept because its
reasoning is the reasoning §6.6 rests on.

**Decision: yes, but opt-in.** The user may add directories outside the Minecraft instance
to the browser, and edit files in them. Not an escape hatch — each is a folder the user
explicitly registered, per profile, the way an editor takes workspace folders. The
motivating cases are real: pack content developed in a git repo outside the instance,
and reference material the user wants beside their work.

This costs nothing in safety because **the action sandbox is a separate boundary**. §7.4
confines `pack.filesystem` to `<instance_root>`, and adding a browser root does not move
that line. Added roots are a *user* surface.

Three things the eventual implementation has to get right:

- **The userdata guard is containment in both directions.** Packsmith's own
  `userdata/` must never become reachable through the file browser — that would let a
  user edit `.star` sources through a door that doesn't apply provenance rules (§3.3.1),
  bypassing the Actions panel. Checking `path != userdata` is not enough: adding userdata's
  *parent* defeats it. No added root may contain, or be contained by, userdata.
- **Paths need a root qualifier.** Ownership records and rollback snapshots are currently
  keyed by a path relative to the single instance root. Multiple roots means every stored
  path must name which root it belongs to.
- **Do added roots extend the action sandbox?** Default **no** — actions stay confined to
  the instance. The consents differ: "let me edit here" is not "let downloaded code write
  here." If an action ever legitimately needs to write into an added root (generating into
  a datapack repo, say), that should be a *second*, explicit, per-root opt-in — never
  something acquired for free by adding a folder.

##### Symlinked Content Inside the Instance

`FileStore` resolves paths before checking containment, and resolution follows symlinks —
so a symlink or junction pointing *out* of the instance is rejected even though it visibly
lives inside it. Symlinking external content into an instance (datapacks, global packs) is
normal practice for pack devs, so this will surface as a confusing error: "path escapes the
instance root" about a path the user can see inside the instance.

This was a side effect of `resolve()`, not a decision. Options: keep it (strict, safe,
occasionally baffling); allow symlinks whose *link* is inside the root even when the target
isn't; or require the target to be registered as an added root (above), which folds this
into the same opt-in model and is probably the honest answer.
