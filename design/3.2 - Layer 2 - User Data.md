### 3.2 Layer 2: User Data

Layer 2 is where PackSmith becomes something. It consists of three primitives — **Tags**,
**Blueprints**, and **Views**. Layer 2's invariant: **no side effects on external state.**
It computes (filters, queries, sorts), but it never writes files, never triggers jobs,
never modifies anything outside the database. It is pure, idempotent, and observable-only.
That decoupling is critical: the same tag can drive multiple jobs, and changing a job
doesn't change the user's intent.

To be precise: the user *does* assign tags inside a view's table — but the view config
itself carries no assignment logic. The assignment happens through the table delegate,
which the view happens to be rendering. The view defines what you see; the table UI is
where you act.

All user data is stored in a per-profile SQLite database (`profile.db`).

#### 3.2.1 Tags

Tags are user-defined scalar values assigned to registry entries from Layer 1. They are
NOT game data. Each tag is **strictly scoped to a single registry type** — a `remove` tag
on `minecraft:item` is a completely separate definition from a `remove` tag on
`minecraft:block`. This is not a limitation; it's load-bearing. Registry types have
fundamentally different semantics, and a tag that means "remove this item from crafting"
is a different concept from "remove this block from worldgen." Separate definitions,
separate assignments, separate queries.

The ergonomic cost is real: tags that have genuinely identical semantics across registry
types (e.g., `mod_source` — "which mod introduced this?") must be defined N times, once
per registry type. This is accepted as the right tradeoff — the alternative (cross-registry
tags) would blur the boundary between fundamentally different domains and complicate every
query path.

Five types:

| Type        | Values                    | Example                          |
|-------------|---------------------------|----------------------------------|
| `bool`      | `true`, `false`, or unset | `remove`, `is_food`, `is_hidden` |
| `string`    | any text, or unset        | `notes`, `lang_override`         |
| `enum`      | one of N options, or unset| `tier` (early/mid/late/end)      |
| `number`    | int or float, or unset    | `weight`, `stack_size`           |
| `reference` | a registry entry ID from any registry type, or unset | `material` (diamond sword → `minecraft:diamond`) |

The `reference` type is a pointer to a specific registry entry. Unlike the other scalar
types, it stores a full registry ID (e.g., `minecraft:diamond`) and is validated against
the packdump. This enables lightweight cross-registry relationships without needing a full
blueprint — "what material is this tool made of?" is a single tag, not a schema.

Tags can have **default values**. An unset tag with a default displays and behaves as
the default in the UI (including copy operations), but the default is NOT written to the
database — the distinction between "explicitly set to X" and "defaulting to X" is
preserved.

**Where the query engine stands on that distinction** (settled 2026-08; it was previously
implied only for the UI, and the two readings were indistinguishable in practice):

| Question | Sees defaults? | Why |
|---------------------------|-----|--------------------------------------------------|
| `t:remove == false` (value comparison) | **yes** | It asks *what is this tag's value here*, and the answer for a pristine cell is its default — the same answer the table shows. Filtering must agree with your eyes. |
| `HAS t:remove` (existence)             | **no**  | It asks *was a decision recorded here*, which only the assignment row can answer. Inflating it made `HAS` true for every entry on any defaulted tag, and `NOT HAS` — the gap-finding idiom — return nothing. |

The two are deliberately different questions, and a defaulted tag is exactly where they
diverge: every entry has a *value*, only some have an *assignment*. The pair partitions the
registry, so "defaulting to false" and "explicitly false" never both match the same filter.

##### Tag Definitions vs. Tag Assignments

A critical distinction runs through the rest of PackSmith:

- **Tag definitions** (name, type, registry scope, enum values, default) are **user-only.**
  Actions cannot create, modify, rename, or delete tag definitions. Schema is the
  user's vocabulary; actions work within it. (Note that *retyping* is absent from that
  list — not because actions may do it, but because **nobody** may; see Tag Schema
  Evolution below.)
- **Tag assignments** (which entries have which values) are **hybrid.** Both the user and
  actions can create, modify, and delete assignments, subject to the ownership system below.

This same split applies to blueprints (schemas user-only, instances and bindings hybrid)
and is the single most important rule about what Layer 3 can and cannot do to Layer 2.

##### Identity, Naming, and References

A tag definition's **identity is a surrogate id**, not its name. The name is a *label* —
user-facing, editable, and unique within its registry scope, but never the thing anything
points at internally. This is the same split Views use (§3.2.3), and it exists so that
renaming a tag is a one-row metadata update rather than a migration.

Where a reference lives determines what it references:

| Reference | Points at | Why |
|-----------|-----------|-----|
| Tag assignments | **id** | Internal, per-profile. A rename must not touch a single assignment row. |
| Job step bindings (mappings) | **id** | Internal, per-profile. Stable across renames — and makes "what breaks?" an exact query rather than a string search. |
| Saved View queries (§3.2.4) | **name** | Views are **portable** — forked, exported, shared. An id is meaningless in another profile; a name can still resolve. |
| Action manifests (`likely_name`) | **name** | Authored externally by someone who has never seen this profile. |

The consequence worth stating plainly: **ids are stable but local; names are fragile but
portable.** Neither is right everywhere, so PackSmith uses each where its property matters.
Renaming therefore costs nothing for assignments and bindings, and costs an automatic
rewrite of saved View queries (below).

Why not make everything id-based? Because it produces a silent, dangerous failure. If a
user renames `remove` → `hide` and then creates a *new* tag called `remove` with different
semantics, an id-bound automation keeps operating on `hide` while the user believes it
targets `remove`. Making everything name-based inverts the same failure — the automation
silently retargets to the new `remove`, swapping the data underneath a destructive
operation. The resolution is not to pick a side but to make **the rename itself loud**
(below).

##### Tag Schema Evolution

Tag definitions are live artifacts: users add enum values, rename tags for clarity, and
retire vocabulary that stopped being useful. The rules below follow one principle, the
same one blueprints use (§3.2.2): **additive changes are silent; destructive changes are
loud, state their blast radius before committing, and never fail silently afterward.**

| Mutation | Rule |
|----------|------|
| **Add enum value** | Free and silent. Purely additive — nothing that exists can break. |
| **Remove enum value** | **Allowed**, but loud. Reports both blast radii before committing (below). |
| **Rename tag** | **Allowed**, but loud. Bound job steps must be explicitly relinked; saved Views follow automatically. |
| **Retype tag** | **Forbidden.** Undefine and redefine instead. |
| **Undefine tag** | Cascades to every assignment. Confirmation names the count being destroyed. |

**Removing an enum value** has two independent blast radii, and the confirmation states
both:

- **Automations** — every bound job step whose mapping declares that value in
  `requires_values` (§3.3). This is deterministic precisely *because* actions declare the
  values they depend on.
- **Assignments** — every entry currently holding that value. These are not deleted; they
  become **orphaned assignments** (see Orphan Detection below), resolvable in the Errors
  panel.

> **Remove value `late` from `tier`?**
> 23 assignments use it, and 1 job step (`stone_job` step 2 → `palette:standardize`)
> declares it. Those assignments will be orphaned until you resolve them.

**Renaming a tag** never touches data — assignments and bindings reference the id. What it
touches is *meaning*, so the ceremony is about references, not rows:

- **Job step bindings** (things that *act*) are flagged as needing attention, and **the step
  refuses to run until the user explicitly relinks it.** This is the identical rule §3.2.2
  applies to blueprint schema mutation, and it is what prevents the silent-retarget failure
  described above.
- **Saved View queries** (things that only *observe*) are rewritten automatically — the
  query's `Tag("old")` nodes become `Tag("new")`. No prompt, no breakage; the column header
  simply shows the new name.

That split — **loud when it acts, quiet when it observes** — is the general rule. Blocking
a read-only View behind a relink prompt would be noise; letting a destructive automation
silently change targets would be dangerous.

**Retyping is forbidden** rather than orphaning-with-coercion (the blueprint approach)
because a tag has no structure to preserve. Changing `weight` from `number` to `enum`
doesn't reshape its values, it invalidates them — the old data is meaningless under the new
type. Undefine-and-redefine is the honest expression of that, and it eliminates the entire
coercion-proof problem space that §3.2.2 needs for slots. Consistent with the "start strict,
loosen if a real need surfaces" stance taken elsewhere.

One deliberate narrowing from the blueprint precedent: §3.2.2 makes *any* action touching a
blueprint with orphaned instances refuse to run. Tags do **not** adopt that blanket rule —
23 stale `late` values must not block an automation that only reads `remove`. A step refuses
to run only when a value **it declares** is gone. Precision instead of collateral blocking,
which is only possible because mappings declare their required values.

##### Assignment Ownership

Every tag assignment that exists in the database has exactly one owner: either the user
or a specific action. Ownership is not a property of the value — it's a property of the
*existence of the assignment itself.*

The rule:

> An assignment either exists or it doesn't. If it exists, someone owns it.

This gives four practical states per (entry, tag) pair:

| State                        | Assignment row? | Ownership        |
|------------------------------|-----------------|------------------|
| **Pristine**                 | No              | Nobody           |
| **User-owned**               | Yes             | The user         |
| **Action-owned**             | Yes             | A specific action|
| **(Ownership-transferred)**  | Yes             | New owner        |

State transitions:

- **Pristine → user-owned:** user interacts with a cell (checks a box, types a value,
  picks an enum option). Assignment is created, user owns it.
- **Pristine → action-owned:** an action writes to this (entry, tag). Assignment is
  created, the action owns it.
- **User-owned value change:** user edits an existing user-owned assignment. Value
  updates; user still owns.
- **Action-owned value change by user:** user edits an action-owned assignment. Ownership
  transfers to user; value updates. Transfers are loud (see below).
- **User-owned value change by action:** an action tries to write to a user-owned
  assignment. The action's declared conflict policy fires (see §3.3).
- **Any state → pristine:** user explicitly deletes the assignment (Del key on the cell,
  context-menu "Clear assignment"). Assignment row is removed; nobody owns anything
  here anymore.

The subtle point worth naming: **"unset" is not the same as "pristine."** If a user
explicitly flips a bool from `true` to `false`, the assignment still exists with value
`false` — the user owns the decision "this should be false." This looks identical to a
pristine cell visually unless PackSmith renders the ownership indicator. The only way to
return to pristine is the explicit delete action.

For `bool` tags specifically, this means the registry table view must distinguish three
visual states per cell, not two:

- Pristine: truly empty cell, no indicator

> **As built, a pristine bool shows a faint tri-state checkbox rather than nothing** — a
> deliberate departure, kept because "truly empty" is indistinguishable from "not a bool
> column" and from "not editable", so the user cannot tell where they are allowed to click.
> The ghost says *this is a bool and it is yours to set*; it is visibly different from both
> checked and unchecked. What it must never do is imply a value, which is why it is
> tri-state rather than an unchecked box. **The load-bearing distinction — ownership
> bar vs no bar — is unchanged**, and that is what separates pristine from an explicit
> `false`.
- Assignment exists with value `false`, owned by someone: unchecked checkbox with an
  ownership tint/dot/border
- Assignment exists with value `true`, owned by someone: checked checkbox with an
  ownership tint/dot/border

For enum/string/number/reference tags, the pristine-vs-owned distinction is naturally
visible (empty cell vs. cell containing a value), but the ownership indicator still
appears to distinguish user-owned from action-owned.

Loud ownership transfer: when the user edits an action-owned assignment, they see a brief
confirmation ("This assignment was managed by `mod_classifier:classify`. Taking ownership
will prevent that action from updating it on future runs. Continue?"). Once confirmed,
the cell transitions to user-owned and the former action owner is displaced. The reverse
— an action writing to a user-owned assignment — is gated by the conflict policy system
in §3.3 and never silent.

##### Key Operations

- **Define/Undefine** — create or destroy a tag type (undefine cascades to all
  assignments). User-only operation; actions cannot do this.
- **Assign/Unassign** — set or clear a tag value, supports bulk operations. Creates or
  updates an assignment row, establishes ownership. Available to both users (through the
  UI) and actions (through the API, subject to conflict policy).
- **Delete assignment** — fully remove an assignment row, returning the (entry, tag) pair
  to the pristine state. User-only; actions cannot fully delete an assignment, only write
  over it (which transfers ownership rather than clearing it).
- **Query** — filter registry entries by tag values with operators: `eq`, `neq`, `in`,
  `not_in`, `gt`, `lt`, `gte`, `lte`, `exists`, `not_exists`. Also `owned_by_user`,
  `owned_by_action`, `owned_by(<action_ref>)` for ownership-aware queries.
- **Orphan detection** — find assignments that reference something no longer present. An
  assignment is orphaned when either:
  1. its **entry** no longer exists in the current packdump (important after registry
     changes), or
  2. its **value** is no longer part of its definition (an enum value was removed).

  Both are the same proposition — *this assignment points at something that isn't there* —
  so they share one state, one report, and one place to resolve it. Neither is stored:
  orphan status is **derived** by checking assignments against the packdump and against
  their definitions, so it can never go stale. Orphans surface in the Errors panel (§4.1)
  with three one-click resolutions: **Clear** (delete the assignments), **Reassign to…**
  (bulk-set them to a valid value), or **Restore** (re-add the removed enum value to the
  definition — the analog of §3.2.2's "Revert Schema").

#### 3.2.2 Blueprints

Blueprints solve the problem tags can't: **modeling relationships between registry
entries.**

Tags are flat — they describe a single entry in isolation. But modpack development
constantly requires reasoning about *groups* of related entries that the game's flat
registry doesn't formally connect. The canonical example is stone palettes.

##### The Stone Problem

In vanilla Minecraft, stone types (granite, andesite, diorite, deepslate...) can be
processed into various cuts (polished, bricks, tiles, chiseled...) and each cut exists in
multiple forms (base block, stairs, slab, wall, vertical slab). But the coverage is
**completely arbitrary** — you can craft polished granite but not polished tuff; deepslate
has a cobbled variant but granite doesn't; Quark adds granite bricks but via polished
granite, not raw.

Layer 300 mods on top and it becomes an incomprehensible mess of missing holes and bizarre
inconsistencies. To enforce consistency, you need to:

1. **See** every stone type × cut × form combination
2. **Identify** which slots are filled, which are empty, and which come from which mod
3. **Fill gaps** — generate textures, blocks, recipes for missing combinations
4. **Standardize recipes** — enforce that the same crafting pattern works across all
   stone types

This requires modeling the *relationship* between `minecraft:granite`,
`minecraft:granite_stairs`, `minecraft:polished_granite`, `quark:granite_bricks`, etc. —
entries from different mods that are conceptually one "stone type."

##### How Blueprints Work

A **Blueprint** is an instantiable schema — a struct, or a class without methods.

1. **Define** a blueprint schema: `StoneType` has inline groups (`polished_cut`,
   `brick_cut`, `chiseled_cut`...) and each group has slots (`base`, `stairs`,
   `slab`, `wall`, `vertical_slab`).

2. **Instantiate** the blueprint: create `StoneType:granite`, `StoneType:andesite`, etc.

3. **Bind** entries to slots: `StoneType:granite.polished_cut.base` →
   `minecraft:polished_granite`, `StoneType:granite.polished_cut.stairs` →
   `minecraft:polished_granite_stairs`, etc.

4. **Identify gaps**: empty slots = missing content that needs to be generated or sourced.

5. **Automate**: actions can query blueprint instances to generate recipes, detect
   duplicates, compile "you need to go build these in your glue mod" lists, etc.

Blueprints are **purely descriptive** — they live on Layer 2, not Layer 3. They organize
information. They don't do anything. But actions can access them, and that's where the
power comes from.

##### Nesting and Structure

Blueprints support two kinds of structure:

**Inline groups** — structural nesting within a single blueprint definition. The user
thinks of this as one blueprint with grouped fields, not multiple separate blueprints:

```
StoneType:
  base_block: minecraft:block
  polished:                         ← inline group
    base: minecraft:block
    stairs: minecraft:block
    slab: minecraft:block
    wall: minecraft:block
    vertical_slab: minecraft:block
  bricks:                           ← inline group
    base: minecraft:block
    stairs: minecraft:block
    ...
```

Nesting depth is **unlimited.** At the DB level it's parent-child rows in
`blueprint_slots`, but the user sees one cohesive schema definition.

**Blueprint references** — a slot can reference an instance of *another* blueprint. This
is a pointer, not a copy. If the referenced instance is updated, the reference sees the
change automatically.

```
VillageVariations:
  inhabitants: minecraft:entity_type
  wood_type: WoodType               ← reference to a WoodType instance
  stone_type: StoneType             ← reference to a StoneType instance
```

Binding: `VillageVariations:canyon_villagers.stone_type` → `StoneType:granite`

This composes arbitrarily. `VillageVariations` references `StoneType`. Some future
blueprint could reference `VillageVariations`. No depth limit — it's just pointers with
no data duplication.

**Schema-level cycles are allowed.** A `CladeNode` blueprint with a `descendants` slot of
type `CladeNode` is a legitimate and powerful pattern (recursive tree structures like
cladograms). The schema is just a type definition; cycles there are fine. **Instance-level
cycles** (A references B references A) are a harder question — they could create infinite
loops in traversal, rendering, or action queries. See Open Questions.

##### Slot Typing

All slots are **strictly typed.** Two kinds of *reference* type:

- **Registry type** (`minecraft:block`, `minecraft:item`, etc.) — binds to a registry
  entry ID from the packdump. Validated on bind, autocomplete filtered to the correct
  registry.
- **Blueprint type** (`StoneType`, `WoodType`, etc.) — binds to an instance of that
  blueprint. Validated on bind, autocomplete shows available instances. **Instance-level
  cycles are refused at bind time** — see Live Questions.

...and four **scalar** types: `string`, `number`, `bool`, `enum` (the last carrying its own
value list, like an enum tag). Scalars were added during implementation because a schema
that can only hold pointers can't hold the notes *about* them — "which mod should own this",
"why is this one deliberately empty" — and the alternative was a parallel tag on an entry
that may not exist yet. They are inert: nothing dereferences a scalar, so they add no new
traversal or validation machinery beyond their own type check.

No or-types for now. If a genuine need surfaces during dogfooding, it can be added. Start
strict, loosen if needed.

##### Cross-Reference

A single registry entry can appear in multiple blueprint instances without restriction.
`minecraft:granite` can be bound in both `StoneType:granite` and `BuildingBlocks:granite`.
No special tracking — queryable through `instance_bindings` if needed ("show me every
blueprint instance that references this entry").

##### Auto-Population

There is significant room for an action that auto-fills blueprint slot bindings based on
naming conventions and registry search (e.g., if the stone type is "granite" and the slot
is "polished_base", search for `*polished_granite*` in the item registry). This is one of
the most practically valuable features of the blueprint system — without it, manually
binding hundreds of slots across dozens of instances is tedious enough to undermine the
whole concept. But mod naming conventions are wildly inconsistent (`polished_granite` vs.
`granite_polished` vs. `create:polished_granite`), so the approach needs serious design
work. See Open Questions.

> **Superseded — see "Is Auto-Population Even Required?" in Live Questions.** The search
> half of this was built for §5.3's recommendation templates and works; what the paragraph
> above gets wrong is the *value* claim. Measured on a real schema, a bulk pass could
> decide 6 of 33 unfilled slots, and those six are the ones already cheapest to fill by
> hand. Most empty slots are empty because the content does not exist, which is a fact
> about the pack rather than a matching failure. Not planned for v1.

##### Schema Evolution

Blueprint schemas are live, editable artifacts — users will add, remove, rename, and
retype slots on schemas that already have instances. The mutation rules are designed
around one consistent principle: **non-destructive changes propagate silently;
destructive changes orphan at the instance level and refuse to participate in actions
until the user explicitly resolves their intent.**

**Add slot.** Existing instances gain the new slot in an unset state. A non-modal
notification surfaces the change ("Added `author` to `Recipe Blueprint`. 42 existing
instances now have this slot, unset."). Propagation is silent; the notification is the
only visible side effect. Actions that query the blueprint see the new slot normally —
`None` for unset bindings.

**Remove slot.** If zero instances have a binding for the slot, it is removed silently —
no confirmation, no orphaning. If any instance has a binding, *every instance of the
blueprint that had a binding becomes orphaned* (not just the removed slot's row). Whole-
instance orphaning is deliberate: schema destruction is significant enough that the user
should be forced to confirm intent before downstream actions proceed. **Any action that
touches a blueprint with orphaned instances refuses to run until the orphans are
resolved.** The instance does not silently degrade.

**Rename slot.** Bindings migrate automatically — this is a metadata-only operation, not
a remove-plus-add. A confirmation dialog surfaces the impact ("Rename slot `author` →
`creator` on `Recipe Blueprint`? This will update 42 existing instances. The old name
will no longer exist.") before the rename commits. No orphaning, no data change.

**Retype slot.** The dangerous case. Default behavior: **retype orphans every instance
with a binding to that slot** (same rule as Remove — whole-instance orphan, actions
refuse).
However, PackSmith checks for provable loss-free coercion before showing the retype
dialog:

- **If all existing bindings can be losslessly coerced** to the new type
  (e.g., `int` → `float`, `enum` → `string`, `string` → `enum` where all values are in
  the new enum's set), the dialog offers three choices:
    - *Retype & Auto-Coerce* — apply the type change, convert all bindings, no orphaning
    - *Retype & Orphan* — apply the type change, orphan all instances anyway (explicit
      user choice to re-bind manually)
    - *Cancel*
- **If coercion would lose data or fail** (e.g., `int` → `registry reference`, narrowing
  conversions with out-of-range values), auto-coerce is not offered. The dialog shows
  only *Retype & Orphan* or *Cancel*.

Default and strictness are preserved; the auto-coerce path exists only when PackSmith
can *prove* the coercion is lossless. This keeps the rule predictable ("retype orphans")
while eliminating friction in cases where orphaning would be pure theater.

##### Mapping Re-Validation on Schema Mutation

When a user confirms a rename, retype, or removal on a blueprint slot, PackSmith
finds all action mappings (across all installed packages) whose `required_shape`
references the mutated blueprint schema. Each affected mapping is re-validated
against the new schema shape.

If validation fails (a rename broke the shape contract, a retype changed a slot's
kind, a removal deleted a slot the shape requires), every job step currently bound
to the affected mapping is flagged as needing attention — the step refuses to run
until the user re-binds or the schema is reverted.

This is surfaced in the pre-mutation confirmation dialog: "This rename will
invalidate 3 action mappings: `stone_job` step 2 (`removal_suite:nuke`),
`glue_mod_job` step 1 (`compat:fill_gaps`), `brick_compat` step 4
(`palette:standardize`). Those steps will need to be rebound." The user makes an
informed choice before the mutation commits.

##### Resolving an Orphaned Instance

When an instance is orphaned (via slot removal or retyping), it surfaces in the Errors
panel under an "Orphaned Instances" section and is locked against action access. The user
has four resolution options available per-instance (or applied in bulk):

1. **Discard** — delete the orphaned bindings permanently, un-orphan the instance. Any
   data tied to removed or retyped slots is lost.
2. **Preserve** — keep the orphaned bindings in a limbo state, un-orphan the instance
   for action purposes. The limbo data is not exposed to actions but is retained in the
   database, useful if the slot might return or for historical reference.
3. **Revert Schema** — undo the schema mutation that caused the orphaning. Every instance
   of the blueprint snaps back to the pre-mutation state.
4. **Change Problematic Values** — applicable only for retype orphans. Opens an inline
   editor where the user re-binds the problematic slot values under the new type. Once
   all problematic bindings are re-bound, the instance un-orphans automatically.

All four are one-click actions. The user must choose one; there is no "ignore" or
"dismiss" that silently proceeds with a broken instance.

Three consequences of that rule were settled in implementation rather than here, and are
recorded now because each is a real constraint a user can hit:

- **A blueprint with unresolved orphans refuses further destructive schema edits.** You
  cannot remove a second slot while the first removal is still unresolved. This follows
  from "refuse to participate until the user explicitly resolves their intent" — stacking
  mutations would make the pending resolutions ambiguous about which change they answer.
- **Resolving every orphan of a mutation ends its revertibility.** "Revert Schema" undoes
  the mutation that caused the orphaning; once nothing is orphaned by it, the mutation is
  settled and there is no longer a resolution in flight to revert. Revert is an *escape
  from the orphaned state*, not general undo.
- **Blueprint conflict policy is keyed per blueprint, not per slot.** An action declares
  one policy for the schema it binds, not a different rule for each slot. Two mappings
  binding the same blueprint with different policies is refused outright (§3.3), so the
  per-blueprint key is the finest granularity that can be unambiguous.

##### Schema vs. Data Ownership

Blueprints follow the same split as tags:

- **Blueprint schemas** (the shape — slot names, types, nesting, blueprint references)
  are **user-only.** Actions cannot create, modify, rename, retype, or delete schemas.
- **Blueprint instances and slot bindings** are **hybrid.** Both the user and actions can
  create instances, edit bindings, and delete instances, subject to the ownership system.

Ownership on blueprint data operates at **per-binding granularity**, not per-instance.
Each `(instance, slot)` binding has its own owner (user or action). An instance created
by an action can have its bindings individually overwritten by the user, transferring
ownership slot-by-slot. Instance creation itself is attributable — "this instance was
created by `mod_classifier:classify`" — but once bindings start getting touched by
different parties, the instance becomes a hybrid artifact with per-slot ownership.

Conflict behavior when an action tries to write to an already-bound slot is governed by
the action's declared conflict policy (§3.3), identical to tag assignment conflicts.

##### Database Schema

```
blueprints          — the schema definition (the "class")
blueprint_slots     — fields/groups per blueprint (parent_slot_id for nesting, type for
                      registry type or blueprint reference)
blueprint_instances — a named instantiation ("granite", "andesite")
instance_bindings   — slot → registry entry ID or blueprint instance ID
```

#### 3.2.3 Views

A **View** is a saved, reopenable rendering configuration — a named
**(query, renderer, renderer config)** tuple. The query decides what data flows in;
the renderer decides which UI widget displays it; the renderer config covers whatever
knobs that specific renderer exposes (column selection, node layout, sort order,
slot visibility, etc.).

The separation is load-bearing: the View concept is not married to any specific
widget. Multiple renderers will exist — the registry-table renderer for entry-list
views, the blueprint-node renderer for schema/instance graphs, and others to come.
A View picks one renderer; the renderer instantiates against the View's config.
Adding a new renderer in the future is purely additive — new renderer option, new
config shape, existing Views unaffected.

Views are **strictly read-only as a concept** — the View *config* carries no
assignment logic and never triggers jobs. Editing happens through the rendered
widget (a registry table's cell delegate, a blueprint node's slot editor, etc.),
not through the View itself. Separation of church and state.

Every View specifies, at minimum:

- A **query** that selects what to display (see Filtering below)
- A **renderer** chosen from the set of available renderers
- That **renderer's own config** — shape varies per renderer

Registry-table-specific config (which registry type to target, which tag columns to
show, which columns are editable vs. read-only) lives with the registry-table
renderer's own documentation, not here. Other renderers will have entirely different
config shapes — a blueprint-node view has no columns; it has node layout and slot
visibility options instead.

Examples ranging from trivial to complex (all registry-table Views, since that's
the renderer most Views use in practice):

- "All `minecraft:item` entries where `remove` == true" (simple tag filter)
- "All `minecraft:item` entries, showing `remove`, `hide_only`, `lang_override` columns"
  (the main item browser)
- "All `minecraft:entity_type` where `is_creature` == true, showing `species_name`,
  `clade`, `diet` columns" (creature taxonomy view)
- "All `minecraft:item` where `is_food` == true, showing `food_group`, `nutrition_value`,
  `special_food` columns" (diet system)

Even the main item browser is itself a View — one that happens to use the
registry-table renderer with a near-empty filter. The system must handle **hundreds
of views** gracefully — most packs will accumulate 200-300, the vast majority being
trivially simple "show me X where Y" configurations.

##### Filtering

Every opened view has a **filter bar** at the top of its table. This is where queries
live — not in the sidebar, not in a separate dialog. The filter bar supports two modes:

- **Query builder** (visual): filter rows with dropdowns — pick a tag, pick an operator,
  pick a value, click plus to add another condition. AND/OR toggle between rows. Zero
  learning curve, discoverable, good for the common case.
- **Text query** (direct): a text representation of the same filter, editable inline.
  Fast for power users who know what they want.

The two modes stay in sync — editing the text updates the builder, using the builder
updates the text. The builder IS the documentation for the query syntax. Users learn the
text language by watching what the builder produces.

> **As built (2026-08), this is one surface short.** The filter bar is text-only, and the
> visual builder lives in a separate ⚙ dialog rather than beside it — so the two modes
> exist but are not the single synced surface described above, and nobody learns the syntax
> by watching the builder. What IS enforced is the round-trip that makes syncing possible
> later: the dialog refuses to save a filter it cannot faithfully represent, falling back
> to the text form instead of silently rewriting it. The remaining work is presentational,
> not semantic.

The filter bar is a **user-facing language** that lowers into the query engine's AST
(§3.2.4) — it is not itself the engine. Everything typed here (including the `t:`/`a:`/`b:`
shorthand for tags/attributes/blueprint slots) is builder-side sugar; the engine only ever
sees the fully-resolved nodes. Following the §3.1 field split, the language distinguishes:

- Tag values (L2): `t:remove == true`, `t:tier IN ("early", "mid")`, `t:weight > 5`
- Tag existence: `HAS t:notes`, `NOT HAS t:tier`
- Intrinsics (the entry itself): `id CONTAINS "granite"`, `mod == "quark"`
- Attributes (L1 dump data): `a:localization MATCHES ".*Brick.*"`
- Boolean logic: `AND`, `OR`, `NOT`, parenthetical grouping
- Registry type scoping: `minecraft:item WHERE ...`
- Case-insensitivity: `CONTAINS_I`, `MATCHES_I`, `MATCHES_TOKENS_I` (the `Cmp.ci` flag).
  A distinct operator rather than a `/i` suffix, because ids contain `/`
  (`minecraft:worldgen/biome`) and the tokenizer keeps them whole.
- String escaping: `\"` and `\` inside a quoted value.

**Extras the implementation added, kept deliberately.** These went beyond this section and
earned their place; recorded so they read as decisions rather than accidents:

- **Bare-word search** — `granite brick wall` with no operator lowers to a token match
  across the entry's id *and* its display name, so the most common gesture in the bar does
  the most useful thing (§5.3's candidate finder) and finds `quark:granite_bricks_wall`
  regardless of word order or plurals. `~` is its explicit spelling.
- **`@` template parameters** (`@slot`, `@b:base_block`) — §5.3 recommendation templates
  resolve per cell. Still ordinary tokens to the grammar, which is what keeps a template
  plain serializable data.
- **`AllSlots`** — a blueprint's columns are a fact about the schema, not a preference of
  the view, so a blueprint query projects them wholesale rather than freezing a list.
- **Caret-positioned syntax errors** — the bar points at the offending character.

Changing a filter updates the table live. If the user likes the result, they can save it
as a named view.

##### Creating Views

Three paths to the same result — all produce a named view config in the sidebar:

1. **Filter bar → save** (exploratory, bottom-up): open a blank registry table, play with
   filters, get a useful result, save it. The view already exists as a tab — saving just
   names it.

2. **New View wizard** (intentional, top-down): right-click in the Views sidebar panel →
   "New View." Minimal dialog: pick the renderer, then fill in that renderer's config
   (for the registry-table renderer: pick registry type, pick tag columns, optionally
   set an initial filter, name it). Opens as a tab for further refinement.

3. **Tag shortcut** (quick single-tag view): from the Tags sidebar panel, click a tag →
   "Create View for this tag." Pre-fills the wizard with the tag's registry type and that
   one editable column. One click, view created.

#### 3.2.4 The Query Engine

Views are saved queries. Filter bars are live queries. Blueprint slot suggestions
(§5.3) are queries. All three are the same operation — *select data from Layer 1 and
Layer 2, shape it into a table* — and they are all served by **one engine.** The query
engine is not a fourth L2 primitive; it is the **computational substrate** the primitives
(Views especially) are expressed in terms of. It is the single most load-bearing piece of
machinery in PackSmith, because so much of the app reduces to "run a query, render the
result."

This section specifies what a query *is*. It is deliberately abstract — no UI, no widgets,
no SQL. Those live above it (§3.2.3, §5.x) or below it (the executor). What lives here is
the model.

##### Founding Principles

1. **Headless in, headless out.** The engine takes a query, returns a table. It has no
   knowledge of the UI, ever. The UI is a translator on both ends: it lowers user gestures
   *into* a query, and maps a result table *onto* widgets. Swap the entire GUI and the
   engine is untouched.
2. **One engine, every use.** View construction, live filtering, and slot suggestion are
   not three features — they are three callers of one function. Live filtering is just
   *compose the View's base query with the filter-bar query*. There is no second code path.
3. **Downhill dependency.** The engine reads Layer 1 and Layer 2. It **never** reads
   Layer 3. Actions are the ones who call *it* — `pack.query(...)` is a built-in capability
   (§7.4) that hands an action the same engine the GUI uses. Authority flows down; the
   engine sits below actions and above storage.

Two meta-principles govern where complexity is allowed to live:

- **The AST holds relational operations; friendly idioms live in the builder.** The engine's
  vocabulary is small, orthogonal, and unforgiving. Everything approachable — shorthand,
  autocomplete, typo-tolerance, "did you mean" — is a *front-end* job done by the query
  builder, which lowers human gestures into the strict AST and teaches the language by
  *showing* the query it generated. Approachability is never paid for with engine complexity.
- **Rendering is renderer config, not part of the query.** A query returns a value *and its
  type*. Whether a boolean column shows as a checkbox or a `true`/`false` string is a
  decision the renderer makes from the type — it is not encoded in the query. The query says
  *what the data is*; the View config says *how to draw it*.

##### The Form: Query In, Table Out

Every query, without exception, returns a **table**:

```
Result = {
  columns: [(name, type), (name, type), ...],   # ordered
  rows:    [ {col_name: value, ...}, ... ],       # ordered
}
```

One shape for every use. A filter over the item registry, a "unique mods in this pack"
rollup, a cross-registry duplicate-name report — all of them come back as `columns + rows`.
This uniformity is what lets a single renderer stack sit on top of the whole engine.

Rows come in two flavors, and the difference is load-bearing:

- **Entry-backed rows** carry the identity of a real registry entry (its id). Because the
  engine knows *which entry* a row is, that row is **editable** — a View rendering it can
  offer tag cells that write back through the table delegate (§3.2, §5.1).
- **Computed / group rows** are the output of a projection or aggregation that no longer
  corresponds to a single entry (a `DISTINCT` over mods, a per-mod count). These rows are
  **read-only** — there is no entry to write back to. A View built on such a query is a
  report, not an editor.

Editability, then, is not a flag the user sets — it is a *consequence* of the query's shape.
Select entries, you get an editor; aggregate them, you get a report.

##### Why Not SQL (decision record)

The obvious shortcut is to let queries be raw SQL against the profile database. It was
seriously considered and **rejected.** The reasoning is preserved so it isn't re-litigated:

- **Storage mismatch.** Tags are user-defined and dynamic, stored EAV-style. Raw SQL over
  EAV means ugly self-joins and pivots for even simple multi-tag filters — the exact thing
  the builder is supposed to hide.
- **No round-trip.** The visual builder and the text query must stay in sync (§3.2.3). You
  can lower a builder gesture into SQL, but you cannot reliably lift arbitrary SQL back into
  the builder. The two-way binding dies.
- **Welds the language to physical storage.** A query that names raw columns breaks the
  moment a tag is renamed or the schema migrates. The query language must survive storage
  changes; SQL cannot.
- **Breaks the capability model.** Actions run queries through `pack.query` (§7.4). A
  Starlark action emitting SQL strings is a non-starter — it couples the sandboxed action
  layer to the database dialect.

The resolution: use the relational **model**, not the SQL **language**. A query is an
abstract relational expression (below). The **executor** that runs it is swappable. The v1
executor is a **pure-Python evaluator** over the packdump (L1, in memory) and bulk-loaded
tags (L2) — fast and simple at the ~2000-entry scale PackSmith works at. A SQLite-backed
executor remains a possible future swap *behind the same AST* if scale ever demands it. The
model is the contract; the executor is an implementation detail.

##### The AST

A query is **serializable data, not code.** This is a hard constraint, not an aspiration:
queries are written to the profile database (a saved View *is* a query), duplicated when a
View is forked, and exported when a View is shared. Every node is therefore a plain
dataclass that round-trips through JSON with zero code — no lambdas, no callables, no
embedded functions. All behavior (how `Mod` is computed, how an `Attribute` is looked up)
lives in the **executor**, keyed by node type — never inside the node.

The top-level shape:

```
Query(scope, filter, select, order_by?, limit?, distinct?)
```

- **`scope`** — the row source and field namespace: it answers *"what does one row
  fundamentally represent?"* Two kinds:
  - `Registry("minecraft:item")` — rows are the entries of a registry.
  - `Blueprint("StoneType")` — rows are the instances of a blueprint (fields become slots).

  **Why only these two.** Registry and Blueprint are PackSmith's only two *base relations* —
  the only things a row can *be*. A tag value is never a free-standing thing; it is always the
  triple `(entry, tag, value)`, i.e. a **column read off** an entry, not a row in its own
  right. So `Tag` (and `Attribute`, `Mod`) can never be a scope — they are things you *read
  from* a row, not things you can stand a query on. "Give me all `item_lore` values" is not a
  new scope; it is `Registry(...)` filtered to entries that *have* that tag, projecting its
  value. Scope picks the **noun** (item / instance); tags and attributes are **adjectives** you
  read; `Union`/aggregation reshape the result. Scope grows only if a genuine third base
  relation ever appears (querying the tag *vocabulary* — "all my enum tags" — would be one, but
  that is a schema/meta concern, not pack content, and is out of scope for this engine).
- **`filter`** — a boolean expression tree deciding which rows survive (below). Optional;
  absent means "all rows."
- **`select`** — the ordered list of fields to project into columns.
- **`order_by?`, `limit?`, `distinct?`** — sort keys, row cap, and row-level de-duplication.

**Fields** are where the §3.1 attribute split earns its keep. Every field reference is
exactly one of two kinds:

- **Intrinsic** — part of the entry itself, no lookup:
  - `Id` — the entry *is* its id. There is no "id field"; `Id` is the entry.
  - `Mod` — a derivation, the namespace computed from the id (`alexscaves:galena` →
    `alexscaves`).
- **Attached** — looked up from a source, named by a full-word node:
  - `Tag("remove")` — an L2 tag value.
  - `Attribute("localization")` — an L1 packdump-provided attribute (§3.1).
  - `Slot("base")` — a blueprint slot binding (blueprint-scoped queries).

> **The rule: intrinsic fields are the entry; attached fields are looked up from a source.**
> There is **no shorthand in the AST.** The `t:` / `a:` / `b:` prefixes a user types into a
> filter bar are *user-facing language only* — the builder lowers `t:tier` into `Tag("tier")`
> before the engine ever sees it. The engine deals exclusively in fully-resolved, full-word,
> unabbreviated nodes.

**Filters** are a small, orthogonal set:

- `Cmp(field, op, value, ci?)` — compare a field against a value. Ops: `eq`, `neq`, `gt`,
  `lt`, `gte`, `lte`, `in`, `not_in`, `contains`, `matches`. `matches` is the Python `re`
  dialect; `contains` and the string comparisons take an optional `ci` (case-insensitive)
  flag.
- `Has(field)` — the field is present at all (the tag is assigned, the attribute exists).
  Distinct from comparing its value — `Has(Tag("tier"))` is "has a tier," `Cmp(Tag("tier"),
  "eq", "end")` is "is end-tier."
- `And([...])`, `Or([...])`, `Not(expr)` — boolean composition.

Worked examples, trivial to spicy:

```python
# "every item tagged remove" — an editable entry list
Query(
    scope=Registry("minecraft:item"),
    filter=Cmp(Tag("remove"), "eq", True),
    select=[Id],
)

# "all Alex's Caves items, by display name"
Query(
    scope=Registry("minecraft:item"),
    filter=Cmp(Mod, "eq", "alexscaves"),
    select=[Id, Attribute("localization")],
    order_by=[Attribute("localization")],
)

# "the set of mods present in this pack" — a computed rollup, read-only
Query(
    scope=Registry("minecraft:item"),
    select=[Mod],
    distinct=True,
    order_by=[Mod],
)

# "anything with a tier tag whose id looks like an ore"
Query(
    scope=Registry("minecraft:item"),
    filter=And([
        Has(Tag("tier")),
        Cmp(Id, "matches", r".*_ore$"),
    ]),
    select=[Id, Tag("tier")],
)
```

##### The Power Ladder

The AST is designed so that power is **additive** — later capabilities extend the vocabulary
without changing the form (still query in, table out) or the model (still relational).

**v1 (what gets built first):** single-scope filter / project / sort / limit / distinct over
registry entries × attributes × tags. This alone covers the overwhelming majority of real
Views ("show me X where Y") and the rollup reports.

**Later, additive, still relational:**

- **Navigational paths** — `Deref(refField, field)`: follow a reference and read the
  target's field (a spawn egg → the localized name of the mob it spawns).
- **Condition joins** — `sources=[Source("a", ...), Source("b", ...)]` + a `join` condition,
  fields qualified by `src=`. Plus `Norm(...)` (case-fold + strip) and the `Id(src=a) < Id(src=b)`
  idiom the builder surfaces as a "unique pairs" toggle. This is the cross-mod duplicate-name
  finder — and the one feature that most tempts a SQLite backend.
- **Union** — `Union([query, query, ...], distinct?)`: combine the rows of several queries
  into one result, branches aligned by column name (`.as_("text")`). This is *row-level* fan-out
  — one entry can contribute several output rows (e.g. "every `item_lore` OR `hotbarDescription`
  value containing 'diamond'" — an entry with both matching emits two rows). Distinct from
  `Coalesce`, which is *column-level*: `Coalesce([...]).as_("name")` draws one column from several
  source fields within a single row. Union merges rows; Coalesce merges fields.
- **Aggregation / grouping** — counts, distributions ("entries per mod per registry").

##### The Ceiling

There is a deliberate wall. **Recursion is not a query.** Detecting a circular dependency
chain in a quest graph, or any traversal whose depth is data-dependent, cannot be expressed
in the relational AST — and it is *intentionally* not made to. That work is a **read-only
action** (the §5.3 escape hatch): the action calls `pack.query(...)` to get the flat edge
list, then runs the graph algorithm in ordinary code. The engine supplies primitives; the
action supplies the algorithm.

This is the same line §5.3 draws between **declarative and procedural**. Stress-testing the
AST against real reporting cases found the ceiling landing *exactly* on that line — which is
the sign the two decisions are consistent, not accidental. The filter bar stays loudly dumb;
the engine is powerful but bounded; genuinely procedural analysis escapes to a read-only
action. Three tiers, one seam each.

##### The Field Catalog (implementation note)

For a given scope, the executor must resolve a field reference (`Tag("remove")`, `Mod`,
`Attribute("localization")`) to *how to compute it for each row*. That mapping — per scope,
`name → (kind, resolver)` — is the **field catalog.** It is the concrete bridge between the
abstract AST and the physical data: `Id` resolves to the entry id, `Mod` to a namespace
split, `Attribute(x)` to a packdump lookup, `Tag(x)` to a tag-store lookup.

The catalog is **per registry**, which the storage now supports directly: tag definitions
are registry-scoped (composite `(registry_type, name)` key, design 3.2.1), so the catalog
answers "which tags exist for `minecraft:item`?" with a single `definitions_for(registry_type)`
call. The `Attribute` resolver likewise reads L1 dump attributes via `attribute(registry_type,
entry_id, name)` — today just `localization`.

#### Live Questions

##### Blueprint Instance Cycles — RESOLVED: reject at bind time

Schema-level cycles remain explicitly allowed (recursive `CladeNode` is a legitimate
pattern and is unaffected). **Instance-level cycles are refused when the binding is made**,
with the offending path named: `StoneType:granite → Village:canyon → StoneType:granite`.

Chosen over the two alternatives (depth-limited traversal, or leaving it to consuming code)
because of *when* the question gets asked. Nothing dereferences a reference today — `Deref`
is up the §3.2.4 power ladder and §5.2's node view is unbuilt — so refusing at the edge is
cheap now and buys a permanent invariant: **every future traversal may assume termination**
rather than carrying a visited-set and a depth limit forever. The cost is that a genuinely
cyclic instance graph becomes unrepresentable, which no real modelling need has yet asked
for. A `cycles()` query also exists, to report any that predate the rule.

##### Blueprint Binding Orphan Detection — RESOLVED: mirror tag orphans

Taking this section's own steer ("this should probably mirror the tag orphan-detection
operation so the two primitives stay symmetric"), a binding whose target has left the
packdump is **derived, never stored** — computed on demand exactly like `find_orphans` on
tags, so it cannot go stale — and it is **surfaced, not enforced**: it appears in the Errors
panel as a warning and locks nothing.

That last part is the asymmetry worth being explicit about, because this design has two
different things called "orphan":

| | orphaned **instance** | orphaned **binding** |
|-------------|-------------------------------------|--------------------------------|
| caused by   | a destructive schema edit — the user's own act | the packdump changing underneath |
| stored?     | yes, with the mutation that caused it | no, derived on demand |
| consequence | locked out of actions until resolved | surfaced; nothing is locked |

The user must resolve the first because they caused it and only they know what they meant.
Nobody decided the second, so demanding a decision would be punishing them for a mod update.
Auto-clearing was rejected for the same reason it is rejected for tags: the binding is the
record of an intent, and a temporarily-absent entry (a mod disabled for one test launch) is
not a reason to destroy it.

##### Is Auto-Population Even Required?

This question used to read "Blueprint Auto-Population Strategy" and assumed the answer
was yes — the only open part being *how*: string-similarity matching, user-trained
patterns, or blueprint-level regex hints. **The premise is what turned out to be
questionable**, and it was written before recommendation templates (§5.3) and the
candidate picker existed. Both were built for a different reason and between them they
already are the "naming conventions and registry search" engine this asked for.

Measured against a real schema (6 instances × 10 slots, 33 unfilled registry slots), with
the template `@b:base_block @group @leaf`:

| outcome | count | what a bulk pass could do |
|--------------------|-------|-------------------------------------------|
| exactly one match  | 6     | propose it |
| several matches    | 2     | nothing — a human has to choose |
| no match           | 25    | nothing — the content doesn't exist |

So auto-population would decide **6 of 33**, and those six are precisely the cheapest
cells to fill by hand: with a template that narrows to one candidate, the picker is open,
one item, Enter. The other 27 need a person either way.

**The "no match" result is not a miss — it is usually the correct answer**, and this is
the finding that reframes the feature. Checking the 25 empties: they are dominated by
`chiseled.stairs`, `chiseled.slab`, `chiseled.wall` — variants Minecraft does not have.
Every looser candidate the matcher could offer (`create:cut_andesite_stairs` for a
*chiseled* stairs slot) is confidently wrong. That is this section's own opening
restated: "the coverage is completely arbitrary."

The consequence is that the original worry — inconsistent mod naming — is not the
blocker. Token matching (order-independent, plural-normalised, namespace-stripped)
handles naming. What remains is **semantic**, and no string matcher will ever fix it.

**Current answer: not required for v1.** The costs are asymmetric — an empty cell costs
nothing, while a wrong binding is silently corrupt data that goes on to drive recipe
generation — so any such system must propose rather than fill, which means a review
surface, an ownership decision (user-owned edit vs. action-owned subject to conflict
policy), and a new UI mode. That is a large amount of machinery to automate the easy 18%.

**What would change the answer** is not "we have a lot of gaps" but a measured
observation: *visiting cells that turn out to have no candidate at all is where the time
goes.* If that materialises, the cheap fix is not a proposals system — it is a **candidate
count annotation** on the grid, so a cell with zero candidates never needs visiting. That
is a query, and §5.3 already establishes that reporting is the query engine's job.

Worth noting when re-reading this: at the time of writing, the 300-mod pack this design
exists for had **zero blueprints defined**. The tedium described above was a prediction,
not an observation.

##### Query Language Specification

**The engine model is now specified in §3.2.4** (the AST, the table form, the power ladder,
the ceiling) — which answers the "how powerful is the query engine" reframing §5.3 raised.
What remains open is narrower, and splits in two:

- **The surface language** (the filter-bar text, not the AST): operator precedence, the
  regex dialect exposed to users, edge cases (e.g., `IN` on a bool tag), and error messages
  for malformed input. This is a builder/parser concern — a grammar that lowers into the
  §3.2.4 AST — not an engine concern.

(The registry-scoping prerequisite that used to sit here is **resolved**: tag definitions are
now registry-scoped in storage, design 3.2.1, so the §3.2.4 field catalog rests on real
per-registry definitions.)
