## 6. Files, Ownership, and Editing

This section covers everything about how Packsmith deals with the modpack instance's
actual files on disk: how the user finds them (File Browser), how ownership is tracked
across files and across keys within structured files (File Ownership System), and how
the user inspects and edits them (Text Editor, NBT Editor, JAR Viewer).

"The instance" is the default place rather than the only one — §6.6 lets the user track
further roots, which is what makes generating a glue mod's assets possible at all, since a
Gradle project is never going to live inside the instance. Everything below applies to a
tracked root unchanged: ownership, staging, dry run and rollback were never rooted in the
path.

### The Throughline: Ownership

Every file Packsmith touches has an ownership state — untouched, user-owned, or
action-owned (§6.1). For structured files, ownership is tracked at the key level: a
single `quark-common.toml` can have five different keys owned by five different actions
and the rest owned by the user. The editors surface this ownership visually so the user
always knows who wrote what before they start editing, and they route edit attempts
through the ownership-transfer flow when the user tries to override a non-user owner.

File ownership *looks* like the Layer 2 ownership models in §3.2.1 (tag assignments) and
§3.2.2 (blueprint bindings) — all three answer the same surface question, "who owns this
piece of state, and what happens when someone else tries to write to it?" — but the
resemblance is only skin-deep. They are **two different engines for two different worlds,
and must not be unified.** Layer 2 data lives in Packsmith's own database, where Packsmith
is the *sole* writer; conflicts are therefore clean two-party affairs (user vs. action)
that a declared policy can resolve (§3.3). Files live on disk, where an *uncontrolled
external world* also writes them — the game rewrites `options.txt`, mod updates rewrite
configs, the user edits in another tool — so file ownership can never trust that its state
is what it last saw, and stays conservative: hard-block user-owned targets, detect drift
via existence-checks (§6.1), surface loudly always. Same vocabulary at the surface
(user/action states, loud transfers); deliberately different machinery beneath.

### The Principle: Editors Are Generic

Packsmith ships a small number of **editors**, each targeting a broad file category:

| Editor         | Target files                                                                              |
|----------------|-------------------------------------------------------------------------------------------|
| Text Editor    | `.js`, `.json`, `.toml`, `.yaml`, `.ini`, `.cfg`, `.star`, `.txt`, `.zs`, anything textual |
| NBT Editor     | `.dat`, `.nbt`, and other binary NBT                                                      |
| JAR Viewer     | `.jar`, `.zip` archives                                                                   |

Mod-specific behavior — KubeJS autocomplete from the packdump registry, Patchouli book
page previews, Paxi-aware override resolution — **does not live in the editors**. It
lives in the Integrations layer (§7), which registers language services, decorators,
context-menu actions, and override-target resolvers into the generic editors.

This keeps the editor count small (one editor per file category, not one per mod) and
the integration pattern composable (every integration plugs into the same editor APIs).
A future Patchouli integration doesn't need a new editor; it registers a completion
provider and a hover handler into the Text Editor for files under `patchouli_books/`.
KubeJS does the same for `kubejs/**/*.js`. The editor handles the baseline; the
integration adds the mod-specific intelligence.

### Editor Dispatch

When the user opens a file (double-click in File Browser, follow a cross-reference,
extract-and-open from the JAR Viewer), Packsmith picks the editor by file extension and
content sniffing:

- Known text extensions → Text Editor
- Known NBT extensions → NBT Editor
- Known archive extensions → JAR Viewer
- Unknown/binary → JAR Viewer opens it as a hex dump (or a "cannot display" placeholder
  for formats the system doesn't recognize)

Multiple editors can be open simultaneously — they're all tabs in the main workspace
(§4.2 Tab Architecture), peer to the View tabs from §5.
