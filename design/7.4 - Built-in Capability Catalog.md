### 7.4 Built-in Capability Catalog

**PLACEHOLDER** — this section is a sketch, not a spec. The full catalog of built-in
capabilities (exact method signatures, return types, error modes, examples) will be
written after the core API settles through implementation. For now, the intent is to
enumerate what's built-in so the mental model is complete.

Everything below is "always satisfied" in every profile — these capabilities are
provided by the built-in Packsmith runtime, not by integrations. Actions can use them
unconditionally.

#### Logging

- **`log`** — `pack.log(level, message)`, plus probable convenience variants for
  structured per-phase logging (`pack.log_section(name)`, `pack.log_result(...)`).
  Output flows into the Logs bottom panel tab while the job runs, and is kept with the
  run in its Run Report tab's Log section (§4.1).

#### Layer 1 (Game Data) Reads

- **`registry.read`** — enumerate registries and their entries, and read an entry's
  attributes. `pack.registry.entries(registry_type)`, `pack.registry.has(id)`,
  `pack.registry.attribute(id, name)`. See §3.1 for the entry / attribute / derivation
  split: an entry *is* its id; attributes (like localization) are attached, dump-provided
  data; derivations (like the mod namespace) are computed from the id.
- **`registry.localized_name`** — convenience for the `localization` attribute, with
  fallback to the raw id.

All of Layer 1 is read-only (§3.1), so there are no `registry.write` capabilities.

#### Layer 2 (User Data)

**Tags:**

- **`tags.read`** — query tag definitions, assignments, by registry type and tag
  name.
- **`tags.write`** — set/clear assignments. Subject to §3.2.1's ownership
  lifecycle and conflict policies.

**Blueprints:**

- **`blueprints.read`** — query blueprint schemas, instances, bindings.
- **`blueprints.write`** — create instances, write bindings. Subject to §3.2.2's
  ownership and conflict-policy rules.

**Views:**

- **`views.read`** — enumerate saved views, read their configs (action runs
  queries through view config for reporting/automation).
- Writing views is user-only (§3.2.3); no `views.write` capability exists.

Tag and blueprint definitions (the schema, not data) are user-only; no
`tags.define` or `blueprints.define_schema` capabilities. Actions work within
the user's vocabulary, they don't modify the vocabulary.

##### Every Read Is Staged-First (2026-08-15)

An action sees **its own uncommitted writes**. Writes accumulate in the step's staging
buffer (§1.1) and every read on `pack` — a tag value, a tag *query*, a slot binding,
`blueprints.gaps`, a file's contents, a file's existence, any of their ownerships — checks
that buffer before the store. So `write` then `read` returns what you wrote, within the
step, before anything has been committed.

Stated here because the one read that did **not** do this was invisible: `tags.query` went
to the committed store, so an action could set `remove = true` on an entry and then fail to
find it in the very next query. Nothing errored; the entry was simply absent, and the
action skipped work it believed it had queued.

Two consequences worth knowing when authoring:

- The rule is uniform. There is no read for which "but this one sees the real state" is
  true, and an action should never be written to work around one.
- It is what makes a multi-step dry run faithful (§3.3): step 2 reads step 1's *staged*
  writes exactly as it would read step 1's *committed* ones, and cannot tell the
  difference.

#### Filesystem (Arbitrary, Scoped)

- **`filesystem.read`** — read any file within `<instance_root>` via
  `pack.filesystem.resolve(path).read_all()` / `read_key(...)`. Escaping the instance
  root errors.
- **`filesystem.write`** — write any file within `<instance_root>`. Same scoping.
  Used for edge-case files that don't fit a more specific capability (EMI's
  `/emi.json` at root, default-config copies, etc.).

Provider-routed resolvers (`datapacks`, `resourcepacks`, `kubejs`) use `filesystem`
under the hood after resolution, but those are separate capabilities with their own
ergonomic routing. Authors should prefer the narrow capabilities when applicable;
`filesystem` is the escape hatch.

There is no dedicated `config` capability. Mod config files are just files under the
instance root — read/written through `filesystem.*` with the author pointing at the
right path (a library package can encapsulate a mod's path if it's worth sharing). A
built-in `mod → config path` registry was considered and rejected: mod config
locations are too inconsistent (EMI's `emi.json` at the pack root being the classic
counterexample) for such a registry to be anything but perpetually incomplete.

Worth recording that `emi.json` is **not** a lone eccentric. A real 246-mod 1.20.1 pack
keeps five mod configs at the instance root — `emi.json`, `foolproof.json`,
`patchouli_data.json`, `user-prefs.json`, `rhino.local.properties` — alongside 701 files
under `config/` in 37 subdirectories and ten formats (json, toml, dat, mcmeta, txt, json5,
properties, ini, yaml, png). Root-level config is a pattern, not an exception, and the tail
is long enough that the rejected registry would have been wrong about the interesting
cases specifically.

##### What Did I Write Last Time? (2026-08-18)

An action whose output is a *projection* of Layer 2 — a pack that must match a tag — has to
clear what the tag no longer says, or it is additive-only: untag everything from one mod and
its old entries keep applying because nothing rewrote that file.

The tempting answer is per-step scratch state the action writes for itself. **Rejected.** It
would make an action's output a function of its own history rather than of `(L1, L2,
bindings, config)` — the same hazard this section refuses a clock and randomness for, since
two identical packs would then produce different files depending on what ran before. It also
needs a fourth staging engine to keep §3.3's dry-run guarantee, for bookkeeping nobody reads.

Packsmith already knows the answer: `file_ownership` stamps every action write with its
`package:action_id`. So it is a **read, not a store** — `pack.datapacks.owned(pack)` and
`pack.resourcepacks.owned(pack)` return the paths this action owns inside one pack.
Derived, never remembered, for the reason §3.2.1 gives for orphans and stale bindings: a
record kept beside the truth goes stale, and a derived one cannot.

**Why it takes a pack rather than listing everything.** Ownership is per ACTION and cannot
be otherwise — `FileStaging.write` decides whether a write is a takeover by comparing
`owner_action_ref`, so two steps of one action must look like one owner or each would
permanently steal from the other. An unscoped listing would therefore hand a step every file
the same action wrote in *other* steps, and an action clearing "everything I own that I did
not write this run" would blank a sibling step's output, silently. The pack is what tells
those steps apart, so it is a required argument rather than a filter the author is trusted
to remember.

Two steps of one action bound to the *same* pack are still indistinguishable, and no naming
fixes that — it is the file-world twin of two mappings binding one blueprint with different
policies, which §3.3 refuses at declaration time. The eventual answer is §7.2's install-time
claim-conflict detection applied to steps, not a parameter.

#### Where A Mod's Config Actually Lives

The path question above is the *smaller* of the two, and this section previously said
nothing about the larger one: for a minority of mods, **"the config for mod X" is not one
file.** Forge (and NeoForge) split configs by scope, and only one of the three is what most
people mean:

| Location | What it is | Lifecycle |
|---|---|---|
| `config/<mod>-common.toml`, `-client.toml` | instance-global | read at startup; the source of truth for the overwhelming majority of mods |
| `defaultconfigs/<mod>-server.toml` | a **template** | copied into a world's `serverconfig/` **only when a new world is created** |
| `saves/<world>/serverconfig/<mod>-server.toml` | the live per-world value | affects that world alone |

**Scale it correctly: this affects roughly 5% of mods.** In the same 246-mod pack, 14
distinct `*-server.toml` files appear across four worlds — 5.7%. It is emphatically *not*
how Forge configs generally work, and treating it as the common case would misdescribe the
other 94%. But the 14 include Create, JEI, Curios and InControl, so it is a small slice
made of exactly the mods a pack developer tunes: **low frequency, high consequence.**

Both wrong answers fail *silently*, which is what makes this worth writing down:

- Edit `defaultconfigs/` and an existing test world does not change — it looks like nothing
  happened.
- Edit a world's `serverconfig/` and it works today and is gone the moment a new world is
  made. That is the one that reaches players, because players always start a new world.

`defaultconfigs/` also **starts empty and stays empty until a human fills it.** Nothing
generates it. The actual workflow is: create a world, let Forge write
`<world>/serverconfig/<mod>-server.toml`, then copy that file into `defaultconfigs/` by
hand. It is pure clerical work, and it is invisible when forgotten.

None of this changes the ruling. Every one of these paths still goes through
`pack.filesystem.resolve(...)`, because each fails the test that made a datapack slottable
(§3.3): **the user neither owns nor names them.** Mods name their config files and Forge
names the directories — unlike `tweaks`, which the user named. A `pack.config` scope
resolver was considered on the strength of the three-scope split and rejected once the 5%
figure was measured: a whole namespace is not warranted, and
`pack.filesystem.resolve("defaultconfigs/create-server.toml")` already says exactly what it
means.

##### Live Question: `defaultconfigs` Drift

The valuable thing here is probably not a copy command but a **diagnostic**: *"`create-server.toml`
in world 'Badlands' differs from `defaultconfigs/`."* That catches the settings you tuned
in your test world and never promoted — a §5.3-style recommendation rather than a new
capability, and cheap because both files are already on disk. The copy is trivial; knowing
you owed it is the hard part. Not scoped, not committed.

##### Note: Nothing Currently Stops An Action Writing Into `saves/`

`filesystem` enforces exactly one boundary — the instance root — and `saves/` is inside it.
So an action can already write into a live world today: `serverconfig`, `level.dat`, region
files. That is a pre-existing property rather than something the config discussion
introduces, and per-world config editing is a legitimate thing to want. But §6.1's
ownership model has never said anything about world directories, so the permission is
currently granted by omission rather than by decision. Flagged, not resolved.

#### Capability Introspection

- **`capabilities.has(name)`** — `bool`: is this capability provided in the current
  profile?
- **`capabilities.version(name)`** — `int` or `None`: version of the active provider
  for this capability.

Used when an action declares a capability as optional (§7.2) and wants to branch on
whether to use it:

```python
if pack.capabilities.has("kubejs.script_write"):
    pack.kubejs.resolve(phase="server", name="packsmith_hook").write(js_source)
else:
    pack.log("info", "KubeJS not installed; skipping script hook")
```

#### Error Handling

- **`fail(reason)`** — halt the action step. Mandatory API per §3.3's
  "no exceptions" constraint (Starlark lacks `try/except`). All transactional stages
  discard; the reason is logged and surfaced to the user.

#### Notable Non-Capabilities

Things **not** exposed as capabilities, intentionally:

- **No process execution.** No `subprocess`, no shell, no `os.system`.
- **No network.** No HTTP, no socket, no DNS. Starlark's hermetic design.
- **No clock/randomness beyond deterministic Starlark.** Actions are supposed to be
  deterministic given their inputs; adding `time.now()` or `random.choice()` would
  make dry-run convergence (§3.3) inconsistent with the committed run. If a use case
  for nondeterminism emerges, it'll get a specific capability with clear semantics.

  **The host has to hold up its own end of this**, which is less obvious than banning a
  clock. A query with no `ORDER BY` is nondeterministic in exactly the same way — an
  action that iterates its results and stops after N, or writes numbered output, produces
  different files on different runs — and the action author has no way to know or fix it.
  So results handed to an action are ordered, and that is part of this rule rather than an
  implementation detail of the store.
- **No direct Python interop.** The runtime injects the `pack` object; actions can't
  reach into the host Python runtime.
- **No dynamic loading.** Starlark's `load(...)` is restricted to the package
  dependency graph; arbitrary paths error.

This list will grow as the catalog fills in; what's here is the bare minimum mental
model of "what can an action do" for the API spec to feel grounded.
