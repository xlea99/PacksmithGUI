### 7.4 Built-in Capability Catalog

**PLACEHOLDER** — this section is a sketch, not a spec. The full catalog of built-in
capabilities (exact method signatures, return types, error modes, examples) will be
written after the core API settles through implementation. For now, the intent is to
enumerate what's built-in so the mental model is complete.

Everything below is "always satisfied" in every profile — these capabilities are
provided by the built-in PackSmith runtime, not by integrations. Actions can use them
unconditionally.

#### Logging

- **`log`** — `pack.log(level, message)`, plus probable convenience variants for
  structured per-phase logging (`pack.log_section(name)`, `pack.log_result(...)`).
  Output flows into the Job Results / Logs bottom panel tabs (§4.1).

#### Layer 1 (Game Data) Reads

- **`registry.read`** — query registries for entries, IDs, properties.
  `pack.registry.entries(registry_type)`, `pack.registry.has(id)`,
  `pack.registry.properties(id)`.
- **`registry.localized_name`** — fetch display name for a registry entry via the
  localization layer.

All of Layer 1 is read-only (§3.1), so there are no `registry.write` capabilities.

#### Layer 2 (User Data)

**Tags:**

- **`l2.tags.read`** — query tag definitions, assignments, by registry type and tag
  name.
- **`l2.tags.write`** — set/clear assignments. Subject to §3.2.1's ownership
  lifecycle and conflict policies.

**Blueprints:**

- **`l2.blueprints.read`** — query blueprint schemas, instances, bindings.
- **`l2.blueprints.write`** — create instances, write bindings. Subject to §3.2.2's
  ownership and conflict-policy rules.

**Views:**

- **`l2.views.read`** — enumerate saved views, read their configs (action runs
  queries through view config for reporting/automation).
- Writing views is user-only (§3.2.3); no `l2.views.write` capability exists.

Tag and blueprint definitions (the schema, not data) are user-only; no
`l2.tags.define` or `l2.blueprints.define_schema` capabilities. Actions work within
the user's vocabulary, they don't modify the vocabulary.

#### Filesystem (Arbitrary, Scoped)

- **`filesystem.read`** — read any file within `<instance_root>` via
  `pack.filesystem.resolve(path).read_all()` / `read_key(...)`. Escaping the instance
  root errors.
- **`filesystem.write`** — write any file within `<instance_root>`. Same scoping.
  Used for edge-case files that don't fit a more specific capability (EMI's
  `/emi.json` at root, default-config copies, etc.).

Provider-routed resolvers (`datapacks`, `resourcepacks`, `kubejs`) use `filesystem`
under the hood after resolution, but those are separate capabilities with their own
ergonomic routing. Authors should prefer the narrow capabilities when applicable;
`filesystem` is the escape hatch.

#### Config (Built-in Mod Config Targets)

- **`config.read`** — read mod config files known to PackSmith's built-in target
  registry via `pack.config.resolve(mod, variant).read_all()` /
  `read_key(...)`.
- **`config.write`** — write to the same. Target registry is extensible by
  integrations.

For configs not in the registry, drop to `filesystem.*`. The config namespace is
for the ergonomic common case (the author doesn't have to know that Quark's common
config is at `<instance>/config/quark-common.toml` — they say
`pack.config.resolve(mod="quark", variant="common")` and PackSmith resolves).

#### Capability Introspection

- **`capabilities.has(name)`** — `bool`: is this capability provided in the current
  profile?
- **`capabilities.version(name)`** — `int` or `None`: version of the active provider
  for this capability.

Used when an action declares a capability as optional (§7.2) and wants to branch on
whether to use it:

```python
if pack.capabilities.has("kubejs.script_write"):
    pack.kubejs.resolve(phase="server", name="packsmith_hook").write(js_source)
else:
    pack.log("info", "KubeJS not installed; skipping script hook")
```

#### Error Handling

- **`fail(reason)`** — halt the action step. Mandatory API per §3.3's
  "no exceptions" constraint (Starlark lacks `try/except`). All transactional stages
  discard; the reason is logged and surfaced to the user.

#### Notable Non-Capabilities

Things **not** exposed as capabilities, intentionally:

- **No process execution.** No `subprocess`, no shell, no `os.system`.
- **No network.** No HTTP, no socket, no DNS. Starlark's hermetic design.
- **No clock/randomness beyond deterministic Starlark.** Actions are supposed to be
  deterministic given their inputs; adding `time.now()` or `random.choice()` would
  make dry-run convergence (§3.3) inconsistent with the committed run. If a use case
  for nondeterminism emerges, it'll get a specific capability with clear semantics.
- **No direct Python interop.** The runtime injects the `pack` object; actions can't
  reach into the host Python runtime.
- **No dynamic loading.** Starlark's `load(...)` is restricted to the package
  dependency graph; arbitrary paths error.

This list will grow as the catalog fills in; what's here is the bare minimum mental
model of "what can an action do" for the API spec to feel grounded.
