### 7.1 Capabilities and Providers

**Capability** = a named interface. The named ability an action can request.
`datapacks.write`, `datapacks.read`, `resourcepacks.write`, `kubejs.script_write`,
`l2.tags.read`, `log`, `registry.read`, `filesystem.write`, and so on. This is what
actions declare they need and what the `pack.*` API exposes as callable surfaces.

**Provider** = an implementation of a capability. The concrete thing that satisfies
the interface in a given profile. The built-in PackSmith runtime is a provider of
many capabilities (`log`, `registry.read`, `l2.tags.*`, `filesystem.*`). The Paxi
integration is a provider of `datapacks.write`, `datapacks.read`,
`resourcepacks.write`, `resourcepacks.read`, and Paxi-specific extras like
`datapacks.ordering`. OpenLoader provides the same basic set minus the ordering
capability. Different profiles have different provider sets.

The split is load-bearing: **capability is the interface actions depend on; provider
is the implementation that answers.** Actions don't know or care which provider is
active. A tag-removal action using `pack.datapacks.write(...)` works identically
whether Paxi or OpenLoader is providing `datapacks.write` under the hood.

#### The Resolution Table

At profile load, PackSmith inspects:

- The built-in set of capabilities the runtime provides
- The set of active integrations (§8) and the capabilities they register as
  providers

And produces a **capability resolution table** for the profile — essentially a map
from capability name to the provider currently satisfying it:

| Capability              | Provider         |
|-------------------------|------------------|
| `log`                   | built-in         |
| `registry.read`         | built-in         |
| `l2.tags.read`          | built-in         |
| `l2.tags.write`         | built-in         |
| `filesystem.read`       | built-in         |
| `filesystem.write`      | built-in         |
| `datapacks.read`        | Paxi (§8.1)      |
| `datapacks.write`       | Paxi (§8.1)      |
| `datapacks.ordering`    | Paxi (§8.1)      |
| `resourcepacks.read`    | Paxi (§8.1)      |
| `resourcepacks.write`   | Paxi (§8.1)      |
| `resourcepacks.ordering`| Paxi (§8.1)      |
| `kubejs.script_write`   | KubeJS (§8.2)    |
| ...                     | ...              |

Capabilities with no active provider are simply absent from the table.

#### Satisfaction Check

When an action is loaded (at profile load or when installed), PackSmith computes its
required capability set (§7.2) and cross-references the profile's resolution table.
Three possible outcomes per required capability:

- **Satisfied** — a provider is active. No issue.
- **Unsatisfied, required** — no provider for this capability; the action is marked
  **unavailable** in the current profile. It appears in the Actions panel with a
  warning indicator; any job step referencing it refuses to run; the step editor
  surfaces a hint pointing at the integration (or built-in update) needed.
- **Unsatisfied, optional** — no provider, but the action declared this capability as
  optional (§7.2). The action still runs; the code is expected to handle the
  capability's absence gracefully.

The satisfaction check runs at profile load and every time the provider set changes
(new integration installed, new mod detected, etc.).

#### Dotted Naming

Capabilities use dot-notation names that mirror the API namespace:
`datapacks.write`, `datapacks.ordering`, `l2.tags.read`, `kubejs.script_write`.
Sub-capabilities nest under their parent: `datapacks.ordering` lives under the
`datapacks` tree as a finer-grained capability that only some datapack providers
satisfy.

This has two benefits:

1. **Names mirror the API.** An action calling `pack.datapacks.ordering.set_priority(...)`
   requires the `datapacks.ordering` capability — the name is derivable from the code.
2. **Hierarchy matches semantics.** A user scanning an action's required capabilities
   sees "uses four `datapacks.*` capabilities" as one semantic cluster instead of
   four seemingly-unrelated strings.

#### Sub-Capabilities as Optional Provider Extensions

A provider can supply some sub-capabilities of a namespace without supplying all of
them. The Global Data Packs mod provides `datapacks.read` and `datapacks.write` but
no ordering capability and no resourcepacks capabilities at all. OpenLoader provides
datapacks and resourcepacks but no ordering. Paxi provides all of them.

An action only calling `pack.datapacks.write(...)` requires just `datapacks.write` —
runs on any of the three. An action calling `pack.datapacks.ordering.set_priority(...)`
requires `datapacks.ordering` and is therefore Paxi-specific.

The user's profile resolution table tells them at a glance which providers exist,
which capabilities are satisfied, and which are missing.

#### Multi-Provider Disambiguation

When two providers satisfy the same capability (the user has both Paxi and OpenLoader
installed), PackSmith picks one as the default for the profile and offers the choice
in relevant UI surfaces (e.g., the JAR Viewer's save-as-override prompt in §6.5).
Sticky per profile. See §8.1 for the details of loader disambiguation.

For capabilities that come from exactly one expected provider (e.g., `kubejs.*` only
from the KubeJS integration), there is no disambiguation — one provider, or none.

#### Capability Versioning

Capabilities carry a version. An action's declaration of a capability requirement can
specify a minimum version:

```toml
[[actions.requires]]
capability = "datapacks.write"
min_version = 2
```

If the active provider implements an older version, the satisfaction check fails the
same way as "no provider" does. This lets capability interfaces evolve without
breaking old actions silently.

Cheap future-proofing — we probably never bump a version in MVP, but declaring the
versioning model up-front is worth it.
