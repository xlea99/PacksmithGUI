### 6.1 File Ownership System

> **MVP note (§1.1).** The MVP implements **whole-file ownership only** (the three states
> below, claimed via `handle.write`). Per-key ownership for structured configs, the
> comment-preserving round-trip parsers it requires, and the blob-store file versioning
> are all deferred — they are the heaviest engineering in this section and aren't needed
> to prove the core loop. See §1.1.

Every file in the modpack instance that Packsmith interacts with has exactly one of three
ownership states:

| State | Meaning | Constraints |
|---|---|---|
| **Untouched** | Neither user nor action has modified this file through Packsmith. It's the mod's default, vanilla, or whatever shipped with it. | Anyone can claim it. |
| **User-owned** | The user has edited this file (either manually in the Text Editor or through an explicit claim). | Actions are **blocked** from touching it. If an action wants this file, the user must explicitly release ownership. |
| **Action-owned** | An action created or claimed this file. | The user is **locked out** of editing until they explicitly take ownership. Taking it transfers the file to them and blocks the action until they release it back. |

Ownership transfers are **explicit, visible, and loud.** Never silent overwrites. The user
always knows who owns what, and conflicts are prevented rather than resolved.

Note the symmetry: the block runs **both** ways. An action writing a user-owned file fails
loudly, and a user editing an action-owned file is locked out until they take it. An earlier
draft of the table above said the user was merely *warned* — that contradicted this section's
own philosophy and was fixed. A warning is worse than a lock for a specific reason: the
warning fires when you edit, but the consequence (the action's next run failing) arrives days
later, so the user cannot connect them and goes digging. A lock puts cause and effect in the
same moment, and the prompt itself teaches the model. Same argument as `unsafe` in Rust — the
dangerous thing stays possible, but you have to name it.

#### The Rust Philosophy

This is deliberately strict. The permissive approach ("actions and users can both freely
edit anything") sounds flexible but creates invisible chaos — an action silently overwrites
a manual edit, or a manual edit silently invalidates something that's SPOG'd on
a view somewhere. The strict model is annoying for five minutes while you get used to it.
The permissive model is terrifying permanently because you can never trust that your files
are in the state you think they are.

#### Action Ownership Declaration

Actions **explicitly declare** which files (or keys — see below) they intend to own. This
enables Packsmith to show the full picture *before anything runs*:

- "This action will create/modify these 47 files"
- "3 of these are currently user-owned — release them or the action will skip them"
- "These 12 are already owned by a different action — here's the conflict"

For any file in the browser, Packsmith can show not just who owns it *now* but who *will*
touch it on the next run. "This file is managed by `removal_suite:nuke`. Last generated 3
days ago. Will be regenerated on next run." Full provenance, full predictability.

The **kind** of ownership an action claims on each file — whole-file vs per-key — is
determined by which API method the action calls, not by a separate manifest field.
Calling `handle.write(content)` on a file handle claims whole-file ownership;
calling `handle.write_key(key, value)` claims per-key ownership of that specific key.
The method name IS the claim. See §7.3 for the full capability API surface and §7.2
for how Packsmith infers an action's full ownership claim set from static analysis.

#### Whole-File Means Byte-For-Byte (2026-08-15)

Whole-file ownership makes an implicit promise this section never stated: a file an action
reads, changes one thing in, and writes back comes out **as it went in, plus that change**.
Per-key ownership has round-trip parsers to keep comments and formatting; whole-file has
nothing but the discipline of not touching what it was not asked to touch.

Python's default text mode quietly breaks it. `newline=None` translates in *both*
directions — `\n` becomes the platform separator on write, every ending becomes `\n` on
read — with two consequences on Windows:

- **It corrupts.** Writing `"a\r\nb"` puts `a\r\r\nb` on disk, which reads back as
  `"a\n\nb"`. The file gained a blank line nobody asked for.
- **It rewrites files barely touched.** A `.toml` with CRLF endings, read, one key changed,
  written back, comes out entirely LF. Mod configs are the canonical thing actions edit,
  and every line then reports as modified — which makes the Run Report's diff (§4.1)
  useless on any Windows-authored config, and makes a rollback restore a file that is not
  the file it snapshotted.

Translation is therefore **off** on every read, write and restore in the file store. A
round trip is byte-exact and a file's own line endings survive contact with an action.

This is also load-bearing for §3.3's dry-run guarantee: a dry run reads the bytes it
staged, a real run reads them back off disk, and the two can only be interchangeable if
nothing rewrites them in between. The same applies to Layer 2 values surviving `str()` and
back through SQLite.

#### Per-Key Ownership for Structured Configs

For unstructured files (scripts, raw text), ownership is per-file. One owner, period.
Each action writes its own files. KubeJS loads all `.js` files in a directory, so a
removal action writes `server_scripts/packsmith_removal.js` and a recipe action writes
`server_scripts/packsmith_recipes.js`. No conflict.

But mod config files break the per-file model. `quark-common.toml` is one file. An action
that disables features, an action that configures Wraith Sounds entity lists, an action
that manages the Pettable allowlist, and the user who wants to tweak a UI setting — all
have legitimate reasons to touch the same file.

The solution: **per-key ownership for structured config formats.** Packsmith parses the
config, tracks ownership at the key/field level, and merges on write. Each action claims
specific keys. The user owns everything unclaimed. Multiple actions can coexist
in the same file as long as they don't claim the same keys.

```
quark-common.toml
  ├── [Wraith Sounds].wraith_entities     ← owned by: wraith_cfg:apply_entities
  ├── [Enchanting Stacks].stacks          ← owned by: enchanting:apply_stacks
  ├── [Enchantments To Begone].list       ← owned by: removal_suite:nuke
  ├── [Pettable].allowlist                ← owned by: pettable:apply_allowlist
  └── everything else                     ← owned by: user (or untouched)
```

Key-level conflicts (two actions claiming the same key) are detected at package
install/configuration time, not at runtime.

#### Editor Integration

The Text Editor (§6.3) surfaces key-level ownership visually — subtle background tint on
action-owned ranges, ownership indicators in the gutter, tooltips showing provenance.
Edit attempts against action-owned ranges route through the ownership-transfer flow.
The NBT Editor (§6.4) does the same for compound paths. The JAR Viewer (§6.5) always
opens files read-only from within the archive; its save-as-override workflow writes to
datapack/resourcepack directories as new user-owned files.

#### Supported Structured Formats

Per-key ownership applies to any format that is parseable with addressable fields:

| Format | Key Granularity | Notes |
|--------|----------------|-------|
| JSON / JSONC / JSON5 | any key path | Comment preservation needed for json5/jsonc |
| TOML | `[section].key` | Comment preservation — solvable with round-trip libs |
| YAML / YML | any key path | Comment preservation, whitespace sensitivity |
| INI / .properties | `key` or `[section].key` | Java standard, used by MC for lang/some configs |
| .conf | `key` | Simple key=value (as seen in Forge ecosystem) |
| .cfg | Forge category + key | Forge-specific legacy format, still appears |
| CSS (e.g. `emi.css`) | selector block + property | EMI uses CSS-syntax for config — fully parseable |
| .mcmeta | any key path | It's JSON |
| .dat / NBT | any compound path (e.g. `Data.Player.Inventory`) | See §6.4 — NBT has its own editor but the ownership model is the same per-path shape as the other structured formats |

Per-file ownership only (unstructured):

| Format               | Notes |
|----------------------|-------|
| .js / .zs /  scripts | Each action writes its own file |
| .txt                 | Could be anything — per-file only |

The critical engineering concern across all structured formats is **comment-preserving
round-trip parsing.** Packsmith must read, modify specific keys, and write back WITHOUT
destroying comments, formatting, or key ordering. This is a solved-ish problem (round-trip
TOML/JSON5/YAML libraries exist) but requires deliberate parser selection.

#### File Versioning

Actions create and modify files. These changes are **versioned** through a
**content-addressed blob store** — git-inspired, but not git itself. Each unique file
version is stored once by content hash; snapshot metadata (which action produced it,
via which job run, pre-write or post-write, when) lives in SQLite and references the
blob. Pack devs iterate — they run the same jobs repeatedly while tweaking — so
deduplication isn't theoretical; a full snapshot-dir-copy scheme would blow up disk
usage fast on realistic workflows.

Why not just use git under the hood? Git's commit model doesn't fit cleanly with
Packsmith's metadata needs (per-step transaction state, "ran with no changes" records,
action attribution outside the commit-message string), and shipping libgit2 or requiring
a git binary is a dependency cost that buys us less than controlling the metadata schema
ourselves. Why not plain directory copies? Disk usage — see above. Content-addressed
blob storage is the sweet spot: git's deduplication without git's baggage, and without
putting a `.git` directory anywhere the user can trip over it.

Before an action touches a file, its current state is captured as a blob and the
snapshot row is recorded. After the action step completes, the result is captured the
same way. Text diffs are computed on demand via `difflib.unified_diff` (stdlib, no
extra dep); binary diffs (NBT, images) are format-specific and handled by the
respective editors when applicable.

This gives:

- **Per-file history**: "Show me every version of `quark-common.toml`"
- **Per-run grouping**: "Full Removal Workflow, April 15 — modified 126 files, added 6000
  lines" as a single reviewable unit
- **Rollback**: "Restore `supplementaries.toml` to before the removal run touched it"
- **Diffing**: expand any run, see every file diff, approve or rollback the
  whole batch or individual files

The void gets a flashlight. "My script just touched 126 files and I hope it was right"
becomes "my script touched 126 files and here's exactly what changed in each one."

#### Write-Time Existence Checks

External writes happen — mod updates rewrite configs, Minecraft regenerates
`options.txt` on launch, a user edits a file in VSCode or drags one in from Explorer.
Packsmith doesn't proactively scan for these changes. Instead, the write capabilities
(§7.3) take **existence flags** — `file_must_exist`, `key_must_exist` — that guard
each write at the moment the action tries to perform it:

- Action's per-key write to `quark-common.toml:[Wraith Sounds].wraith_mobs` with
  `key_must_exist=True` → if the key is missing (mod update renamed or removed it), the
  write fails loudly with a clear error. The step halts; the user sees exactly what
  the action expected and what it found.
- Action's whole-file write with `file_must_exist=True` → same treatment for the file
  itself.

When an existence check fails, the user gets three resolution options:

1. **Revert** — restore the file from the blob store's last known good version, so the
   action can retry successfully.
2. **Accept** — treat the current on-disk state as the new truth. The tracking baseline
   updates; any action claims on targets that no longer match are **released** (the
   claim is marked dead, the action no longer owns that target). A loud summary names
   each released claim and which jobs are affected: "`removal_suite:nuke` claimed
   `[Enchantments To Begone].list` — key no longer present. Affected jobs: Full Removal
   Workflow."
3. **Release** — stop tracking the file entirely. Future external changes are invisible;
   any action claims on the file are released.

Per-key *migration* is not offered. Packsmith does not try to move a claim from
`wraith_mobs` to `mobs_to_add_wraith_sounds` even if the value pattern suggests a
rename. Actions hardcode their target paths in Starlark source, so there's no user-level
repair path — schema breaks in mod configs are package-author problems, not Packsmith's
to paper over.

There is no background drift scanner, no startup scan, no editor-open drift banner.
Existence drift surfaces at the moment an action tries to do something that depends on
the expected state — which is both the only time Packsmith can reliably act on the
information and the only time the user has enough context to decide how to resolve.

Untracked files still appear in the File Browser (§6.2) — hiding them would make the
browser useless. They render with a muted visual treatment to mark them as unmanaged.
Opening one in the Text Editor auto-claims user ownership, transitioning the file from
untouched to tracked.

**Value drift** — a mod update silently changing a value the action previously wrote,
without changing existence — is not independently detected. The action's next run
re-establishes its intended value through overwrite; the pre-existing value is
irrelevant because the action is the authoritative producer of its owned state and is
about to replace it. This is consistent with the rest of Packsmith's philosophy of
avoiding bubble-wrap UX for self-healing situations.

#### Deleting What An Action Owns (2026-08-25)

Ownership answers "may I write this". Generation asks a second question — **"may I stop
writing this"** — and the answer is deliberately narrower.

An action that only ever writes is not idempotent. Drop a stone from a blueprint and its
six hundred files stay in the mod, compiled forever, describing blocks nothing registers.
The fix is a **sweep**: write what should exist, then remove what you own here and did not
write this run. That is only safe to hand an author if *what you own* is exact and *delete*
cannot reach past it.

**Deletion follows §3.2.1's rule, not this section's.** A write may TAKE a file from another
action — files are open-world, only the user is hard-blocked, and the loser can re-run and
take it back. A delete cannot be undone that way by anyone but its author, and it returns
the path to *"nobody has ever written this"*, which is a state only the user can produce. So
an action may remove **only what it already owns**, and four cases are refused:

| | |
| --- | --- |
| the user owns it | refused — the §6.1 hard-block, and stronger here |
| another action owns it | refused, where a *write* would merely log a takeover |
| **nothing owns it** | **refused** — see below |
| taken from someone else earlier in this step | refused — laundering |

The third is the one that reads either way, and the intuition from tags is wrong. For a tag,
"no row" means pristine and there is genuinely nothing to clear, so `_refuse_foreign_delete`
returns quietly. **A file is not a row.** No ownership record plus a file on disk means
something arrived by a door Packsmith does not watch — and "nobody owns it" is then the
strongest possible reason to leave it alone, because there is no record of who would lose it.

The fourth mirrors the L2 engine exactly: taking a file and then deleting it is two legal
acts whose net effect is one that is forbidden, so the buffer remembers what it took.

**Deletion is staged like everything else.** `content = None` *is* the deletion, modelled
inside the pending buffer rather than in a second set — so `read` returns None, `exists`
says no, and `changes()` classifies `removed` with `after: None`, which is how absence was
already spelled (§3.3). Rollback needed nothing new: `restore` already rewrites prior bytes
from a snapshot, so the inverse of a delete is the inverse of a write with the sides swapped.

##### Sweeps Are Scoped Per Action, Never Per Step

`owned(root, excluding)` answers **"what did I write last time"** — derived from the
ownership table rather than remembered, for the reason §3.2.1 gives for orphans: a record
kept beside the truth goes stale and a derived one cannot.

Scoping is per **action**, which is the safety: another generator sharing the same tree owns
its own files, they are not in the list, and the two need no coordination whatsoever. It is
**not** per step — two steps of one action would each see the other as a foreign owner and
log a takeover on every file of every run — so two steps of the same action pointed at one
folder *will* sweep each other. `under` exists for an author who does that anyway.

**The exclusion is filtered host-side, against the canonical key** (`FileStore.key`), and
this is not a detail. `key` applies `normcase`, which lowercases on Windows, so an author
comparing their own spellings would find `ModBlocks.java` absent from their own produced
list and delete the file they had just written — on every single run, silently, leaving a
mod with no registry. The caller must never do that comparison, so the API does it.

One consequence to know: **moving a file between actions requires the old owner to release
it.** Reassign responsibility for a file and the previous owner's next sweep sees "mine, not
produced this run" and removes it. There is no mechanism for the handover yet; today it is
a matter of clearing the ownership row.

#### Live Questions

##### Round-Trip Parser Selection

Which libraries do we use for comment-preserving round-trip parsing of TOML, JSON5,
YAML, and the other structured formats listed above? This is the core engineering
challenge of the per-key ownership system — without comment-and-formatting-preserving
round-trips, writes would destroy user annotations on every action run. Needs
research per format.

##### Per-Key Ownership Edge Cases

Key rename in the Text Editor: user renames a key, parser sees delete-old + insert-new.
Does ownership transfer? Is the old key's ownership orphaned? What if it was
action-owned? Also: the Text Editor edit-interception UX for action-owned ranges (block
keystroke? revert after? allow with pending-review banner?). Needs an explicit decision.
