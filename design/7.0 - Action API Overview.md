## 7. The Action API

Section 3.3 describes actions, jobs, and the L3 execution model — the *semantics* of
what actions are, how they're invoked, and how jobs compose them. This section
describes the *authoring surface* an action actually uses: the capability system, the
Starlark API, how Packsmith figures out what an action needs, and how integrations
extend the API with additional capabilities.

> **MVP note (§1.1).** The `pack` capability object described here is built for real in
> the MVP and is the load-bearing L1↔L3 / L2↔L3 interface. What the MVP does *not* build
> yet: the Starlark runtime and static capability inference (§7.2 — actions are plain
> Python callables for now), capability *gating* / the satisfaction check (§7.1), and
> integration-provided capability providers (§7.5 — the MVP uses raw `filesystem` writes
> and a hardcoded `config` mod→path map instead of Paxi/KubeJS routing). See §1.1.

### Section map

- **§7.1 Capabilities and Providers** — the core concept. A capability is a named
  interface (e.g., `datapacks.write`); a provider is an implementation (the built-in
  runtime, Paxi, OpenLoader, KubeJS, etc.). Actions declare which capabilities they
  need; profiles supply providers; Packsmith resolves.
- **§7.2 Declaring Requirements** — how Packsmith figures out what capabilities an
  action needs. Mostly via static analysis of the Starlark source; authors can
  optionally add metadata like user-facing reason strings.
- **§7.3 The Capability API** — the shape of the `pack.*` namespace. Resolvers,
  handles, operations, existence flags, transactional batching, read-your-writes
  semantics.
- **§7.4 Built-in Capability Catalog** — placeholder catalog of the always-satisfied
  capabilities (log, L2 access, filesystem, registry reads). Deep-dive deferred.
- **§7.5 Integration-Provided Capabilities** — how integrations register as providers
  of additional capabilities. Cross-references §8 for the catalog of integrations
  Packsmith ships with.
- **§7.6 Writing Actions in Starlark** — authoring conventions, banned primitives,
  `load` rules, helper-function patterns, the `pack` object.

### Why this section exists separately from §3.3

§3.3 answers questions like: *what is an action? what is a job? how do conflict
policies work? what happens when an action step fails?* Those are architectural
questions about the L3 execution model.

§7 answers questions like: *how do I actually write an action? what does the API
look like? what capabilities are available? how do I declare what my action needs?*
Those are authoring questions that change independently of the architectural model.

Splitting them keeps each section focused and lets the API spec evolve (new
capabilities added, the `pack.*` namespace refined) without churning the
architectural spec.

### Relationship to §6.1

§6.1 defines the **ownership model** — who owns what state, transfer rules, per-key
vs whole-file ownership, the blob-store versioning system. §7 defines the **API
that actions use to claim ownership**. The two are tightly coupled: §6.1's
whole-file-vs-per-key ownership distinction is physically encoded by which write
method the action calls (§7.3's `handle.write(...)` vs `handle.write_key(...)`). The
method name IS the ownership claim.
