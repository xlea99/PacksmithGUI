### 6.3 Text Editor

The **Text Editor** is PackSmith's surface for editing textual files — scripts, configs,
datapack JSONs, action source, and anything else that lives as human-readable text. It
is a single PackSmith-level editor built on the Monaco backbone, with per-key ownership
integration, read-only support, and a registration API that integrations use to add
mod-specific intelligence.

It is **not** Monaco. Monaco is the text-buffer and syntax engine underneath. The Text
Editor is what the user interacts with — the tab type, the dirty-state model, the
ownership decorations, the edit interception, the save/override flow. Calling Monaco the
editor would conflate an embedded dependency with a PackSmith-level product surface.

#### Monaco as Backbone

Monaco ships as bundled JavaScript (not CDN-loaded) and runs inside a single
QWebEngineView shared across all Text Editor tabs. Each open text file is a Monaco
**model** — a lightweight buffer holding content, undo history, cursor position, and
dirty state independently. Switching between Text Editor tabs swaps the active Monaco
model via a JS call through QWebChannel. See §4.2 Tab Architecture for the
one-WebEngineView-many-models scheme that makes N open text files effectively free.

Monaco is used because: syntax highlighting for every relevant format is already
excellent, the decoration API supports the ownership visualization this editor needs,
its language-service API is clean (completion providers, hover providers, etc.), and
the Qt embedding pattern is well-understood.

#### Baseline Behavior

- Dark theme (vs-dark), matching the rest of the UI
- Auto-detected language per file extension
- Dirty state tracking, Ctrl+S to save
- Minimap, line numbers, smooth scrolling
- Standard text-editor keybinds: undo/redo, find/replace, multi-cursor, etc.

Target files include mod configs (`.toml`, `.cfg`, `.json`, `.json5`), datapack content
(`.json`, `.mcmeta`), scripts (`.js`, `.star`), and unstructured text. The NBT Editor
(§6.4) handles binary NBT; the JAR Viewer (§6.5) handles archive browsing. Anything
textual that doesn't fit those categories lands in the Text Editor.

#### Per-Key Ownership Integration

For structured formats tracked under per-key ownership (§6.1), the Text Editor uses
Monaco's decoration API to surface ownership visually:

- **Action-owned keys** — subtle background tint, lock icon in the gutter. Edits to
  these ranges are intercepted (via `onDidChangeModelContent`) and blocked or routed
  through the ownership-transfer prompt. Tooltip on hover: "Managed by:
  `removal_suite:nuke`. Click to release ownership."
- **User-owned keys** — subtle gutter indicator, tooltip showing provenance.
- **Untouched keys** — rendered normally, fully editable. The moment the user saves a
  change that touched an untouched key, PackSmith assigns user ownership to it.

For unstructured files (scripts, raw text), ownership is per-file and surfaced as a
status-bar indicator — the decorations don't apply because there's no key granularity
to decorate.

The full ownership model — states, transitions, what "loud transfer" looks like — lives
in §6.1. This section is only about how the Text Editor renders and enforces it.

#### Read-Only Mode

The Text Editor supports full **read-only mode** as a first-class capability, not a
decoration. In read-only mode:

- The buffer refuses all edits (Monaco's `readOnly` option)
- No dirty state, no save path
- A visible banner at the top of the editor indicates why it's read-only
- Find, copy, select, navigate — all still work

Read-only is used in several contexts:

- **Downloaded package source files** (`.star` from §3.3 packages) — the user sees what
  the action does but can't modify it. Authored packages are editable; downloaded ones
  are not.
- **Action tab documentation sources** — README files and similar reference content.
- **JAR-extracted non-overridable files** (§6.5) — class files, `META-INF/`, `mods.toml`,
  `pack.mcmeta` at a jar root, etc. There's no meaningful override target, so the user
  can view but not edit.
- **File history snapshots** — viewing a previous version of a file from the versioning
  system (§6.1) shows the old content read-only; restoring it is a separate explicit
  action.

Read-only is decided per-tab at open time, but it is **not frozen there**. Two things
change it mid-session, both because the alternative is a tab that lies:

- **The user lifts a lock they're allowed to lift.** Taking an action-owned file (§6.1)
  unlocks the buffer in place. This originally said the path was to close and reopen —
  but a reopen after a take reloads the same bytes the tab already holds, so the ceremony
  bought nothing and cost the user their cursor. The *permission* check is what §6.1
  requires; the reopen was never the point.
- **Ownership moves underneath an open tab.** A job run taking a file locks the tab; a
  take in the File Browser unlocks it. Lock state is re-asked of the source, not
  remembered from open time, so it can't drift out of step with the file.

Locks the user may *not* lift stay unliftable — a jar-extracted asset still routes
through the save-as-override workflow (§6.5); a history snapshot still requires an
explicit restore. Those are read-only because of where the bytes came from, and no
amount of ownership changes that.

#### Integration Registration API

Integrations (§7) register with the Text Editor to add mod-specific intelligence on top
of the generic editing baseline. The API is keyed on **file-match patterns** — an
integration declares which files it cares about, and its registered services activate
only on matching tabs:

- **Completion providers** — autocomplete from packdump data, KubeJS globals, etc.
- **Hover providers** — tooltips showing registry entry details, mod provenance, etc.
- **Decorators** — non-ownership visual annotations (e.g., inline ingredient previews
  adjacent to item references, highlighted placeholder tokens in Patchouli pages)
- **Command registrations** — file-type-specific commands exposed in the command palette
  or the file's context menu

These surfaces already exist in Monaco's native API — the integration registration layer
is a thin wrapper that PackSmith uses to route registrations through §3.4's declarative
model (so the same API works for hardcoded-MVP integrations and post-MVP Starlark
plugins). The concrete API shape is defined in §3.4.

#### Save Behavior

Ctrl+S saves through whatever path is appropriate for the file's origin:

- Normal file — write to disk, update dirty state, run the ownership-claim logic if the
  user just touched untouched keys
- JAR-extracted file — routes through the save-as-override workflow (§6.5), which writes
  to the user's datapack/resourcepack via the loader integration (§7.1)
- Read-only file — no-op, but never a *silent* one: the refusal names the lock's reason
  (the owning action, usually) the same way a blocked keystroke does. A save that appears
  to do nothing is indistinguishable from a save that failed

#### Built Beyond This Section

Four things exist in the editor that this section never asked for. They are recorded here
because undocumented behaviour is indistinguishable from accidental behaviour:

- **`DocumentSource`** — the editor doesn't know what a file *is*. It talks to a named
  source (`instance:` for files on disk, others for the synthetic documents blueprints and
  views open), and each source answers the same three questions: read, write, and *why
  might this be read-only*. That last one is what makes lock state re-askable rather than
  remembered, which is what §6.3's mid-session unlocking above depends on. Provenance
  locks — a jar-extracted asset, a history snapshot — are a source's answer, not a flag
  the editor carries.
- **JSON5-tolerant reads** — Minecraft's ecosystem is full of JSON with comments and
  trailing commas, and a parser that refuses them refuses real files the user has to
  edit. Reads tolerate; writes emit strict JSON.
- **`claim` / `release` as primitives** — §6.1 describes ownership changing as a
  consequence of editing. Making it a thing you can *do* directly is what lets the File
  Browser offer it as a menu item and lets the editor lift a lock without a write.
- **The unsaved-changes close guard** — Save / Discard / Cancel when closing a dirty tab.
  Its Save branch depends on the Monaco buffer being read on the JS side before the model
  is disposed; that ordering is load-bearing and is commented at the call site.
