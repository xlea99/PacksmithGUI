### 9.2 Database Schema

The SQLite database stores all Layer 2 data. Ownership tracking (see §3.2.1 and §3.2.2)
means every row in `tag_assignments` and `instance_bindings` carries an owner reference.

Ownership rows reference **actions**, not jobs — jobs are user-owned step sequences, the
code that actually claims ownership is always an action (see §3.3.1). Action references
use the stable `package:action_id` form.

```
tag_definitions       — id (surrogate PK — identity, see §3.2.1),
                        registry_type, name, type, enum_values, default_value
                        UNIQUE (registry_type, name)
tag_assignments       — tag_id FK, entry_id, value,
                        owner_kind (user | action),
                        owner_action_ref (nullable, package:action_id)
                        PRIMARY KEY (tag_id, entry_id)

blueprints            — id, name (unique), description
blueprint_slots       — blueprint_id, parent_id (nesting), name, kind (group | value),
                        type, registry_type, ref_blueprint_id, enum_values, position
blueprint_instances   — blueprint_id, name, created_by, orphaned_by
                        UNIQUE (blueprint_id, name)
instance_bindings     — instance_id, slot_id, value
                        (registry entry ID or blueprint instance ID),
                        owner (user | action), action_ref (nullable)
                        PRIMARY KEY (instance_id, slot_id)
blueprint_mutations   — a removal/retype awaiting resolution, with a snapshot to revert to
blueprint_limbo       — bindings a mutation stranded, held until re-bound or dropped

views                 — id (surrogate PK), name (unique), query_json (the serialized
                        query AST, §3.2.4), renderer, renderer_config, position

job_runs              — id, job_id (SET NULL), job_name, started_at, finished_at, status
step_runs             — id, action_ref, status, reason, started_at, finished_at,
                        rollback_data, log_output, job_run_id, step_id, position_in_run
jobs                  — id, name (unique), default_on_error, pinned, position
job_steps             — job_id, position, kind (action | job_ref), action_ref,
                        ref_job_id, on_error, bindings, config
file_ownership        — path (PK, canonical key), owner_kind, owner_action_ref
```

#### Where This Diverges From The Prose Above

Four differences, each deliberate, and each previously undocumented — which is how a
schema stops being a specification and becomes folklore.

**`tag_assignments` has no `registry_type`.** It's reachable through `tag_id` →
`tag_definitions.registry_type`, and a tag definition is already scoped to exactly one
registry (§3.2.1). Storing it twice would allow rows that disagree with their own
definition. Note the knock-on: §3.3.3 describes `job_exceptions` addressing a row by
`(registry_type, entry_id, tag)`, which no longer matches — an exception row identifies
its target the same way everything else does, by `tag_id` and `entry_id`.

**Ownership columns are named two ways.** `tag_assignments` and `file_ownership` use
`owner_kind` / `owner_action_ref`; `instance_bindings` and `blueprint_limbo` use `owner` /
`action_ref`. The *shape* is identical — kind plus nullable action ref — so §3.2.2's "the
same policies apply unchanged" holds, and the code funnels both through one
`policy_key(kind, scope, name)` helper. But it holds semantically, not syntactically: you
cannot write one query against both. Not worth a rebuild migration on live profiles; worth
knowing before you write a join.

**`blueprint_instances.created_by` is one nullable column, not a kind/ref pair.** NULL
means the user made it; a non-NULL value is the `package:action_id` that did. There is no
third state — "created by an action but we don't know which" isn't a thing — so the pair
was encoding one bit twice.

**Columns added after the fact, all additive:** `job_runs.job_name` (denormalized so run
history survives deleting the job), `job_runs.status` includes `running` (a crash leaves
the row visible rather than absent), `step_runs.reason`, `step_runs.job_run_id` /
`step_id` / `position_in_run`, `jobs.position`, `blueprint_instances.orphaned_by`.

**`step_runs.rollback_data` carries more than the inverse.** It is a JSON blob holding
`l2` / `files` / `blueprints` — the per-engine inverse rollback consumes — and, since
2026-08-15, a fourth key `changes`: §3.3's change record, which is what the Run Report tab
renders for a committed run.

Filing it *inside* an existing column rather than adding one is the point, and it is not
laziness. A new column is a `SCHEMA_VERSION` bump and a migration, for data that is
already JSON, already per-step, and already read only by things that ask for the key they
want. `rollback_step` reads exactly the three keys it knows, by name, so the addition is
invisible to it; a row written before the key existed simply has no changes to show, which
is an honest answer about an old run rather than a reason to fail. The column's name is
now narrower than its contents — it is the record of what a step *did*, of which the
inverse is the part that can undo it — and that is a fair price for not migrating.

Those migration-added link columns carry **no FK constraint**, and SQLite can't add one
without rebuilding the table. For `step_runs.step_id` that's correct rather than lax: an
FK would cascade-delete run history when a step is removed, or refuse the removal — and
history is meant to outlive what it describes (which is the whole reason `job_name` is
denormalized). `blueprint_instances.orphaned_by` *is* a live link; its integrity is held by
discipline at both mutation-deletion sites, pinned by tests in
`tests/test_schema_invariants.py`.

#### Layer 3 Tables That Don't Exist

§3.3.3 defines `packages`, `actions` and `job_exceptions` as database tables. **`packages`
and `actions` were never built, deliberately** — §3.3.1's folder model won: an authored
package is a directory of `.star` files and a manifest on disk, discovered by scanning,
not rows to keep in sync with the files they describe. Authoring an action means editing a
file, which is the point.

That makes §9.0's "everything the user creates lives in SQLite" false as written, and it
should be read as: **everything the user creates *as data* lives in SQLite; what they
create as code lives on disk.** Tags, blueprints, views and jobs are data. A Starlark
action is a source file, and a source file belongs in a text editor and a diff, not a BLOB.

`job_exceptions` is also unbuilt — the per-entry exception flow it belongs to isn't
implemented yet.

Schema details (column types, indexes, foreign keys, migration strategy) are not yet
finalized — this is a structural sketch, not a DDL specification. The ownership columns
are load-bearing for the §3.2 ownership lifecycle and the §3.3 conflict policy system;
everything else is subject to refinement during implementation.

#### Live Questions

##### Data Migration / Schema Versioning

As the SQLite schema evolves during development, how do we handle migration of
existing profile databases? `profile.py` has a TODO about this. Not urgent for early
dev (blow away and recreate is fine), but needs a real answer before any release
where users have data they care about. Options: a dedicated migrations directory with
numbered up-scripts (Alembic-style), lazy per-table inspection-and-patch on open, or
a schema-version pragma that triggers a one-shot migration routine on mismatch.
