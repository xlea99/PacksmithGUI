### 4.1 Window Layout

Standard IDE-style layout with three zones: a left sidebar for navigation, a main
workspace for content (~3/4 of the area), and a collapsible bottom panel (~1/4) for
output, status, and the status bar.

```
┌──────────────────────────────────────────────────────┐
│  Header: profile name, MC version, loader            │
├─────┬────────────────────────────────────────────────┤
│  V  │  [View: Items] [Text: config.toml] [BP:Gran]   │
│  B  │                                                 │
│  T  │            Main workspace (tabs)                │
│  F  │                                                 │
│  R  │               (~3/4 height)                     │
│  J  │                                                 │
│     ├─────────────────────────────────────────────────┤
│     │  [Logs] [Job Results] [Errors]                   │
│     │          Bottom panel (~1/4 height)             │
│     ├─────────────────────────────────────────────────┤
│     │  Status bar (item count, dirty files, job run)  │
└─────┴─────────────────────────────────────────────────┘
```

Dark mode UI throughout (dark grays, blue accent).

#### Left Sidebar

A vertical icon strip (like IntelliJ/VS Code) where each icon swaps the sidebar panel
content. These are **navigation** panels — how you find and open things. Clicking an item
in any panel typically opens a tab in the main workspace.

| Icon | Panel | Purpose |
|------|-------|---------|
| V | **Views** | Searchable list of saved view configurations. Double-click opens the View in its chosen renderer — typically a registry table (§5.1), sometimes a blueprint node view (§5.2). Ships with sensible defaults (Item Registry, Block Registry, etc.). See §5. |
| B | **Blueprints** | Browse blueprint schemas and instances as a tree. Click a schema to see all instances. Click an instance to open an editor tab. |
| T | **Tags** | All declared tags. Click spawns a minimal view (registry type + that one editable column) — the quick-action *is* the click. Shortcut into the Views system. |
| F | **Files** | The semantic file browser. See §6.2 for the full design — smart/honest modes, loader-aware path resolution via integrations (§7). |
| R | **Registry** | Categorical registry-type list (`minecraft:item`, `minecraft:block`, `minecraft:entity_type`, etc.). Clicking a category opens a zero-tag registry-table View (§5.1) scoped to that type — essentially the fastest way to get a "just show me everything" table without configuring a real View. |
| A | **Automation** | **Jobs** and **Actions**, in two tabs. *Jobs* — searchable, pinned ones first, right-click to edit/create/pin, double-click opens a job editor tab (§3.3.2). *Actions* — installed actions by package; inspect manifests and read documentation (§3.3.1). Actions are not pinnable: they are not the runnable surface. |

More panels can be added later (search/query, etc.) without any architectural changes —
the sidebar is just a list of panels, adding one is trivial.

The strip shows **icons, not letters.** It shipped with single letters (V/B/T/F/R/J/A) as a
placeholder, and they were the wrong shape for the job: an edge strip exists to be reached
for *without looking*, and what a glance resolves is a silhouette — seven glyphs at one
size, weight and colour have nearly identical outlines, so the strip had to be read rather
than recognised. A letter is also a label for a label ("T" abbreviates *Tags*, which is
already the name), and seven of them were used with Search and Settings both wanting S.
Icons come from a vendored Phosphor font (MIT), chosen for distinct outlines rather than
prettiness; the letters survive as a fallback if the font ever fails to load.

**Jobs and Actions share one slot.** They held two until the run control (below) moved
*running* into the header — which demoted the Jobs panel to an editing surface, and editing
jobs is as rare as browsing actions. Two occasional Layer 3 surfaces, one slot. Tabs rather
than stacked sections because they are different shapes: a flat list with run buttons
versus a provenance-governed file tree, and stacked sections make differently-shaped lists
fight over a narrow column.

#### Main Workspace

Horizontal tab bar. These are the things you're actually **working in.** All tab types
are peers — View tabs (§5), Text Editor tabs (§6.3), NBT Editor tabs (§6.4), JAR Viewer
tabs (§6.5), job editors, conflict-resolution tabs — anything.

Opening a View, double-clicking a file, clicking a blueprint instance — all spawn tabs
here. Multiple tabs of the same type are fine (three Views open, two files open, etc.).
Tabs can be closed, reordered, and (eventually) split.

See §4.2 Tab Architecture for how the single tab bar hosts heterogeneous tab types
(Qt widgets and shared-WebEngine Text Editor models) without exploding into N
Chromium processes.

#### Bottom Panel

Collapsible (closed by default, drag up or hotkey to open). Takes roughly **1/4 of the
main area height** when open — enough to scan logs without stealing focus from the
workspace. The status bar lives at the very bottom of this panel, not as a separate
window-level strip. Home for **output and status** — things you want visible while working
but that aren't your primary focus.

| Tab | Purpose |
|-----|---------|
| **Logs** | Live log viewer. Essential for debugging job output, packdump import warnings, etc. |
| **Job Results** | Per-run summary: "Removal Job: 126 files modified, 3 skipped (user-owned)." Expandable to per-file diffs. This is where the file versioning system surfaces. |
| **Errors / Warnings** | Orphaned tags, broken blueprint bindings, ownership conflicts. Each row can be *resolved in place*; **jumping to the relevant view/file/tag is post-1.0** — see below. |
| **Packdump** | Packdump management and review. Shows the diff *summary* (entries added/removed, changed registries, mod list changes), surfaces orphaned tags at risk, lists the archived snapshots, and can revert to any of them. **The diff itself opens as its own tab** — a real update to a 300-mod pack moves thousands of entries, and a strip a few rows tall is a place to learn *that* something changed, not to read *what*; the full tab is filterable and scrollable. A "Bless" action appears only when a dump is actually waiting, which happens only with auto-adopt turned off (§3.1) — a permanently disabled button is a standing invitation to wonder what it does. |

Additional bottom tabs (search results, etc.) can be added as needed.

##### Jumping From an Error to Its Subject — post-1.0 (2026-08-12)

This section originally promised error rows were "clickable to jump to the relevant
view/file/tag". Deferred, not because it is hard but because **the panel took the other
route and the other route is the better half.** Every problem type is resolvable *without
going anywhere*: a stale binding offers "Relink to 'banned'", an orphaned tag offers Clear /
Reassign / Restore-the-value, and a blueprint orphan offers §3.2.2's resolutions. Jumping is
for when you want to *look* before deciding — real, but weaker than fixing it where you
found it.

It is also close to free whenever it is wanted: the rows already carry their subject in item
data (the registry type and tag name, the stale-binding record, the orphan), and
`_open_tag_view`, `_open_blueprint` and `_open_document` all exist. It needs a signal and
some wiring, not a design.

Natural home is a pass over the bottom panel as a whole rather than its own slice.

#### Menu Bar

Standard menu bar at the top: `File | Edit | Window | Views | Profiles | Help`.

Two notes on the names. **Views** is plural because it is the Views *system* (§5.0) — New
View, saved views — not the conventional View menu of zoom and toggles; those live under
**Window**. Several entries are visible-but-disabled placeholders for capabilities that
aren't built; they are deliberate, so the shape of the app is legible before every corner
of it works, and each one is disabled rather than absent so it can't be mistaken for
something that silently does nothing.

The **Profiles** menu handles profile management — create, switch, delete. Switching
profiles is a heavy action (reloads the entire packdump and database) and prompts for
confirmation. Packsmith remembers the last active profile and auto-loads it on startup.

#### Header & Status Bar

- **Header**: `{profile_name}` on the left, the **run control** in the middle, and
  `{mc_version} {loader} {loader_version} | {mod_count} mods` on the right.

  The **run control** is a job picker and a play button — the run-configuration pattern,
  and the answer to §3.3.2's "rarely edited, constantly re-run". Pinned jobs sort first in
  its dropdown; `Ctrl+R` runs the selection; the picked job is remembered per profile. It
  disables play with a reason when the selected job can't run, and locks for the duration
  of a run. It hides entirely when a profile has no jobs, rather than showing an empty
  dropdown. See §3.3.2's *Pinning, and the Run Control*.

  Putting it here is what makes the Jobs panel an editing surface rather than the place you
  go to press play — which is why Jobs and Actions could then share a sidebar slot.
- **Status bar**: the bottom-most strip inside the bottom panel (always visible even when
  the panel's tab content is collapsed). Shows contextual information: item count in
  current view, dirty file indicators, job run status, etc.

  It re-states itself **on tab activation**, not only when a tab opens. Writing it once at
  open meant that after a tab switch the bar confidently described a tab that was no longer
  in front — and a status bar that is wrong is worse than one that is empty, because
  nothing distinguishes the two. What it says depends on what's in front: row count for a
  view, and for a file, who owns it (§6.3) plus whether it has unsaved changes.
