### 7.5 Integration-Provided Capabilities

Built-in capabilities (§7.4) are always satisfied. Integration-provided capabilities
depend on which mods are installed in the current profile. This section describes the
**mechanism** by which integrations register as capability providers; §8 describes
the specific integrations Packsmith ships with.

#### The Registration Surface

An integration registers with Packsmith via a handful of declarative API calls
(§3.4's plugin registration model). Among those: **`register_provider`.** An
integration provides a capability by declaring:

- The capability name (`datapacks.write`, `kubejs.script_write`, etc.)
- The version it implements
- The handler functions that back the capability's API surface (for resolvers and
  operations)

For MVP, integrations are Python modules inside Packsmith calling `register_provider`
directly at startup. Post-MVP, they become Starlark `.star` plugin files calling the
same registration functions through the plugin runtime (§3.4).

#### Conditional Activation

A provider registration is conditional on its mod being detected in the current
profile's packdump. The KubeJS integration's registration code runs at profile load
only if `kubejs` appears in the mod list. The Paxi integration's runs only if
`paxi` appears. Providers whose gating mod isn't present simply don't appear in the
resolution table.

This means an action declaring `kubejs.script_write` runs on a KubeJS-installed
profile and fails the satisfaction check on a profile without KubeJS. The user is
pointed to install KubeJS (or to use a different action, or to mark this action as
optional if it's one part of a larger multi-phase workflow).

#### What a Provider Registers

A provider registration includes:

1. **Resolver functions** — how to map the capability's resolver inputs to
   handles. E.g., Paxi's `datapacks.resolve(pack_name, namespace, path)` knows how
   to compute the correct path under `<instance>/config/paxi/datapacks/...`.
2. **Operation backends** — for capabilities that extend the handle API with
   provider-specific methods (e.g., Paxi's `datapacks.ordering.set_priority`), the
   provider supplies the implementation.
3. **Metadata for UI** — human-readable provider name, documentation link, version,
   etc., for display in the resolution table and conflict-disambiguation UI.

Operation implementations are generally simple — a resolver that computes a path
plus a thin translation layer over the existing `filesystem` capability for reads
and writes. Most of the work is in the resolver.

#### Sub-Capabilities

A provider can register some sub-capabilities in a namespace without registering
others. Paxi registers all of `datapacks.read`, `datapacks.write`,
`datapacks.ordering`, `resourcepacks.read`, `resourcepacks.write`,
`resourcepacks.ordering`. OpenLoader registers `datapacks.read`, `datapacks.write`,
`resourcepacks.read`, `resourcepacks.write` — no ordering. The "Global Data Packs"
loader mod registers only `datapacks.read` and `datapacks.write` — no resourcepacks
at all.

Each sub-capability is a separate registration call. An action that requires a
specific sub-capability will find it satisfied only when a provider that registers
that specific sub-capability is active.

#### Multi-Provider Resolution

When two providers register for the same capability, Packsmith picks one as the
default for the profile and offers the choice in relevant UI surfaces. See §8.1 for
the specifics of loader disambiguation, which is the common multi-provider case.
Sticky per profile — user's choice persists across sessions.

Providers that aren't selected as the default still exist in the resolution table
with a "not selected" flag and can be swapped in via the UI without reinstalling
anything.

#### Library Packages vs Integration Providers

An integration provides **capabilities** — extensions to what actions can call.
A **library package** (§3.3.1's concept) provides **helper functions** that actions
can `load` and use — just shared Starlark code, not an extension of the API.

The two compose: an `@emi_utils` library package might internally call
`pack.filesystem.resolve("emi.json").write_key(...)` to hide items in EMI's config —
encapsulating the knowledge that EMI's config lives at the pack root (not under
`config/`) so action authors never have to know it. The library's code uses built-in
capabilities under the hood; it doesn't register anything new with the capability system. Authors using `@emi_utils` declare
`emi_utils` as a package dependency, not a capability.

If a mod's API genuinely can't be expressed through existing capabilities (rare —
mostly applies to mods that expose in-game runtime APIs like KubeJS's script
execution), an integration provides a new capability. Otherwise, libraries are the
right abstraction.
