### 5.3 Reporting and Recommendations

This section is a **decision record.** Two linked questions surfaced while working the
canonical stone problem (§3.2.2), and both had tempting-but-wrong answers that would have
added whole subsystems. The reasoning is preserved here so the conclusions don't get
re-litigated — the *why* is the valuable part.

Both questions come from the same place: the hardest part of the stone problem isn't
applying recipe changes to each item ID, it's **finding each item ID.** `alexscaves:galena`
has stairs and a slab but no wall — yet `quark:ac_galena_wall` exists. Create adds a cut-brick
form but skips Alex's Caves; Stoneworks fills that hole but misses the slab. Three mods each
add their own `chiseled_galena`. The registry is 100+ types of naming chaos with arbitrary
coverage. Packsmith has to help the user *see* and *fill* that — which raised: (1) is that a
new "reporting" subsystem? and (2) where does the fill-assistance ("recommendations") live?

#### Part A — Reporting is not a subsystem. It's the query engine.

**The question.** Surfacing "what's in the pack, organized, so the user can act on it" felt
like a distinct capability — call it *reporting* or *meta-actions*. Should Packsmith grow a
reporting system?

**The wrong turn.** Modeling reports as **read-only actions** (an action whose output is
structured information instead of file writes). It's expressible — an action declaring only
`read` capabilities is a legitimate thing — but it's the wrong altitude for almost every
real report.

**The resolution.** A report is a **query.** The distinction that matters isn't read-vs-write
(reports and queries are both read-only) — it's **declarative vs. procedural.** Walk the real
cases and nearly all are declarative:

- Tag-completeness audit ("`is_food == true` AND NOT HAS `food_group`") — already the query
  language.
- Orphan detection — already a SQL query in `tags.py`.
- Provenance / distribution ("entries per mod per registry") — aggregation.
- Cross-mod duplicates — fuzzy grouping.
- Even the stone candidate-finder — a token/fuzzy match: `id MATCHES_TOKENS("galena", "wall")`
  finds `quark:ac_galena_wall` *because* it contains both tokens, ignoring the `ac_` prefix
  and namespace that break substring matching.

None of those want arbitrary code. They want a **query engine more powerful than the
filter-bar sketch in §3.2.3** — projection of computed columns, aggregation, grouping,
fuzzy/token matching, joins across L1 + L2 + blueprint bindings. Add those and "reports" stop
being a distinct concept: they're saved queries, rendered — which is to say, **Views.**

This reframes the §3.2.3 "Query Language Specification" Live Question. It was filed as "spec
the filter grammar." It's actually **"how powerful is the query engine"** — and that decision
quietly absorbs ~90% of what "reporting" would have been.

**The philosophy that makes this work:** the value is **human-in-the-loop surfacing, not
automation.** No heuristic can reliably decide that `stoneworks:alexc_galena_cut_brick` is
galena's cut-brick — that's a judgment only the pack dev can ratify. So reporting isn't "be
clever and do it for me," it's "be a great research assistant — here's everything relevant,
organized and ranked, *you* decide." This is the same flashlight the file-versioning system
(§6.1) shines on file diffs, pointed at the registry instead.

**Where the action framing survives:** the genuinely procedural tail — reports needing
multi-hop traversal or custom algorithms a query can't express ("every item used as an
ingredient in a recipe that produces a removed item"). *That* is a read-only action. It's the
**escape hatch, not the definition** — and it's far-future (v2+), not something to build now.

**The filter bar decision (locked):** the filter bar stays **loudly dumb** — a visual
builder, zero learning curve — but is powered underneath by **one universal query language
usable everywhere.** If you know how to type a complex query, it works in the same bar; a
richer query surface may appear in other contexts later. This is already latent in §3.2.3
("the builder IS the documentation for the query syntax," the two modes stay in sync).

#### Part B — Recommendations live in View config, not the blueprint.

**What a recommendation is.** When filling a slot (or any registry-pointer cell), a query
that surfaces likely registry candidates — finding `quark:ac_galena_wall` for the galena
"wall" slot despite the naming chaos — ranked, for the human to confirm. The tool *finds*;
the human *decides*. (Working name: **candidate recommendations** — the blessed name is a
Live Question below.)

**Not auto-suggest-by-inference.** Packsmith must not guess "the slot named `stairs` means
search `+stairs`." Slot names are arbitrary — that's the entire reason **mappings** exist
(§7.1). Inferring intent from user-chosen names is fragile and off-brand. Instead, the
**user authors the recommendation query**, parameterized over the instance and anchored on a
reliable slot (the base binding): `id MATCHES_TOKENS(tokens(base), "stairs")`. The author
encodes "base is my anchor" *by referencing it* — Packsmith never discovers it. Name-inference
survives only as a **draft the author ratifies** while authoring, never as a silent binding.

**Where does it live? The debate.** This is where the reasoning matters, because three
positions were tried and two were wrong:

- **Not a constraint / not the type.** The type is a *closed gate* — it defines what's
  *allowed* and you cannot bind outside it. A recommendation is an *open hint* — it must
  never restrict, or you lock yourself out of exactly the `stoneworks:ac_gal_str` weirdness
  that makes the problem hard. They look alike (you stare at both while filling a cell) but
  one is a wall and one is a sticky note.

- **Not blueprint schema/data.** Proven by two independent tests, which the recommendation
  fails on both:
  - **Separability.** Can you serialize the blueprint without it? Type — no, the structure is
    undefined and unbindable; it's constitutive. Recommendations — yes, strip every one and
    the blueprint is byte-for-byte still itself, fully functional, just less convenient.
  - **Causal inertness.** Does removing it change what any action *reads*? Type — yes.
    `default` — yes (an unset tag with a default resolves to it on read; remove it and
    automation behaves differently, which is why `default` is legitimately definitional).
    Recommendation — **no**; no action reads it, and stripping every recommendation produces
    identical output from every job.
  - **The clincher:** a fact *about* a blueprint cannot legitimately differ between two
    instances of it (all StoneType instances share their slot types — that's what makes them
    StoneType). But galena and granite can coherently have *different* recommendations without
    either ceasing to be a valid StoneType. Therefore a recommendation is not part of what a
    StoneType *is*.

- **Therefore: View renderer config.** A recommendation is a knob a blueprint-oriented
  renderer exposes, authored/saved/reused as part of a **View** — which is a separate L2
  artifact from the blueprint. Consumers: **humans** via the rendered fill-helper; **actions**
  (someday, if an auto-populate action wants them) via `views.read` (§7.4) — already a
  declared capability, since an action reading a recommendation is just an action reading a
  View. One home; both doors already exist. Nothing touches the blueprint.

**Scope precision.** Strictly, it's config on **any renderer with fillable registry-pointer
cells** — primarily the blueprint renderers, but the same knob would naturally appear on a
`reference`-type tag column in the plain registry table someday. Blueprint-heavy, not
blueprint-exclusive — and *not* a general standalone system.

**Cold start.** A fresh user who imports a blueprint but has authored no View has no
recommendations — the same situation as a fresh tag with no View. Solved the same way: ship
sensible **default Views**, and let a shared blueprint travel with an optional **suggested
filling-View** as a separate companion artifact (analogous to packages shipping suggested
jobs, §3.3.2). Convenience without coupling.

##### ~~Cross-Renderer Recommendation Sharing~~ — MOOT FOR 1.0

> Deferring the Node View past 1.0 (§5.2, 2026-08-11) dissolves this question rather than
> postponing it: there is exactly one blueprint renderer, so there is nothing to re-spec

> the eventual answer is now partly constrained by what shipped: recommendations live in
> `renderer_config` on the grid, so any sharing mechanism has to migrate them out of there
> rather than design them from scratch.

If Packsmith ships **both** a Blueprint Node View (§5.2) and a multi-instance table renderer
(instances as rows, slots as columns), they are *different renderers* → *different View
configs*. Under "recommendations live in View config," the user would have to **re-spec their
recommendations in each** — exceedingly annoying for a 24-slot × 29-instance schema. This is
in genuine tension with the Part B conclusion: sharing wants recommendations to live somewhere
*referenceable by multiple Views* (a reusable recommendation artifact that Views point at? a
per-blueprint recommendation set that renderers pull from?), which pulls partway back toward
"a saved query things reference." Deferred, but important — it's the first real crack the Part
B model will have to answer when a second blueprint renderer exists.
