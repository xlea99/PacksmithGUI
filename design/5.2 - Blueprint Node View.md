### 5.2 Blueprint Node View

> **DEFERRED PAST 1.0 by decision, 2026-08-11.** Not blocked, not unresolved, not waiting
> on anything — judged simply not load-bearing. Nothing else in 1.0 depends on it.
>
> **The grid renderer took the job.** §5.2 was specified when the blueprint editor was a
> placeholder and it was not yet obvious what looking at a blueprint would feel like. What
> got built instead — instances as rows, slots as columns, with the suggestion picker in
> the cells — turned out to be the shape the stone-palette problem actually wants: you are
> comparing 29 instances across 24 slots and hunting the gaps, which is a table question.
> A node graph is the better answer for a *different* question (how do these schemas
> reference each other), and that question has not come up in real use yet.
>
> Its one genuinely portable idea already landed elsewhere: §5.3's candidate
> recommendations are renderer config, and they live on the grid renderer today.
>
> **This stays specified rather than deleted.** When a second blueprint renderer is worth
> having, the design and its open questions should be here waiting rather than re-derived.

**PLACEHOLDER** — full design to be worked through separately. This section will
describe the node/graph renderer used by Views targeting blueprint schemas and
instances.

> **See §5.3** for where this renderer got part of its identity: candidate
> recommendations (the fill-assistance that finds `quark:ac_galena_wall` for an empty
> "wall" slot) are **renderer config on this and other blueprint-oriented renderers**,
> not part of the blueprint data. §5.3 also flags the deferred cross-renderer sharing
> question (Node View vs. a multi-instance table renderer).

The rough idea: a schema appears as a node tree (inline groups nested, blueprint
references shown as edges to other schemas). An instance appears as the same tree
with bound registry entries populating slots and empty slots highlighted as gaps.
The View is the primary surface for both browsing blueprint data and identifying
gaps to fill.

Significant open questions — layout algorithm (manual vs. auto), edge rendering
for cross-schema references, how instances relate to schemas visually, bulk
gap-filling UX, integration with the auto-population strategy in §3.2.2's Live
Questions — all deferred until we sit down and design it properly.

For now, everything the Blueprint Node View needs to express is defined in §3.2.2
(blueprint schemas, instances, bindings, ownership, schema evolution rules). This
section will fill in *how* all of that gets rendered and edited once we tackle it.
