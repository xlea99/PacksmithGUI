## 8. Integrations

Integrations are mod-aware extensions that teach PackSmith about specific mods —
datapack loaders, scripting frameworks, guidebook systems, anything whose presence in
the modpack changes how PackSmith should behave. This section documents the specific
integrations PackSmith ships with. The plugin *system* that will eventually host
third-party integrations is documented in §3.4.

### The Pattern

Integrations don't ship their own editors, their own file browsers, or their own tab
types. They register into the generic surfaces that already exist:

- Smart folders and context-menu actions → §6.2 File Browser
- Language services (completion, hover, decorators) → §6.3 Text Editor
- Override-target resolution → §6.5 JAR Viewer and action file APIs
- Bottom-panel tabs → §4.1 Window Layout
- Packdump-informed data (item IDs, block IDs) → Layer 1 (§3.1)

The pattern is consistent: PackSmith builds the generic surface; the integration
registers its mod-specific knowledge into that surface. This keeps the editors small
and the integration set composable.

### MVP Delivery

For MVP, integrations are **hardcoded** into PackSmith as Python modules that call the
registration APIs at startup. Post-MVP, the plugin runtime (§3.4) replaces the
hardcoded calls with Starlark-declared `.star` plugin files. The API surface is the
same either way — the MVP integrations *are* the prototype plugin API, just with the
callers being internal Python instead of external Starlark.

### Integration Catalog

- **§7.1 Global Datapack & Resourcepack Loader Integration** — foundational-but-optional.
  Enables global-scope datapack/resourcepack overrides by resolving paths through whichever
  loader mod is installed (Paxi, OpenLoader, Moonlight/Global Packs).
- **§7.2 KubeJS** — scripting framework. Smart folders for KubeJS's three script
  directories, registry-backed autocomplete, potentially DB access at game runtime.

Future integrations (not planned for v1.0 but on the radar): Patchouli book page
previews and template scaffolding, Create ponder-schema support, InControl/Item
Obliterator format helpers, EMI config assistance.

### Integration Scope

Integrations describe **how PackSmith behaves when a given mod is present.** They do not
ship their own actions (those come from packages, §3.3), do not modify Layer 2 data
directly, and do not write game state. An integration's job is to make the user's
workflow for that mod less terrible — better paths, better autocomplete, better context
menus, better override targeting.

Actions that *use* a mod's APIs (writing KubeJS scripts, generating Patchouli book
pages, configuring Item Obliterator) live in packages and run through the job system
(§3.3). The line: integrations improve the *authoring* experience; actions carry out
*work* against mod APIs. The two compose — an integration can make the Text Editor
smarter about the files an action produces, and an action can generate files that the
integration's smart folders route intelligently.
