### 5.1 Registry Table View

The **Registry Table** is the workhorse renderer — the one used by the vast majority
of Views in practice. It displays registry entries as rows with tag values as
editable columns, built on Qt's Model/View/Delegate architecture:

- **RegistryTableModel** — virtual/lazy-loading model, 2 fixed columns (ID, Display
  Name) + N dynamic tag columns
- **RegistrySortProxy** — type-aware sorting: numbers sort numerically, bools sort
  False→True, strings sort case-insensitive, empty values always sink to bottom
- **RegistryTableView** — keyboard-driven bulk editing
- **Cell delegates** — type-specific rendering and editing per tag type

#### Renderer Config

A Registry Table View's renderer-specific config (§3.2.3) includes:

- Which registry type(s) to target — typically one, occasionally a union
- Which tag columns to show, and in what order
- Which columns are editable vs. read-only display
- Default sort (first column, A→Z, unless overridden)

Registry type scoping is strict: tag columns are per-registry (§3.2.1), so a View
targeting `minecraft:item` cannot display a tag scoped to `minecraft:block`. The
View editor's column picker filters options accordingly.

#### Keyboard Shortcuts

| Key         | Action                                                              |
|-------------|---------------------------------------------------------------------|
| Space       | Gmail-style bool toggle (all True → all False, otherwise all True)  |
| Delete/Bksp | Clear selected cells (unset tags)                                   |
| Ctrl+C      | Copy as TSV (plain text) + HTML table                               |
| Ctrl+V      | Single-value paste fill with type validation                        |
| Enter       | Commit edit and move down one row                                   |
| Ctrl+Z      | Undo                                                                |
| Ctrl+Y      | Redo                                                                |

#### Copy Behavior

- Format: TSV (tab-separated values)
- Bools copy as literal `true`/`false` (not empty — empty means unset)
- Default values are included in copy even if not explicitly written to DB
- Multi-cell selection copies all selected cells, not just the anchor

#### Undo/Redo

All tag edits go through an **EditStack** using the command pattern:

- **TagEditCommand** — single cell edit, stores old/new value, can apply/undo
- **BatchEditCommand** — groups multiple TagEditCommands, optimizes bulk operations
- Redo stack is cleared when a new command is executed

#### Ownership Visualization

Per §3.2.1, every cell has one of three ownership states: pristine, user-owned,
action-owned. The registry table renders these distinctly — for bool cells in
particular, where "pristine" and "user-owned false" look visually identical without
an ownership indicator. See §3.2.1 for the full state table and transition rules.

#### Default Sort

First column, A→Z on open.

#### Live Questions

##### Undo Scope

Ctrl+Z in a view — does undo cross tabs? Cross sessions? What about undoing a tag
definition change that cascaded to hundreds of unset assignments? The per-view
EditStack is specified above, but cross-view and destructive-cascade undo is not.
