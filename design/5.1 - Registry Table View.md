### 5.1 Registry Table View

The **Registry Table** is the workhorse renderer — the one used by the vast majority
of Views in practice. It displays registry entries as rows with tag values as
editable columns, built on Qt's Model/View/Delegate architecture:

- **RegistryTableModel** — virtual/lazy-loading model, 2 fixed columns (ID, Display
  Name) + N dynamic tag columns
- **RegistrySortProxy** — type-aware sorting: numbers sort numerically, bools sort
  False→True, strings sort case-insensitive, empty values always sink to bottom
- **RegistryTableView** — keyboard-driven bulk editing, plus a right-click menu for the
  same operations (§3.2.1 names one for Clear assignment; keyboard-only made it
  undiscoverable)

Extras the implementation added, kept deliberately:

- **Enum columns sort in declaration order**, not alphabetically — `early / mid / late`
  is the order the user defined and the order they mean; A→Z would scramble it.
- **Takeover confirmation is aggregated per edit**, not per cell: taking 200 cells from an
  action asks once and names the actions involved, where 200 dialogs would be a thing to
  click through rather than a decision.
- **Number cells tolerate separators** (`1 000`, `1,000`) on entry.
- **Enum dropdowns open on edit**, so the vocabulary is visible without a second click.

Still absent: a default-sort override (views always open sorted by the first column,
A→Z) and per-view column order/editability configuration.
- **Cell delegates** — type-specific rendering and editing per tag type

#### Renderer Config

A Registry Table View's renderer-specific config (§3.2.3) includes:

- Which registry type(s) to target — typically one, occasionally a union
- Which tag columns to show, and in what order
- Which columns are editable vs. read-only display
- Default sort (first column, A→Z, unless overridden)

Registry type scoping is strict: tag columns are per-registry (§3.2.1), so a View
targeting `minecraft:item` cannot display a tag scoped to `minecraft:block`. The
View editor's column picker filters options accordingly.

#### Keyboard Shortcuts

| Key         | Action                                                              |
|-------------|---------------------------------------------------------------------|
| Space       | Gmail-style bool toggle (all True → all False, otherwise all True)  |
| Delete/Bksp | Clear selected cells (unset tags)                                   |
| Ctrl+C      | Copy as TSV (plain text) + HTML table                               |
| Ctrl+V      | Single-value paste fill with type validation                        |
| Enter       | Commit edit and move down one row                                   |
| Ctrl+Z      | Undo                                                                |
| Ctrl+Y      | Redo                                                                |

#### Copy Behavior

- Format: TSV (tab-separated values)
- Bools copy as literal `true`/`false` (not empty — empty means unset)
- Default values are included in copy even if not explicitly written to DB
- Multi-cell selection copies all selected cells, not just the anchor

#### Undo/Redo

**Specified in §9.3.3, not here.** This section originally described a per-view `EditStack`
of `TagEditCommand` / `BatchEditCommand` objects. That was the wrong home: an undo stack
living inside the registry table implies a second one inside the blueprint editor, and with
it a second implementation of the same reversal and a second chance to get staleness wrong.

The reversal primitive is already shared — rollback (§3.3) stores inverse records of an
identical shape for tag assignments and blueprint bindings alike. §9.3.3 puts one stack in
front of it. What this view contributes is what it always should have: producing a record
when a cell is edited, and refreshing when something is reversed underneath it.

#### Ownership Visualization

Per §3.2.1, every cell has one of three ownership states: pristine, user-owned,
action-owned. The registry table renders these distinctly — for bool cells in
particular, where "pristine" and "user-owned false" look visually identical without
an ownership indicator. See §3.2.1 for the full state table and transition rules.

#### Default Sort

First column, A→Z on open.

#### Live Questions

##### Undo Scope — *answered in §9.3.3 (2026-08-18)*

Cross-tab and cross-session are now decided: the stack is **per tab** (global undo reverses
what the user cannot see) and **not persisted** (§9.3.1's snapshots answer "yesterday" more
cheaply). Reversing in one tab refreshes the others.

The destructive-cascade half is also answered: deleting a tag definition is **not**
undoable. Undo reverses values, never schema — see §9.3.3. It is recoverable from the
snapshot §9.3.1 takes before the deletion, which the confirmation is required to say.
