# PackSmith Design Document

> **Last updated:** 2026-04-22
>
> This is a living design document. It captures the full vision of PackSmith, including
> unbuilt systems, with the understanding that specifics will evolve as decisions are made.
> It is the single authoritative reference for what PackSmith is, why it exists, and how
> it works.

---

## 1. What PackSmith Is

PackSmith is an IDE for Minecraft **modpack** development. Minecraft modding has world-class tooling: IntelliJ/VSCode plugins, Architectury, Fabric Loom,
ForgeGradle, KubeJS and its ecosystem. But modpack development — the act of curating, configuring, and
enforcing consistency across dozens or hundreds of mods simultaneously — is a horrific
frankenstack of 15+ disconnected tools, mountains of manual file editing, and prayer. The
current state of the art for most pack devs is Google Sheets and manual auditing.

PackSmith's core insight: **documentation and action are the same problem.** When a pack
dev decides to remove an item, they must remember that decision (documentation) AND
propagate it across five or six disparate files (action). These are currently handled by
completely different workflows — a spreadsheet over here, manual file edits over there —
and the inevitable result is that one drifts out of sync with the other.

PackSmith unifies them. Checking a box IS the documentation of intent AND the trigger for
actual file changes. One gesture, both purposes. Single Pane of Glass (SPOG).

## 2. The Two Halves

PackSmith is a two-part system.

### 2.1 Packdump (The Forge Mod)

A Minecraft Forge mod (currently targeting 1.20.1, Forge 47+) that acts as a data
extraction bridge. On world load (or via `/packdump dump`), it serializes the game's
complete state into JSON:

- **Registries** — every registry type (100+ in modded 1.20.1): items, blocks, entities,
  biomes, enchantments, mob effects, sound events, worldgen features, etc. Each gets its
  own file with a sorted `values` array.
- **Localization** — display names for items, blocks, entities, enchantments, and mob
  effects, resolved through the game's language system.
- **Metadata** — timestamp, MC version, Forge version, loader info, complete mod list
  with versions, and a registry manifest.

Output lands in `<gameDir>/packdump/` as:
```
packdump/
  meta.json
  registries/
    minecraft_item.json
    minecraft_block.json
    ... (one per registry type)
  attributes/
    localization.json
```

The mod also performs a **world datapack safety check** — if world-specific datapacks
(IDs starting with `file/`) are detected, the dump aborts to prevent contaminated
snapshots.

### 2.2 PackSmith (The Desktop App)

A PySide6 desktop application that consumes Packsmith dumps and provides the full IDE
experience: registry browsing, tagging, blueprint management, job execution,
file editing, and KubeJS integration. This is where all three architectural layers
(Section 3) live.

## 3. The Three-Layer Architecture

The architecture is built on three layers. The separation between them is **load-bearing**
— not organizational convenience. Each layer has a strict contract about what it can and
cannot do.

```
Layer 1: Game Data     — static, immutable, read-only snapshot of game reality
Layer 2: User Data     — descriptive metadata the user attaches TO game data
Layer 3: Actions       — Starlark functions that read Layers 1+2 and produce/edit
                         real files. Invoked via user-owned jobs (step sequences)
                         living in Layer 2.
```

### 3.1 Layer 1: Game Data

Game Data is the read registry/game attributes generated by Packdump. It is inherently **read-only, static, and a report, not
a whiteboard.** It represents the actual truth from the game itself. PackSmith reads it,
displays it, but critically never modifies it.

The game told you what exists. You don't get to argue.

#### Profiles

A **Profile** is the top-level organizational unit — one profile per modded Minecraft
instance. It tracks:

- Profile name
- Minecraft instance path
- MC version (e.g., `1.20.1`)
- Mod loader and version (e.g., Forge `47.4.16`) — frozen at creation
- Settings (e.g., `max_packdump_snapshot_count`)
- References to its packdumps and user database

Profiles are stored in `userdata/profiles/{name}/`.

#### Packdumps

A **Packdump** is an immutable snapshot of the game's registry state at a point in time.
Multiple packdumps are retained per profile (default ~5), with new ones loaded only when
the registry actually changes.

Key design decisions:

- **Automatic discovery.** When the user creates a profile, they point it at their
  Minecraft instance directory. The Packsmith mod always dumps to `<gameDir>/packsmith/`,
  so PackSmith knows exactly where to look — no user configuration needed for dump
  location. PackSmith won't let you do anything until it loads its first packdump, since
  without game data there's no registry to browse, no entries to tag, nothing to automate.
- **New dumps do not auto-merge.** When the user imports a new packdump, they review the
  diff (additions, removals, changes) before "blessing" it as the active snapshot. This
  prevents transient mod installs (install mod to test it, decide it sucks, uninstall)
  from polluting the tag/blueprint data.
- **Packdumps are diffable.** The `compare()` method generates a structured dict of
  differences between any two snapshots — useful for the review/blessing workflow.
- **Localization uses fallback.** If a display name isn't available in the current locale,
  the raw registry ID is shown.

Storage layout per profile:
```
packdumps/
  latest/           # The blessed/active snapshot
    meta.json
    registries/
    attributes/
  history/          # Previous snapshots, most recent N kept
```

#### Multi-Loader Awareness

The GUI itself is largely loader-agnostic — Forge and Fabric registries look the same
once dumped. The Packsmith Java mod will need per-loader versions, but the GUI just tracks
`loader` as metadata. Design for generality, don't over-engineer for it.

### 3.2 Layer 2: User Data

Layer 2 is where PackSmith becomes something. It consists of three primitives — **Tags**,
**Blueprints**, and **Views**. Layer 2's invariant: **no side effects on external state.**
It computes (filters, queries, sorts), but it never writes files, never triggers jobs,
never modifies anything outside the database. It is pure, idempotent, and observable-only.
That decoupling is critical: the same tag can drive multiple jobs, and changing a job
doesn't change the user's intent.

To be precise: the user *does* assign tags inside a view's table — but the view config
itself carries no assignment logic. The assignment happens through the table delegate,
which the view happens to be rendering. The view defines what you see; the table UI is
where you act.

All user data is stored in a per-profile SQLite database (`profile.db`).

#### 3.2.1 Tags

Tags are user-defined scalar values assigned to registry entries from Layer 1. They are
NOT game data. Each tag is **strictly scoped to a single registry type** — a `remove` tag
on `minecraft:item` is a completely separate definition from a `remove` tag on
`minecraft:block`. This is not a limitation; it's load-bearing. Registry types have
fundamentally different semantics, and a tag that means "remove this item from crafting"
is a different concept from "remove this block from worldgen." Separate definitions,
separate assignments, separate queries.

The ergonomic cost is real: tags that have genuinely identical semantics across registry
types (e.g., `mod_source` — "which mod introduced this?") must be defined N times, once
per registry type. This is accepted as the right tradeoff — the alternative (cross-registry
tags) would blur the boundary between fundamentally different domains and complicate every
query path.

Five types:

| Type        | Values                    | Example                          |
|-------------|---------------------------|----------------------------------|
| `bool`      | `true`, `false`, or unset | `remove`, `is_food`, `is_hidden` |
| `string`    | any text, or unset        | `notes`, `lang_override`         |
| `enum`      | one of N options, or unset| `tier` (early/mid/late/end)      |
| `number`    | int or float, or unset    | `weight`, `stack_size`           |
| `reference` | a registry entry ID from any registry type, or unset | `material` (diamond sword → `minecraft:diamond`) |

The `reference` type is a pointer to a specific registry entry. Unlike the other scalar
types, it stores a full registry ID (e.g., `minecraft:diamond`) and is validated against
the packdump. This enables lightweight cross-registry relationships without needing a full
blueprint — "what material is this tool made of?" is a single tag, not a schema.

Tags can have **default values**. An unset tag with a default displays and behaves as
the default in the UI (including copy operations), but the default is NOT written to the
database — the distinction between "explicitly set to X" and "defaulting to X" is
preserved.

##### Tag Definitions vs. Tag Assignments

A critical distinction runs through the rest of PackSmith:

- **Tag definitions** (name, type, registry scope, enum values, default) are **user-only.**
  Actions cannot create, modify, rename, retype, or delete tag definitions. Schema is the
  user's vocabulary; actions work within it.
- **Tag assignments** (which entries have which values) are **hybrid.** Both the user and
  actions can create, modify, and delete assignments, subject to the ownership system below.

This same split applies to blueprints (schemas user-only, instances and bindings hybrid)
and is the single most important rule about what Layer 3 can and cannot do to Layer 2.

##### Assignment Ownership

Every tag assignment that exists in the database has exactly one owner: either the user
or a specific action. Ownership is not a property of the value — it's a property of the
*existence of the assignment itself.*

The rule:

> An assignment either exists or it doesn't. If it exists, someone owns it.

This gives four practical states per (entry, tag) pair:

| State                        | Assignment row? | Ownership        |
|------------------------------|-----------------|------------------|
| **Pristine**                 | No              | Nobody           |
| **User-owned**               | Yes             | The user         |
| **Action-owned**             | Yes             | A specific action|
| **(Ownership-transferred)**  | Yes             | New owner        |

State transitions:

- **Pristine → user-owned:** user interacts with a cell (checks a box, types a value,
  picks an enum option). Assignment is created, user owns it.
- **Pristine → action-owned:** an action writes to this (entry, tag). Assignment is
  created, the action owns it.
- **User-owned value change:** user edits an existing user-owned assignment. Value
  updates; user still owns.
- **Action-owned value change by user:** user edits an action-owned assignment. Ownership
  transfers to user; value updates. Transfers are loud (see below).
- **User-owned value change by action:** an action tries to write to a user-owned
  assignment. The action's declared conflict policy fires (see §3.3).
- **Any state → pristine:** user explicitly deletes the assignment (Del key on the cell,
  context-menu "Clear assignment"). Assignment row is removed; nobody owns anything
  here anymore.

The subtle point worth naming: **"unset" is not the same as "pristine."** If a user
explicitly flips a bool from `true` to `false`, the assignment still exists with value
`false` — the user owns the decision "this should be false." This looks identical to a
pristine cell visually unless PackSmith renders the ownership indicator. The only way to
return to pristine is the explicit delete action.

For `bool` tags specifically, this means the registry table view must distinguish three
visual states per cell, not two:

- Pristine: truly empty cell, no indicator
- Assignment exists with value `false`, owned by someone: unchecked checkbox with an
  ownership tint/dot/border
- Assignment exists with value `true`, owned by someone: checked checkbox with an
  ownership tint/dot/border

For enum/string/number/reference tags, the pristine-vs-owned distinction is naturally
visible (empty cell vs. cell containing a value), but the ownership indicator still
appears to distinguish user-owned from action-owned.

Loud ownership transfer: when the user edits an action-owned assignment, they see a brief
confirmation ("This assignment was managed by `mod_classifier:classify`. Taking ownership
will prevent that action from updating it on future runs. Continue?"). Once confirmed,
the cell transitions to user-owned and the former action owner is displaced. The reverse
— an action writing to a user-owned assignment — is gated by the conflict policy system
in §3.3 and never silent.

##### Key Operations

- **Define/Undefine** — create or destroy a tag type (undefine cascades to all
  assignments). User-only operation; actions cannot do this.
- **Assign/Unassign** — set or clear a tag value, supports bulk operations. Creates or
  updates an assignment row, establishes ownership. Available to both users (through the
  UI) and actions (through the API, subject to conflict policy).
- **Delete assignment** — fully remove an assignment row, returning the (entry, tag) pair
  to the pristine state. User-only; actions cannot fully delete an assignment, only write
  over it (which transfers ownership rather than clearing it).
- **Query** — filter registry entries by tag values with operators: `eq`, `neq`, `in`,
  `not_in`, `gt`, `lt`, `gte`, `lte`, `exists`, `not_exists`. Also `owned_by_user`,
  `owned_by_action`, `owned_by(<action_ref>)` for ownership-aware queries.
- **Orphan detection** — find tags referencing entries that no longer exist in the current
  packdump (important after registry changes).

#### 3.2.2 Blueprints

Blueprints solve the problem tags can't: **modeling relationships between registry
entries.**

Tags are flat — they describe a single entry in isolation. But modpack development
constantly requires reasoning about *groups* of related entries that the game's flat
registry doesn't formally connect. The canonical example is stone palettes.

##### The Stone Problem

In vanilla Minecraft, stone types (granite, andesite, diorite, deepslate...) can be
processed into various cuts (polished, bricks, tiles, chiseled...) and each cut exists in
multiple forms (base block, stairs, slab, wall, vertical slab). But the coverage is
**completely arbitrary** — you can craft polished granite but not polished tuff; deepslate
has a cobbled variant but granite doesn't; Quark adds granite bricks but via polished
granite, not raw.

Layer 300 mods on top and it becomes an incomprehensible mess of missing holes and bizarre
inconsistencies. To enforce consistency, you need to:

1. **See** every stone type × cut × form combination
2. **Identify** which slots are filled, which are empty, and which come from which mod
3. **Fill gaps** — generate textures, blocks, recipes for missing combinations
4. **Standardize recipes** — enforce that the same crafting pattern works across all
   stone types

This requires modeling the *relationship* between `minecraft:granite`,
`minecraft:granite_stairs`, `minecraft:polished_granite`, `quark:granite_bricks`, etc. —
entries from different mods that are conceptually one "stone type."

##### How Blueprints Work

A **Blueprint** is an instantiable schema — a struct, or a class without methods.

1. **Define** a blueprint schema: `StoneType` has inline groups (`polished_cut`,
   `brick_cut`, `chiseled_cut`...) and each group has slots (`base`, `stairs`,
   `slab`, `wall`, `vertical_slab`).

2. **Instantiate** the blueprint: create `StoneType:granite`, `StoneType:andesite`, etc.

3. **Bind** entries to slots: `StoneType:granite.polished_cut.base` →
   `minecraft:polished_granite`, `StoneType:granite.polished_cut.stairs` →
   `minecraft:polished_granite_stairs`, etc.

4. **Identify gaps**: empty slots = missing content that needs to be generated or sourced.

5. **Automate**: actions can query blueprint instances to generate recipes, detect
   duplicates, compile "you need to go build these in your glue mod" lists, etc.

Blueprints are **purely descriptive** — they live on Layer 2, not Layer 3. They organize
information. They don't do anything. But actions can access them, and that's where the
power comes from.

##### Nesting and Structure

Blueprints support two kinds of structure:

**Inline groups** — structural nesting within a single blueprint definition. The user
thinks of this as one blueprint with grouped fields, not multiple separate blueprints:

```
StoneType:
  base_block: minecraft:block
  polished:                         ← inline group
    base: minecraft:block
    stairs: minecraft:block
    slab: minecraft:block
    wall: minecraft:block
    vertical_slab: minecraft:block
  bricks:                           ← inline group
    base: minecraft:block
    stairs: minecraft:block
    ...
```

Nesting depth is **unlimited.** At the DB level it's parent-child rows in
`blueprint_slots`, but the user sees one cohesive schema definition.

**Blueprint references** — a slot can reference an instance of *another* blueprint. This
is a pointer, not a copy. If the referenced instance is updated, the reference sees the
change automatically.

```
VillageVariations:
  inhabitants: minecraft:entity_type
  wood_type: WoodType               ← reference to a WoodType instance
  stone_type: StoneType             ← reference to a StoneType instance
```

Binding: `VillageVariations:canyon_villagers.stone_type` → `StoneType:granite`

This composes arbitrarily. `VillageVariations` references `StoneType`. Some future
blueprint could reference `VillageVariations`. No depth limit — it's just pointers with
no data duplication.

**Schema-level cycles are allowed.** A `CladeNode` blueprint with a `descendants` slot of
type `CladeNode` is a legitimate and powerful pattern (recursive tree structures like
cladograms). The schema is just a type definition; cycles there are fine. **Instance-level
cycles** (A references B references A) are a harder question — they could create infinite
loops in traversal, rendering, or action queries. See Open Questions.

##### Slot Typing

All slots are **strictly typed.** Two kinds of slot types:

- **Registry type** (`minecraft:block`, `minecraft:item`, etc.) — binds to a registry
  entry ID from the packdump. Validated on bind, autocomplete filtered to the correct
  registry.
- **Blueprint type** (`StoneType`, `WoodType`, etc.) — binds to an instance of that
  blueprint. Validated on bind, autocomplete shows available instances.

No or-types for now. If a genuine need surfaces during dogfooding, it can be added. Start
strict, loosen if needed.

##### Cross-Reference

A single registry entry can appear in multiple blueprint instances without restriction.
`minecraft:granite` can be bound in both `StoneType:granite` and `BuildingBlocks:granite`.
No special tracking — queryable through `instance_bindings` if needed ("show me every
blueprint instance that references this entry").

##### Auto-Population

There is significant room for an action that auto-fills blueprint slot bindings based on
naming conventions and registry search (e.g., if the stone type is "granite" and the slot
is "polished_base", search for `*polished_granite*` in the item registry). This is one of
the most practically valuable features of the blueprint system — without it, manually
binding hundreds of slots across dozens of instances is tedious enough to undermine the
whole concept. But mod naming conventions are wildly inconsistent (`polished_granite` vs.
`granite_polished` vs. `create:polished_granite`), so the approach needs serious design
work. See Open Questions.

##### Schema Evolution

Blueprint schemas are live, editable artifacts — users will add, remove, rename, and
retype slots on schemas that already have instances. The mutation rules are designed
around one consistent principle: **non-destructive changes propagate silently;
destructive changes orphan at the instance level and refuse to participate in actions
until the user explicitly resolves their intent.**

**Add slot.** Existing instances gain the new slot in an unset state. A non-modal
notification surfaces the change ("Added `author` to `Recipe Blueprint`. 42 existing
instances now have this slot, unset."). Propagation is silent; the notification is the
only visible side effect. Actions that query the blueprint see the new slot normally —
`None` for unset bindings.

**Remove slot.** If zero instances have a binding for the slot, it is removed silently —
no confirmation, no orphaning. If any instance has a binding, *every instance of the
blueprint that had a binding becomes orphaned* (not just the removed slot's row). Whole-
instance orphaning is deliberate: schema destruction is significant enough that the user
should be forced to confirm intent before downstream actions proceed. **Any action that
touches a blueprint with orphaned instances refuses to run until the orphans are
resolved.** The instance does not silently degrade.

**Rename slot.** Bindings migrate automatically — this is a metadata-only operation, not
a remove-plus-add. A confirmation dialog surfaces the impact ("Rename slot `author` →
`creator` on `Recipe Blueprint`? This will update 42 existing instances. The old name
will no longer exist.") before the rename commits. No orphaning, no data change.

**Retype slot.** The dangerous case. Default behavior: **retype orphans every instance
with a binding to that slot** (same rule as Remove — whole-instance orphan, actions
refuse).
However, PackSmith checks for provable loss-free coercion before showing the retype
dialog:

- **If all existing bindings can be losslessly coerced** to the new type
  (e.g., `int` → `float`, `enum` → `string`, `string` → `enum` where all values are in
  the new enum's set), the dialog offers three choices:
  - *Retype & Auto-Coerce* — apply the type change, convert all bindings, no orphaning
  - *Retype & Orphan* — apply the type change, orphan all instances anyway (explicit
    user choice to re-bind manually)
  - *Cancel*
- **If coercion would lose data or fail** (e.g., `int` → `registry reference`, narrowing
  conversions with out-of-range values), auto-coerce is not offered. The dialog shows
  only *Retype & Orphan* or *Cancel*.

Default and strictness are preserved; the auto-coerce path exists only when PackSmith
can *prove* the coercion is lossless. This keeps the rule predictable ("retype orphans")
while eliminating friction in cases where orphaning would be pure theater.

##### Resolving an Orphaned Instance

When an instance is orphaned (via slot removal or retyping), it surfaces in the Errors
panel under an "Orphaned Instances" section and is locked against action access. The user
has four resolution options available per-instance (or applied in bulk):

1. **Discard** — delete the orphaned bindings permanently, un-orphan the instance. Any
   data tied to removed or retyped slots is lost.
2. **Preserve** — keep the orphaned bindings in a limbo state, un-orphan the instance
   for action purposes. The limbo data is not exposed to actions but is retained in the
   database, useful if the slot might return or for historical reference.
3. **Revert Schema** — undo the schema mutation that caused the orphaning. Every instance
   of the blueprint snaps back to the pre-mutation state.
4. **Change Problematic Values** — applicable only for retype orphans. Opens an inline
   editor where the user re-binds the problematic slot values under the new type. Once
   all problematic bindings are re-bound, the instance un-orphans automatically.

All four are one-click actions. The user must choose one; there is no "ignore" or
"dismiss" that silently proceeds with a broken instance.

##### Schema vs. Data Ownership

Blueprints follow the same split as tags:

- **Blueprint schemas** (the shape — slot names, types, nesting, blueprint references)
  are **user-only.** Actions cannot create, modify, rename, retype, or delete schemas.
- **Blueprint instances and slot bindings** are **hybrid.** Both the user and actions can
  create instances, edit bindings, and delete instances, subject to the ownership system.

Ownership on blueprint data operates at **per-binding granularity**, not per-instance.
Each `(instance, slot)` binding has its own owner (user or action). An instance created
by an action can have its bindings individually overwritten by the user, transferring
ownership slot-by-slot. Instance creation itself is attributable — "this instance was
created by `mod_classifier:classify`" — but once bindings start getting touched by
different parties, the instance becomes a hybrid artifact with per-slot ownership.

Conflict behavior when an action tries to write to an already-bound slot is governed by
the action's declared conflict policy (§3.3), identical to tag assignment conflicts.

##### Database Schema

```
blueprints          — the schema definition (the "class")
blueprint_slots     — fields/groups per blueprint (parent_slot_id for nesting, type for
                      registry type or blueprint reference)
blueprint_instances — a named instantiation ("granite", "andesite")
instance_bindings   — slot → registry entry ID or blueprint instance ID
```

#### 3.2.3 Views

A **View** is a saved, reopenable table configuration. It defines what the user wants to
see and potentially edit. Nothing more.

Views are **strictly read-only as a concept** — the view *config* carries no assignment
logic and never triggers jobs. Tag assignment happens through the table delegate that
the view renders, not the view itself. Separation of church and state.

A View specifies:

- Which registry type(s) to display
- Which tag columns to show
- Filter criteria (which entries match)
- Sort order
- Which columns are editable vs. read-only display

Examples ranging from trivial to complex:

- "All `minecraft:item` entries where `remove` == true" (simple tag filter)
- "All `minecraft:item` entries, showing `remove`, `hide_only`, `lang_override` columns"
  (the main item browser)
- "All `minecraft:entity_type` where `is_creature` == true, showing `species_name`,
  `clade`, `diet` columns" (creature taxonomy view)
- "All `minecraft:item` where `is_food` == true, showing `food_group`, `nutrition_value`,
  `special_food` columns" (diet system)

Even the main item browser is itself a View. The system must handle **hundreds of views**
gracefully — most packs will accumulate 200-300, the vast majority being trivially simple
"show me X where Y" configurations.

##### Filtering

Every opened view has a **filter bar** at the top of its table. This is where queries
live — not in the sidebar, not in a separate dialog. The filter bar supports two modes:

- **Query builder** (visual): filter rows with dropdowns — pick a tag, pick an operator,
  pick a value, click plus to add another condition. AND/OR toggle between rows. Zero
  learning curve, discoverable, good for the common case.
- **Text query** (direct): a text representation of the same filter, editable inline.
  Fast for power users who know what they want.

The two modes stay in sync — editing the text updates the builder, using the builder
updates the text. The builder IS the documentation for the query syntax. Users learn the
text language by watching what the builder produces.

The query language supports:

- Tag value filters: `remove == true`, `tier IN ("early", "mid")`, `weight > 5`
- Tag existence: `HAS notes`, `NOT HAS tier`
- Entry properties: `id CONTAINS "granite"`, `mod == "quark"`,
  `display_name MATCHES ".*Brick.*"`
- Boolean logic: `AND`, `OR`, `NOT`, parenthetical grouping
- Registry type scoping: `minecraft:item WHERE ...`

Changing a filter updates the table live. If the user likes the result, they can save it
as a named view.

##### Creating Views

Three paths to the same result — all produce a named view config in the sidebar:

1. **Filter bar → save** (exploratory, bottom-up): open a blank registry table, play with
   filters, get a useful result, save it. The view already exists as a tab — saving just
   names it.

2. **New View wizard** (intentional, top-down): right-click in the Views sidebar panel →
   "New View." Minimal dialog: pick registry type, pick tag columns to show, optionally
   set an initial filter, name it. Four fields. Opens as a tab for further refinement.

3. **Tag shortcut** (quick single-tag view): from the Tags sidebar panel, click a tag →
   "Create View for this tag." Pre-fills the wizard with the tag's registry type and that
   one editable column. One click, view created.

### 3.3 Layer 3: Actions & Jobs

Layer 3 is the bridge between Layers 1+2 and the actual files in the modpack instance.
It has two concepts: **actions** (what can be done) and **jobs** (what the user wants
done).

An **action** is a declared Starlark entry point inside a package — a pure declaration
of capability. "I can hide items in EMI." "I can generate stone palette recipes."
Actions are written by package authors, sandboxed by construction, and never aware of
each other.

A **job** is a user-authored sequence of steps. Each step either invokes an action
(with specific bindings and configuration) or invokes another job. Jobs are pure
Layer 2 user data — stored in SQLite alongside tags, blueprints, and views. They are
the unit of user intent: "this is my removal workflow."

The separation is load-bearing. Actions are code. Jobs are configuration. Actions
live in packages and are read-only to the user. Jobs live in the database and are
fully user-owned. An action never knows which job invoked it, and a job never touches
Starlark.

#### 3.3.1 Actions

An action is a single declared entry point in a package manifest that PackSmith can
invoke. It is atomic — one Starlark function, one transaction, one unit of work.
PackSmith has no concept of actions calling other actions. Internal code reuse happens
via Starlark helpers inside the package; the action is just the surface the user sees.

##### Design Principles

1. **Nothing is built-in.** Even the concept of "removing an item" is not baked into
   PackSmith's core. The UI provides the interface into a registry; what you DO with
   that is defined by actions.
2. **Downloadable and shareable.** Users can browse, download, and configure
   community-published packages of actions through an in-app store/marketplace (free,
   not monetized). See Community Store below.
3. **Sandboxed by construction.** Actions run in Starlark (see Action Language below),
   a hermetic, capability-based runtime. An action can only touch the world through
   functions PackSmith explicitly registers. No filesystem escape, no network, no
   ambient authority.
4. **Mod-aware but mod-agnostic.** Many actions interface with specific mods (KubeJS,
   Item Obliterator, InControl, EMI, Paxi). Some only touch vanilla datapacks. The
   framework doesn't care — it provides the API surface and lets scripts do their thing.
5. **User vocabulary is authoritative.** An action never hardcodes references to
   user-owned artifacts (tag names, blueprint schema names, instance names). It
   declares structural contracts via **mappings**; the user binds their own artifacts
   into those contracts when configuring a job step. See Mappings below.

##### The Canonical Example: Item Removal

To "remove" an item from a modded Minecraft pack (say `quark:rope`), you can't
literally unregister it. You need to:

1. Hide it in EMI/JEI/REI (the recipe viewer)
2. Add it to `item_obliterator.json`
3. Generate datapack files to remove all recipes that create or use it
4. Add it to a KubeJS server script that nukes all tag assignments
5. Add it to a common hide datapack
6. Ensure that if a player somehow obtains it, it instantly disappears

Six file edits across six formats, plus documenting the decision somewhere.

A package author handles this by writing a single action — `nuke` — whose Starlark
entry point internally calls helper functions for each of those six operations. The
user never sees the helpers. They see one action: `nuke`.

With PackSmith: open a View, check `remove` next to `quark:rope`, run the removal job.
One checkbox, six files updated, decision preserved as an inspectable tag assignment.
SPOG.

##### Action Language & API Boundary

**Starlark** is the official action language, embedded via `starlark-pyo3` (bindings
to Meta's `starlark-rust`, the same implementation that powers Buck2). The host
defines a fixed capability API; actions can only touch the world through that API.
Hermetic by design — no ambient filesystem, network, clock, or syscall access.

Why Starlark:

- **Capability security by construction.** Nothing is ambient. If the host doesn't
  register a function, actions cannot call it. This is exactly the property the
  community store requires — "safe enough that strangers' scripts can run on a user's
  dev machine" is the non-negotiable bar, and Starlark meets it by virtue of language
  design, not by a sandbox configuration you have to maintain.
- **Python-family syntax.** Pack devs coming from KubeJS, Python, or general
  scripting experience feel at home immediately. No 1-based arrays, no nil-vs-None,
  no alien operators.
- **Deterministic and terminating.** No `while True`, no unbounded recursion. Actions
  halt.
- **Battle-tested upstream.** Meta's `starlark-rust` runs Buck2; Bazel's
  `starlark-go` runs the Google build infrastructure. The language has been hammered
  at scale.
- **Low integration cost.** `pip install starlark-pyo3`; register Python functions as
  callables; inject data into a module; eval.

Known constraints to live with:

- **No exceptions.** Actions use sentinel returns and `fail("reason")` for fatal
  errors. Host functions handle recoverable I/O failures behind the API surface.
- **No classes, no while loops, no try/except, no unbounded recursion.** Deliberate
  restrictions that keep actions deterministic and readable. Records are modeled as
  dicts or `struct(...)`.
- **No Python stdlib.** Actions cannot `import os`, `import re`, etc. If they need
  pattern matching, string utilities, or similar, the host exposes those through the
  capability API.

**Potential future: Extism + JS** (post-MVP, tentative). WebAssembly via Extism offers
capability security by construction with a broader expressiveness ceiling and the
option for action authors to use JavaScript (or any WASM-compilable language). Not
part of MVP — the integration cost is roughly 5-10x Starlark's and the ergonomic win
is marginal for the action shapes we care about.

##### Packages

A **package** is the distribution unit. It is a folder containing one or more Starlark
files, a manifest, and optionally documentation, assets, and suggested job definitions.
The manifest declares which specific functions inside the package are exposed as
runnable **actions**. Everything else in the package is implementation — helper
functions, utility modules, shared code between the package's actions.

Actions are declared entry points with full manifests, not every function in every
file.

On-disk layout for a package:

```
userdata/profiles/<profile>/packages/
  removal_suite/                     # one package, two actions: nuke and hide
    manifest.toml
    nuke.star                        # entry point for the nuke action
    hide.star                        # entry point for the hide action
    _emi.star                        # shared internal helper, loaded by both
    _utils.star                      # more internal helpers
    suggested_jobs/                  # optional: suggested job definitions
      full_obliteration.toml
      just_hide.toml
    README.md
  tag_helpers/                       # another package
    manifest.toml
    apply_mod_source.star
    apply_stack_size.star
```

Each package folder is self-contained. PackSmith scans the `packages/` directory,
reads each `manifest.toml`, and indexes every declared action into the sidebar.

A package manifest declares package-level metadata and a list of action entry points:

```toml
[package]
name = "removal_suite"
version = "2.1.0"
author = "example_author"
description = "Item removal with EMI/recipe hiding integration"

[[actions]]
id = "nuke"
file = "nuke.star"
function = "run"
name = "Nuke"
# ... full action manifest: mappings, configuration, conflict_policies ...

[[actions]]
id = "hide"
file = "hide.star"
function = "run"
name = "Hide"
# ... full manifest ...

[[suggested_jobs]]
file = "suggested_jobs/full_obliteration.toml"
description = "Run nuke then hide in one pass"
```

Action source files are pure, uneditable by the application. PackSmith displays them
in Monaco but treats them as read-only for downloaded packages. Bindings and
configuration (the things that differ per-user) live in the profile DB on individual
job steps, never in the source files.

##### Authored vs. Downloaded Packages

Packages come from one of two provenances: **downloaded** (acquired from the community
store or copied in from an external source) or **authored** (created by the user
in-place). This is purely a provenance label — structurally, authored and downloaded
packages are identical. Same manifest format, same on-disk layout, same dependency
system, same everything. There is no privileged "local" package, no magic default
bucket, no special namespace.

When a user wants to write their own Starlark action, they create an authored package
to hold it. The New Action dialog opens with a first field for the target package: a
dropdown of the user's existing authored packages plus a "+ New package..." option.
Creating a new package is one text field for the package name, inline in the dialog —
after that, the user continues with the action-creation flow normally. Total
additional friction compared to a magic default bucket: one text field, exactly once
per new package.

Non-power users can stay in the UI end-to-end: the New Action dialog, the Action
tab's property panels, and the Manifest editor all write to the package's
`manifest.toml` behind the scenes. Power users can edit the TOML and `.star` files
directly; they are just files on disk.

Authored packages can declare dependencies on installed packages and use Starlark
`load` to import from them (see Package Dependencies below). An authored package
can, in principle, be published to the community store later — its structure is
already what the store expects, so publishing is a matter of namespace reservation
and version tagging, not restructuring.

##### Action References and the `package:action_id` Syntax

Every action in every package has a stable, globally addressable identifier of the
form `package_name:action_id`. Examples:

- `removal_suite:nuke`
- `lang_fixer:apply_lang_overrides`
- `my_custom:cleanup` (an authored package named `my_custom`)

This syntax is used wherever an action is referenced: in job step definitions, in the
sidebar, in run logs, etc. There is no implicit same-package shorthand — always write
the full `package_name:action_id` at the configuration layer.

A user-facing UI may abbreviate these when context is unambiguous. At the data layer,
always explicit.

Actions never reference other actions. The `package:action_id` syntax is exclusively
for PackSmith-level surfaces (jobs, UI, logs) — there is no Starlark-level "call this
action" primitive.

##### Package Dependencies and Cross-Package Code Reuse

Packages can depend on other installed packages and `load` Starlark symbols from them.
This is how code reuse works across packages — libraries of shared helpers are just
packages with declared exports (and typically no actions of their own).

Dependencies are declared in the manifest:

```toml
[package]
name = "removal_suite"
version = "2.0.6"

[[package.depends]]
package = "emi_utils"
version = ">=3.0"

[[package.depends]]
package = "registry_helpers"
version = ">=1.2"
```

At install time, PackSmith resolves the full dependency tree, surfaces it to the user
for approval (same trust model as npm/cargo/pip — the user is accepting transitive
trust over everything they're installing), and refuses to install if any dependency is
unavailable.

**Load syntax.** Starlark `load` is used to import symbols, with a Bazel-style module
path convention:

- **Intra-package:** `load("//utils.star", "normalize_name")` — relative to the
  current package's root.
- **Cross-package:** `load("@emi_utils//hiding.star", "compute_hide_list")` — the
  `@package_name` prefix resolves through the declared dependency list. Importing
  from an undeclared package is a load-time error.

Loaded helpers never receive ambient capability. The `pack` object is injected into
the action entry point only. If a helper needs to write files or read Layer 2 data,
the action must explicitly pass `pack` (or a capability-scoped sub-object) as a
parameter. This keeps capability tracking explicit — a helper has exactly the
authority its caller hands it, nothing more.

**Public API vs. internals** (post-MVP). For MVP, every symbol a package ships is
importable. Package authors are responsible for their own semver discipline. A future
`[exports]` manifest section will formalize the public surface and make non-exported
symbols private to the package; not required for initial release.

##### The Mapping System

A **mapping** is a declared slot in an action's manifest that the user binds to one
of their own Layer 2 artifacts when configuring a job step. Mappings are the
mechanism that prevents actions from hardcoding references to user-owned artifact
names.

For example: an item-removal action does NOT say "I need a tag named `remove`." It
says "I need a bool tag on `minecraft:item`; the user will bind their own tag of
that type to this slot." The user's tag can be named anything — `remove`, `kill_it`,
`banned_in_my_pack` — and the action works identically.

Mappings are declared in the action manifest:

```toml
[[actions]]
id = "obliterate_items"
# ...

[actions.mappings.target_items]
kind = "tag"
tag_type = "bool"
registry_type = "minecraft:item"
access = "read"                # read | write | read_write
cardinality = "one"             # one | many | at_least_one
required = true
likely_name = "remove"          # hint for auto-fill heuristics
description = "Items marked true here will be added to item_obliterator.json"
```

Slottable artifact kinds:

| `kind`               | Binds to                            | Notes                                  |
|----------------------|-------------------------------------|----------------------------------------|
| `tag`                | A user-defined tag                  | Typed by `tag_type` + `registry_type`  |
| `blueprint`          | A user-defined blueprint schema     | Typed by `required_shape`              |
| `blueprint_instance` | A user-created instance             | Typed by `required_shape`              |
| `registry_entry`     | A specific entry from Layer 1       | Typed by `registry_type`               |

Views and files are explicitly NOT slottable. Views are ephemeral query renderings
with no identity worth referencing; files are addressed either as mod-convention path
literals in source code or as configuration strings (see Configuration below).

**Access direction** (`access`) declares capability intent:

- `read` — action only queries the bound artifact; cannot write to it
- `write` — action only writes to the bound artifact; cannot read prior state
- `read_write` — action can both query and mutate

The runtime enforces this — calling a write API on a `read` mapping is a runtime
error.

**Cardinality** (`cardinality`) declares how many artifacts bind to the slot:

- `one` — exactly one artifact (UI: single-select picker)
- `many` — zero or more artifacts (UI: multi-select list)
- `at_least_one` — one or more artifacts (UI: multi-select, validated non-empty)

For `many` on `blueprint_instance`, instances can come from multiple user-schemas as
long as each satisfies the declared `required_shape` — the action's contract is
about shape, not schema identity.

**Required vs. optional** (`required`). Required mappings block execution if unbound.
Optional mappings allow the action to run with the slot unbound; the action's code
checks whether the slot is present and adjusts behavior accordingly.

##### Structural Typing for Blueprints

`blueprint` and `blueprint_instance` mappings use **structural typing**, not
schema-name typing. The manifest declares the shape:

```toml
[actions.mappings.stone_types]
kind = "blueprint_instance"
cardinality = "many"
required = true
likely_name = "StoneType"

[actions.mappings.stone_types.required_shape]
base_block = { kind = "registry_entry", registry_type = "minecraft:block" }

[actions.mappings.stone_types.required_shape.polished]
kind = "group"
slots.base = { kind = "registry_entry", registry_type = "minecraft:block" }
slots.stairs = { kind = "registry_entry", registry_type = "minecraft:block" }
slots.slab = { kind = "registry_entry", registry_type = "minecraft:block" }
```

Any user-defined blueprint whose shape matches this contract is a valid binding,
regardless of what the user named it. `MyRockKind`, `StoneSchema42`, `Granite-Style`
— all fine as long as the structure matches.

##### Configuration

**Configuration** covers all scalar parameters that affect how an action runs. This
includes both persistent preferences (`dry_run`, `verbose_logging`) and
per-invocation parameters (`sol_group_id`, `tier_threshold`, target list). There is
no separate "inputs" concept — configuration is unified.

Configuration is declared in the action manifest with types and defaults:

```toml
[actions.configuration.also_hide_in_emi]
type = "bool"
default = true
description = "Also hide removed items in EMI's item panel"

[actions.configuration.sol_group_id]
type = "string"
required = true
description = "Which Spice of Life food group to assign"
```

All configuration values are set **per job step** (see §3.3.2). An action declares
what it accepts; the job step supplies the values. There is no action-level user
configuration — actions are pure declarations.

##### Best-Guess Fill and Recommended Userdata

When a user adds a step to a job that invokes an action, PackSmith attempts to fill
each mapping automatically:

- Scan the user's existing Layer 2 artifacts for matches to the mapping's type
  contract.
- If `likely_name` matches an existing compatible artifact, strongly prefer that
  binding.
- If exactly one compatible artifact exists, pre-select it.
- If multiple compatible artifacts exist, show the most likely candidate, let the
  user pick.
- If none exist, offer **recommended userdata** creation: a one-click "Create this
  artifact for me" action that instantiates a new tag/blueprint/instance matching
  the mapping's contract, prompts the user to name it, and auto-binds it.

For configuration, manifest defaults pre-fill the value. The user can accept or
override.

A step with any unresolved required mapping or required configuration is flagged
with a warning indicator and blocks execution.

##### Action Output and Return Values

An action's entry-point function may return a value. That value is:

- **Displayed in the run log** as structured output, viewable by the user in the
  Job Results panel.
- **Optionally typed and described in the manifest** for documentation purposes:

  ```toml
  [actions.returns]
  type = "list[registry_entry]"
  registry_type = "minecraft:item"
  description = "Items that matched the configured criteria"
  ```

- **Never consumed by another action or another step.** There is no inter-action
  data flow primitive. Actions that need to hand data to other actions do so by
  writing to a mapped Layer 2 artifact that another action reads from — with the
  user binding both steps' mappings to the same artifact.

Actions can also emit structured log output during execution via the capability API
(`pack.log`, `pack.log_section(name)`, etc.) so authors can surface per-phase
attribution in the run log.

##### Ownership of Layer 2 Data

See §3.2.1 (tag assignment ownership) and §3.2.2 (blueprint binding ownership) for
the full ownership lifecycle. Actions participate in this system by claiming
ownership of assignments and bindings they create or write.

When an action tries to write to a (user- or other-action-) owned assignment/binding,
the conflict is governed by the action's declared **conflict policy** for that
mapping:

| Policy      | Behavior on conflict                                                 |
|-------------|----------------------------------------------------------------------|
| `overwrite` | Write the new value, ownership transfers to this action. Logged.     |
| `skip`      | Leave the existing assignment alone. Logged.                         |
| `fail`      | Halt the run before committing any writes. Error surfaced to user.   |
| `ask`       | Pause the run, prompt the user to decide. See resolution UX below.   |

**Conflict policy is a mandatory per-write-mapping declaration.** Every `write` or
`read_write` mapping must specify one of these four policies in the manifest. There
is no default — the author must explicitly choose. This forces the decision because
there is no universally-correct answer.

Conflict policy is **user-overridable at the job step level, but loudly.** The step
configuration exposes the declared policy per-mapping. The user can change it, but
PackSmith surfaces a large warning dialog explaining that overriding the policy
breaks the action author's contract and will produce results the author did not
anticipate. After override, the step shows a persistent indicator next to the
overridden policy so the user doesn't forget.

#### 3.3.2 Jobs

A **job** is a user-authored, user-owned sequence of steps stored in SQLite. It is
pure Layer 2 data — the same category of artifact as a view, a tag definition, or a
blueprint schema. Jobs are created, edited, reordered, and deleted entirely through
the GUI. They never touch Starlark and Starlark never touches them.

Each step in a job is one of two kinds:

- **Action step** — invokes a specific action (`package:action_id`) with its own
  bindings, configuration, exception verdicts, and `on_error` policy.
- **Job step** — invokes another job by reference. At execution time, this is
  flattened into the referenced job's steps. Pure organizational nesting.

Jobs are **composable.** A "master removal" job can contain a "removal" job and a
"recipe cleanup" job as steps. At runtime, the entire tree is flattened into a
sequential list of action steps and executed one by one. The nesting is purely
organizational — it does not affect execution semantics, transaction boundaries, or
capability.

**Cycle detection:** PackSmith rejects job-step references that would create cycles
at creation time. A job cannot reference itself, directly or transitively.

##### Structure

```toml
[job]
name = "Full Removal Workflow"
default_on_error = "halt"

[[steps]]
kind = "action"
action = "removal_suite:nuke"
on_error = "halt"

  [steps.bindings]
  target_items = { artifact = "remove", artifact_kind = "tag" }

  [steps.config]
  also_hide_in_emi = true

[[steps]]
kind = "action"
action = "removal_suite:hide"
on_error = "skip"

  [steps.bindings]
  target_items = { artifact = "deprecated", artifact_kind = "tag" }

  [steps.config]
  also_hide_in_emi = false

[[steps]]
kind = "job"
job_id = "recipe_cleanup"     # references another job in the DB
on_error = "halt"
```

This structure is the canonical form for both the SQLite representation and the
TOML/JSON interchange format (see Import/Export below). The above is what a user
would see if they exported a job; it is also what a package ships as a suggested
job definition.

Note: the TOML shown above is the interchange/export format, not the operational
storage. Operationally, all of this lives in SQLite (see Database Schema below).

##### Per-Step State (Model B)

Every action step carries its own complete invocation state:

- **Bindings** — which Layer 2 artifacts this step's action operates on. Different
  steps invoking the same action can bind to different artifacts.
- **Configuration** — scalar parameters for this invocation. Different steps
  invoking the same action can use different values.
- **Exceptions** — persistent `ask`-policy conflict resolutions for this specific
  step (see Exceptions below).
- **Error policy** — `halt` or `skip` if this step fails.

There is no action-level user state. Actions are pure declarations. All user
decisions — what to bind, how to configure, which conflicts to resolve — live on the
step. A single action can appear in dozens of steps across dozens of jobs, each with
independent bindings, configuration, and exceptions.

##### The Step Editor

When the user edits a step, they see one unified panel of "what this step needs."
Mappings and configuration are presented together as a single list of slots to fill
— some slots show Layer 2 artifact pickers (for mappings), others show inline value
editors (for configuration). The architectural distinction between mappings and
configuration is invisible to the user; they just fill in what the action asks for.

##### Error Handling

Each step has an `on_error` policy: `halt` (default, inherited from the job's
`default_on_error`) or `skip`. Per-step override is available.

- `halt` — if this step's action fails, the entire job stops. No subsequent steps
  run.
- `skip` — if this step's action fails, log the failure and continue to the next
  step.

For job-reference steps, the sub-job's internal failure propagates up: if any step
inside the referenced job fails (and that step's policy is `halt`), the referenced
job is considered failed. The parent job's `on_error` for that job-step then
determines whether the parent continues.

##### `ask` Policy Resolution

When an action has an `ask`-policy write mapping, PackSmith resolves conflicts via a
**dry-run convergence loop.** There is no separate "real run" — the bytes that
commit are exactly the bytes of the final, zero-conflict dry-run.

**The loop:**

1. The action's body executes in **dry-run mode**: reads hit a frozen pre-run
   snapshot, writes stage to the run's scratch area rather than committing. Every
   intended write to an `ask`-policy mapping is checked against the current
   ownership state.
2. If the dry-run produces **zero conflicts**, its staged writes are promoted to
   committed. The step is done.
3. If conflicts exist, the user resolves them in the conflict-resolution tab (see
   below). Resolutions are recorded as **step-scoped verdicts**, sticky across
   subsequent rounds of this run: "keep mine" marks the cell as off-limits to this
   action for the remainder of the run; "use action's" marks the cell as
   action-writeable.
4. The dry-run **re-executes** with the accumulated verdicts applied. Aggregates
   and derived writes are recomputed against the post-resolution state, which means
   new conflicts can surface that the first dry-run couldn't have known about.
   Those surface in a fresh resolution round.
5. Loop continues until a dry-run produces zero conflicts. Termination is bounded:
   every cell the action ever tries to write gets exactly one verdict and cannot
   re-enter the conflict set, so the loop runs at most O(write-set-size) rounds
   (typically 1-2 in practice, because most actions have one layer of derived
   aggregates at most).

**Layer 2 is locked against manual user edits while a step is mid-resolution.**
Otherwise the snapshot the dry-run reads from becomes a moving target between
rounds and convergence is not guaranteed. The UI surfaces the lock state with a
banner; the run history remains browsable but editing is blocked.

##### The Conflict-Resolution Tab

Each round's conflicts open in a **conflict-resolution tab** — a distinct tab type
that reuses the registry table widget for rendering but is not itself a View. Each
row is one conflict cell with a checkbox: **checked = keep my value, action may
not write here; unchecked = accept action's value.**

Rows are visually classified:

| Row class        | Default state                     | Visual treatment                                              |
|------------------|-----------------------------------|---------------------------------------------------------------|
| **Carried-over** | Pre-checked with prior choice     | Muted tint; subtle "remembered" indicator                     |
| **Changed**      | Pre-checked with prior choice     | Warning tint; "CHANGED" flag; secondary line shows diff       |
| **New**          | Unchecked                         | Distinct tint; "NEW" flag; user must act                      |

The classification determines defaults and visibility; the user can always override
any individual row. Bulk actions (reusing the registry table widget's selection
machinery) support "check all selected," "uncheck all selected," "check all from
mod X," etc., for applying policies at scale without cell-by-cell clicking.

Filter/sort/query work the same way they do in any View — the registry table widget
is reused wholesale.

##### Exceptions

Exceptions are persistent `ask`-policy conflict resolutions stored **per step.**
They are Layer 2 user data, stored in SQLite with a foreign key to the step.

**Exception key:** `(step_id, action_id, action_version, cell, proposed_value, user_value)`

Only when all six values match on a future run does the prior verdict auto-apply
(carried-over class). Any mismatch drops the row into the changed class with the
prior choice pre-filled but visually flagged.

Exceptions have a natural lifecycle tied to the step. Delete a step → cascade
delete removes its exceptions. Delete a job → all its steps and their exceptions
are cleaned up. No orphan problem, no manual garbage collection.

Exceptions are inspectable in the step's configuration panel, which shows every
exception for the step with the cell reference, stored values, verdict, and a
last-consulted timestamp. Clear-selected and clear-all actions are available for
users who want to reset a step's relationship with their data.

##### Non-Interactive Runs

`ask` policy requires a user to resolve. A non-interactive run (scheduled
execution, CLI invocation, future automation) that encounters unresolved
`ask`-policy conflicts **fails fast** with an error message pointing the user to
either switch the mapping's policy, pre-resolve the conflicts by running
interactively once, or run interactively now. No silent resolution, no default
choice — the policy is `ask`, and no one is here to ask.

##### Standalone Runs

Running an action directly (not through a saved job) creates an **ephemeral
one-step job.** The user hits Run on an action in the sidebar, gets a dialog to
specify bindings and configuration, and runs once. After execution, PackSmith
prompts: "Save as job?" If accepted, the ephemeral job is persisted to SQLite with
a user-provided name. If declined, the run appears in history but the job
definition is not saved.

This means there is exactly one execution model: **jobs.** Every run, whether a
30-step master workflow or a quick one-off action invocation, goes through the
same engine.

##### Execution Model

Jobs are the unit of execution. A job is an ordered sequence of action steps (after
flattening any job-reference steps).

**Globally serialized runs.** Only one action step is ever executing at a time,
across the entire application. If the user triggers a second job while one is
already running, the new run is queued and starts when the current one finishes.
This is non-negotiable: concurrent writes to the same file or Layer 2 cell would
corrupt the ownership model, and the design simplification of "one thing at a time"
is worth more than any parallelism win.

**Manual triggering for MVP.** All runs are user-initiated. Reactive triggers (on
tag change, on packdump blessing, on file save, scheduled runs) are post-MVP and
would simply be alternative ways to enqueue the same jobs.

**Non-blocking runs.** A run executes on a background thread; the UI remains
responsive throughout. The user can navigate the registry, read files, and browse
blueprints while a run is in progress. Writes stage to an in-memory transaction and
are only committed at the end of each action step, so mid-run UI interactions
cannot race with staged state.

##### Transaction Scope and Rollback

Every **action step** is an independent transaction. All writes — Layer 2
assignments, blueprint bindings, file modifications — stage to a per-step scratch
area during execution. On successful completion, all staged changes commit
atomically. On failure (unhandled `fail()` or error surfaced from the capability
API), the entire staging area is discarded; no real state is touched.

There are no nested transactions. The action step is the transaction boundary;
internal Starlark control flow (helpers, sentinel returns, etc.) operates within
that single scope.

**Jobs are not transactions.** Each action step in a job is its own independent
transaction. If step 2 of 4 fails (and its `on_error` is `halt`), step 1's writes
remain committed and steps 3-4 do not run. The user sees the exact stopping point
and can choose to fix and re-run, or roll back step 1 individually via run history.

**Run history** records each action step as an atomic unit. The user can roll back
an individual step's writes. A full job run appears in history as a sequence of
step entries, each independently rollback-able.

##### Pre-Run Preview

Before a run commits, the user sees a preview showing the job's effective
configuration: which Layer 1 data each step will read, which Layer 2 artifacts
each step will write and with what conflict policies, and which files will be
modified. If the preview reveals conflicts that would trigger `ask`-policy
dialogs, they are resolved during the preview phase, not mid-run.

##### Creating Jobs

Three paths:

- **From the sidebar** — "New Job" action. Opens a job editor tab. User adds steps
  by picking actions from a searchable list, configures each step's bindings and
  configuration inline.
- **From a standalone run** — User runs an action directly, then accepts the "Save
  as job?" prompt. One-step job, ready to extend.
- **From a package** — Package ships suggested job definitions as static TOML/JSON
  files. On install, user opts in per-suggestion. PackSmith reads the file, writes
  rows to the database. From that point on, the job is fully user-owned —
  editable, deletable, unaffected by package updates.

##### Pinning

Jobs can be **pinned.** A pinned job appears in the sidebar with a play button for
one-click execution. Unpinned jobs are listed under a "Library" section without a
direct run button. The flag is purely UX — it does not affect execution semantics.
Unpinned jobs can still be run via right-click → Run.

##### Import/Export

Jobs are serializable to TOML or JSON as an interchange format. Export: user hits
"Export Job" in the GUI, gets a file they can share. Import: someone else loads
that file, PackSmith writes rows to SQLite. This is the same mechanism packages
use to ship suggested job definitions.

Exported job files do NOT include exceptions. Exceptions are user-specific
conflict resolutions that have no meaning outside the user's own profile.
Bindings reference artifact names that may not exist in the importing user's
profile — on import, PackSmith runs the same best-guess fill process as a fresh
step creation, and flags unresolved required bindings.

##### The Sidebar

The left sidebar's automation panel (icon: J or similar) has two sections:

- **Pinned** — jobs with play buttons, ordered by user preference. One-click
  execution.
- **Library** — all jobs (pinned and unpinned), searchable. Also lists all
  installed actions for reference and standalone runs.

Actions appear in the library as reference entries — the user can inspect their
manifest, read their documentation, and launch standalone runs. But actions are
not the primary interaction surface; jobs are.

##### The Action Tab

The **Action tab** is a read-only reference surface for inspecting a single
action. One tab type, one action per tab. Sections:

- **Metadata** — name, description, version, author, package provenance
  (read-only for downloaded packages; editable for authored packages)
- **Declared Manifest** — mappings with type contracts, configuration keys with
  types and defaults, conflict policies, return type. All read-only; this is the
  action's API surface.
- **Documentation** — README from the package, if present.
- **Run History** — all runs of this action across all jobs, with links to the
  owning job/step. Expandable to show what was read, written, structured log
  output, and emitted results.

The Action tab does not hold user bindings, user configuration, or exceptions.
Those live on job steps.

##### Community Store (Post-MVP)

Eventually, PackSmith will have an in-app store where users browse and install
packages. For MVP, this isn't needed — users write custom actions in their own
authored packages, and sharing happens through existing Minecraft channels
(GitHub, Discord). The store becomes valuable once the community is large enough
that organic content production outpaces informal sharing.

The store handles: package hosting, discovery, versioning, trust/reputation,
automatic updates, dependency resolution. Specifics are deferred until that time
comes.

When an installed package publishes a new version with changed mappings (new
required mappings, renamed mappings, retyped mappings) or changed dependencies,
every job step referencing that package's actions is re-validated on update and
the new dependency tree is surfaced for approval. Any required mapping that is
unbound after the update — because it's new, because its old binding was renamed
without a migration hint, or because its old binding is now type-incompatible —
blocks the step from running until the user resolves it in the step editor. There
is no orphan state for step mappings; it's a simple "required and unbound = step
refuses to run."

#### 3.3.3 Database Schema Additions

```
jobs                — id, name, default_on_error, pinned, created_at, updated_at
job_steps           — id, job_id, position, kind (action | job_ref),
                      action_id (nullable, for action steps),
                      ref_job_id (nullable, FK → jobs.id, for job-ref steps),
                      on_error,
                      bindings (JSON, for action steps),
                      config (JSON, for action steps)
job_exceptions      — id, step_id FK → job_steps.id,
                      action_id, action_version,
                      cell (registry_type + entry_id + tag_name
                        OR instance_id + slot_id),
                      proposed_value, user_value,
                      verdict (keep_user | use_action),
                      last_consulted_at

packages            — name, version, author, provenance (authored | downloaded),
                      install_path
actions             — id, package_id FK → packages, action_id, name,
                      manifest (JSON), file, function
                      
job_runs            — id, job_id FK → jobs.id, started_at, finished_at,
                      status (success | partial | failed)
step_runs           — id, job_run_id FK → job_runs.id, step_id FK → job_steps.id,
                      position_in_run (flattened order after job-ref expansion),
                      action_id, started_at, finished_at,
                      status (success | failed | skipped | rolled_back),
                      staged_writes (JSON — L2 changes + file snapshots),
                      log_output (JSON — structured log from pack.log calls),
                      return_value (JSON, nullable)
```

The `job_mappings` and `job_configuration` tables from previous design iterations
are superseded — their data now lives in the `bindings` and `config` JSON columns
on `job_steps`. The `jobs` table from previous iterations (which stored action
definitions) is superseded by the `actions` table.

Schema details (column types, indexes, foreign keys, migration strategy) are not
yet finalized — this is a structural sketch, not a DDL specification.


### 3.4 Plugins (Post-MVP)

Plugins are UI extensions that teach PackSmith about specific mods. They sit outside the
three-layer architecture — they don't touch game data, user data, or action/job logic.
They modify the UI: adding smart folders to the file browser, context menu actions,
bottom panel tabs, Monaco file renderers, and similar conveniences.

Most mods don't need a plugin. Plugins exist for "tooly" mods that affect the development
workflow itself — datapack loaders (Paxi, OpenLoader, Moonlight/Global Packs), scripting
frameworks (KubeJS), guidebook mods (Patchouli), and similar.

#### Examples

- **Paxi plugin**: registers smart folders for `config/paxi/datapacks/` and
  `config/paxi/resourcepacks/`. Adds "New Datapack" and "New Asset Pack" context menu
  options in the file browser.
- **KubeJS plugin**: registers smart folders for `kubejs/server_scripts/`,
  `kubejs/client_scripts/`, `kubejs/startup_scripts/`. Adds "New Server Script" etc.
  context menu actions. Adds a "KubeJS Logs" tab to the bottom panel.
- **Patchouli plugin**: helps with pathing for book pages, possibly renders book page
  JSON as formatted previews in Monaco.

#### Plugin Runtime

Plugins face the same community trust question as actions. A malicious plugin with
arbitrary host access is *more* dangerous than a malicious action (full UI access vs.
controlled file writes). The resolution: **plugins use the same runtime as actions —
Starlark.** One runtime, one trust model, no contradictions.

This works because plugins don't need to touch Qt directly. They describe what they want
through a declarative API — `register_smart_folder()`, `register_context_action()`,
`register_bottom_tab()` — and PackSmith builds the actual UI. The plugin never sees a
widget, never imports PySide6, never reaches into host internals. It just declares
capabilities and PackSmith renders them.

#### MVP Approach

For MVP, plugin functionality is **hardcoded directly into PackSmith** for the most common
mods (Paxi, KubeJS, OpenLoader, Moonlight). But the internal implementation uses the same
registration functions that a future plugin API would expose — `register_smart_folder()`,
`register_context_action()`, etc. The callers are just Python code inside PackSmith
instead of external Starlark scripts.

When the plugin system ships post-MVP, those registration functions become Starlark host
callables, and the hardcoded calls move into `.star` plugin files. The refactor is
mechanical, not architectural — the API surface already exists because PackSmith has been
using it internally.

### 4.2 Registry Table

The primary interface for browsing and editing. Built on Qt's Model/View/Delegate
architecture:

- **RegistryTableModel** — virtual/lazy-loading model, 2 fixed columns (ID, Display
  Name) + N dynamic tag columns
- **RegistrySortProxy** — type-aware sorting: numbers sort numerically, bools sort
  False→True, strings sort case-insensitive, empty values always sink to bottom
- **RegistryTableView** — keyboard-driven bulk editing
- **Cell delegates** — type-specific rendering and editing per tag type

#### Keyboard Shortcuts

| Key         | Action                                                              |
|-------------|---------------------------------------------------------------------|
| Space       | Gmail-style bool toggle (all True → all False, otherwise all True)  |
| Delete/Bksp | Clear selected cells (unset tags)                                   |
| Ctrl+C      | Copy as TSV (plain text) + HTML table                               |
| Ctrl+V      | Single-value paste fill with type validation                        |
| Enter       | Commit edit and move down one row                                   |
| Ctrl+Z      | Undo                                                                |
| Ctrl+Y      | Redo                                                                |

#### Copy Behavior

- Format: TSV (tab-separated values)
- Bools copy as literal `true`/`false` (not empty — empty means unset)
- Default values are included in copy even if not explicitly written to DB
- Multi-cell selection copies all selected cells, not just the anchor

#### Undo/Redo

All tag edits go through an **EditStack** using the command pattern:

- **TagEditCommand** — single cell edit, stores old/new value, can apply/undo
- **BatchEditCommand** — groups multiple TagEditCommands, optimizes bulk operations
- Redo stack is cleared when a new command is executed

#### Default Sort

First column, A→Z on open.

### 4.3 Tab Architecture

The main window uses a **single Qt-owned tab bar** (QTabWidget or QTabBar) where every
tab — regardless of content type — lives side by side as peers. Some tabs are pure Qt
widgets (registry table views, blueprint builders). Some tabs display files in the Monaco
editor. From the user's perspective, they're all just tabs:

```
Tab 1: [RegistryTableView]         ← pure Qt
Tab 2: [Monaco → config.toml]      ← shared WebEngine, model A
Tab 3: [BlueprintViewer]           ← pure Qt
Tab 4: [Monaco → startup.js]       ← same WebEngine, model B
Tab 5: [Monaco → loot_table.json]  ← same WebEngine, model C
```

**One Chromium process, one QWebEngineView, one Monaco instance.** Monaco natively
supports multiple "models" — lightweight text buffers that hold content, undo history,
cursor position, and dirty state independently. Switching between file tabs swaps the
active model via a JS call through QWebChannel. The swap is instant. The single
QWebEngineView is reparented or shown/hidden as the user switches between Monaco tabs
and Qt tabs.

This means 10 open files cost essentially nothing beyond their text buffer in JS memory.
No 10-Chromium nightmare. Monaco assets will be **bundled locally** (not loaded from CDN)
to eliminate network dependency.

### 4.4 File Editor (Monaco)

The Monaco editor provides a full code editing experience within PackSmith:

- Syntax highlighting with auto-detected language
- Dark theme (vs-dark)
- Dirty state tracking and save support (Ctrl+S)
- Minimap, line numbers, smooth scrolling

Target file types: KubeJS scripts (.js), datapack JSONs, mod configs (.toml, .cfg, .json5,
.txt), action source files (.star), and anything else in the modpack instance.

### 4.5 File Browser (Planned)

A collapsible file system panel for browsing files from the modpack instance. But NOT
a dumb directory listing — a **semantic file browser** that understands Minecraft folder
conventions and presents files by *purpose*, not just by path.

Minecraft instance directories are dense forests of wildly different file types scattered
across deeply nested structures. A pack dev constantly navigates two mental hierarchies
simultaneously — the physical file path AND the conceptual purpose — and they frequently
diverge. "Am I in asset packs or data packs right now?" "Am I in server scripts or
client scripts?" A raw tree view doesn't solve this.

PackSmith is uniquely positioned to do better because it already has the packdump — it
knows which mods are installed. It can detect which global datapack loader is present
(Paxi → `config/paxi/datapacks/`, Moonlight → `moonlight-global-datapacks/`,
OpenLoader → its own path) and resolve paths automatically. The file browser presents
files by purpose: "Here are your datapacks. Here are your KubeJS server scripts. Here
are your mod configs." The underlying paths might be wildly different per loader, per
mod, per user setup — but PackSmith resolves them.

This also directly supports the action contract: an action doesn't say "write to
`config/paxi/datapacks/my_pack/data/minecraft/recipes/stone.json`." It says "write this
recipe JSON for namespace `minecraft`, recipe `stone`." PackSmith resolves the actual path
based on the profile's detected configuration. Actions become portable across loader
setups.

### 4.6 File Ownership System

Every file in the modpack instance that PackSmith interacts with has exactly one of three
ownership states:

| State | Meaning | Constraints |
|---|---|---|
| **Untouched** | Neither user nor action has modified this file through PackSmith. It's the mod's default, vanilla, or whatever shipped with it. | Anyone can claim it. |
| **User-owned** | The user has edited this file (either manually in Monaco or through an explicit claim). | Actions are **blocked** from touching it. If an action wants this file, the user must explicitly release ownership. |
| **Action-owned** | An action created or claimed this file. | The user is **warned** before editing. If they edit anyway, ownership transfers to them and the action is blocked until they release it back. |

Ownership transfers are **explicit, visible, and loud.** Never silent overwrites. The user
always knows who owns what, and conflicts are prevented rather than resolved.

#### The Rust Philosophy

This is deliberately strict. The permissive approach ("actions and users can both freely
edit anything") sounds flexible but creates invisible chaos — an action silently overwrites
a manual edit, or a manual edit silently invalidates something that's SPOG'd on
a view somewhere. The strict model is annoying for five minutes while you get used to it.
The permissive model is terrifying permanently because you can never trust that your files
are in the state you think they are.

#### Action Ownership Declaration

Actions **explicitly declare** which files (or keys — see below) they intend to own. This
enables PackSmith to show the full picture *before anything runs*:

- "This action will create/modify these 47 files"
- "3 of these are currently user-owned — release them or the action will skip them"
- "These 12 are already owned by a different action — here's the conflict"

For any file in the browser, PackSmith can show not just who owns it *now* but who *will*
touch it on the next run. "This file is managed by `removal_suite:nuke`. Last generated 3
days ago. Will be regenerated on next run." Full provenance, full predictability.

#### Per-Key Ownership for Structured Configs

For unstructured files (scripts, raw text), ownership is per-file. One owner, period.
Each action writes its own files. KubeJS loads all `.js` files in a directory, so a
removal action writes `server_scripts/packsmith_removal.js` and a recipe action writes
`server_scripts/packsmith_recipes.js`. No conflict.

But mod config files break the per-file model. `quark-common.toml` is one file. An action
that disables features, an action that configures Wraith Sounds entity lists, an action
that manages the Pettable allowlist, and the user who wants to tweak a UI setting — all
have legitimate reasons to touch the same file.

The solution: **per-key ownership for structured config formats.** PackSmith parses the
config, tracks ownership at the key/field level, and merges on write. Each action claims
specific keys. The user owns everything unclaimed. Multiple actions can coexist
in the same file as long as they don't claim the same keys.

```
quark-common.toml
  ├── [Wraith Sounds].wraith_entities     ← owned by: wraith_cfg:apply_entities
  ├── [Enchanting Stacks].stacks          ← owned by: enchanting:apply_stacks
  ├── [Enchantments To Begone].list       ← owned by: removal_suite:nuke
  ├── [Pettable].allowlist                ← owned by: pettable:apply_allowlist
  └── everything else                     ← owned by: user (or untouched)
```

Key-level conflicts (two actions claiming the same key) are detected at package
install/configuration time, not at runtime.

#### Monaco Integration

When a user opens a structured config file with mixed ownership in Monaco:

- **Action-owned keys** are visually decorated — subtle background tint, lock icon in
  the gutter. Edits to these ranges are intercepted and blocked. Tooltip: "Managed by:
  `removal_suite:nuke`. Click to release ownership."
- **User-owned keys** show a subtle indicator in the gutter. Tooltip shows ownership
  provenance.
- **Untouched keys** look normal, fully editable. The moment the user saves a change,
  PackSmith automatically assigns user ownership to the keys they touched.

This is implemented via Monaco's decoration API (background styling, gutter icons) and
edit interception via `onDidChangeModelContent` (check if the edit touched an
action-owned range, revert if so).

#### Supported Structured Formats

Per-key ownership applies to any format that is parseable with addressable fields:

| Format | Key Granularity | Notes |
|--------|----------------|-------|
| JSON / JSONC / JSON5 | any key path | Comment preservation needed for json5/jsonc |
| TOML | `[section].key` | Comment preservation — solvable with round-trip libs |
| YAML / YML | any key path | Comment preservation, whitespace sensitivity |
| INI / .properties | `key` or `[section].key` | Java standard, used by MC for lang/some configs |
| .conf | `key` | Simple key=value (as seen in Forge ecosystem) |
| .cfg | Forge category + key | Forge-specific legacy format, still appears |
| CSS (e.g. `emi.css`) | selector block + property | EMI uses CSS-syntax for config — fully parseable |
| .mcmeta | any key path | It's JSON |
| .dat / NBT | any compound path (e.g. `Data.Player.Inventory`) | Binary tree; viewed in a dedicated NBT tree viewer, not Monaco, but ownership is per-path like any other structured format |

Per-file ownership only (unstructured):

| Format | Notes |
|--------|-------|
| .js / scripts | Each action writes its own file |
| .txt | Could be anything — per-file only |

The critical engineering concern across all structured formats is **comment-preserving
round-trip parsing.** PackSmith must read, modify specific keys, and write back WITHOUT
destroying comments, formatting, or key ordering. This is a solved problem (round-trip
TOML/JSON5/YAML libraries exist) but requires deliberate parser selection.

#### File Versioning

Actions create and modify files. These changes are **versioned** through a custom
snapshot system (not git — too heavyweight, wrong mental model).

Before an action touches a file, its current state is snapshotted. After the action step
completes, the result is snapshotted. Each snapshot is tagged with which action produced
it (and via which job run) and when. This gives:

- **Per-file history**: "Show me every version of `quark-common.toml`"
- **Per-run grouping**: "Full Removal Workflow, April 15 — modified 126 files, added 6000
  lines" as a single reviewable unit
- **Rollback**: "Restore `supplementaries.toml` to before the removal run touched it"
- **Diffing**: expand any run, see every file diff, approve or rollback the
  whole batch or individual files

The void gets a flashlight. "My script just touched 126 files and I hope it was right"
becomes "my script touched 126 files and here's exactly what changed in each one."

#### NBT / .dat Files

PackSmith will support viewing and editing `.dat` (NBT) files, but NOT through Monaco.
NBT is a binary tree structure that wants a **dedicated tree viewer** — expandable nodes
with typed values, similar to NBTExplorer. This is its own Qt widget type living in the
tab system alongside Monaco tabs and registry table tabs.

**Ownership is per-path, not per-file.** NBT is structured data — a tree of addressable
compound paths — and treating it as opaque blobs would create synthetic conflicts between
actions that touch unrelated branches. An action that rewrites a village's loot tables at
`Data.Structures.Villages.<id>.LootTable` doesn't conflict with an action rewriting
`Data.Structures.Villages.<id>.Inhabitants`, and PackSmith shouldn't pretend it does.

The ownership model is identical to TOML/JSON/YAML: actions claim specific compound paths,
the tree viewer surfaces per-node ownership indicators (icons, tinting), and edit
attempts against action-owned paths prompt the standard ownership-transfer flow. The
wrinkle
specific to NBT is that lists (as opposed to compounds) are trickier to address
stably — `MyList[3]` is a fragile handle when the list can be reordered. Path addressing
within lists is a round-trip parser concern, not an ownership-model concern.

## 5. Data Storage

### 5.1 File Formats

| Data                | Format   | Location                                      |
|---------------------|----------|-----------------------------------------------|
| Packdump snapshots  | JSON     | `userdata/profiles/{name}/packdumps/`         |
| Profile metadata    | JSON     | `userdata/profiles/{name}/profile.json`       |
| User data (all L2)  | SQLite   | `userdata/profiles/{name}/profile.db`         |
| App configuration   | TOML     | `userdata/config/main.toml`                   |
| Logs                | text     | `userdata/logs/`                              |

### 5.2 Database Schema

The SQLite database stores all Layer 2 data. Ownership tracking (see §3.2.1 and §3.2.2)
means every row in `tag_assignments` and `instance_bindings` carries an owner reference.

Ownership rows reference **actions**, not jobs — jobs are user-owned step sequences, the
code that actually claims ownership is always an action (see §3.3.1). Action references
use the stable `package:action_id` form.

```
tag_definitions       — tag name, type, registry scope, enum values, default
tag_assignments       — registry_type, entry_id, tag_name, value,
                        owner_kind (user | action),
                        owner_action_ref (nullable, package:action_id),
                        created_at, updated_at

blueprints            — blueprint schema definitions
blueprint_slots       — fields/members per blueprint (parent_slot_id for nesting,
                        type for registry type or blueprint reference)
blueprint_instances   — named instantiations,
                        created_by_kind (user | action),
                        created_by_action_ref (nullable, package:action_id)
instance_bindings     — slot_id, instance_id, bound_value
                        (registry entry ID or blueprint instance ID),
                        owner_kind (user | action),
                        owner_action_ref (nullable, package:action_id),
                        created_at, updated_at

views                 — saved view configurations

job_runs, step_runs   — see §3.3.3
```

Layer 3 tables (`packages`, `actions`, `jobs`, `job_steps`, `job_exceptions`) are defined
in §3.3.3.

Schema details (column types, indexes, foreign keys, migration strategy) are not yet
finalized — this is a structural sketch, not a DDL specification. The ownership columns
are load-bearing for the §3.2 ownership lifecycle and the §3.3 conflict policy system;
everything else is subject to refinement during implementation.

### 5.3 Design Principle

The packdump is **read-only, always.** It never gets modified by PackSmith. Anything the
user creates, decides, or configures lives in the SQLite database. The packdump is truth
from the game; the database is truth from the user.

## 7. Open Questions

### Round-Trip Parser Selection
Which libraries do we use for comment-preserving round-trip parsing of TOML, JSON5, YAML,
and the other structured formats? This is the core engineering challenge of the per-key
ownership system. Needs research per format.

### Data Migration / Schema Versioning
As the SQLite schema evolves during development, how do we handle migration of existing
profile databases? `profile.py` has a TODO about this. Not urgent for early dev (blow away
and recreate is fine), but needs a real answer before any release where users have data
they care about.

### Blueprint Instance Cycles
Schema-level cycles are explicitly allowed (e.g., recursive `CladeNode`). But what about
instance-level cycles — `A` references `B` references `A`? This could cause infinite loops
in traversal, rendering, or action queries. Options: detect and reject at bind time, allow but
with documented depth limits on traversal, or allow and let consuming code handle it.

### Blueprint Binding Orphan Detection
When a registry entry disappears from a new packdump and it's bound to blueprint instances,
what happens? Auto-clear the binding? Enter an "orphan" state (like tag orphans)? Surface
it during the packdump blessing workflow? The blessing workflow needs blueprint-aware logic.

### Blueprint Auto-Population Strategy
Auto-population is one of the most practically valuable blueprint features — without it,
manually binding hundreds of slots is tedious enough to undermine the concept. But mod
naming conventions are wildly inconsistent. Needs real design: string-similarity matching?
User-trained patterns? Blueprint-level regex hints from the schema author? Or defer
entirely and accept manual binding for MVP?

### Views at Scale
The design estimates 200-300 views for a mature pack. A flat searchable list in the sidebar
will break down well before that. How do we organize views — folders? Tags on views?
Pinned favorites? Some combination? Needs UX design.

### Query Language Specification
The filter bar query language is sketched but not formally specified. Operator precedence,
regex dialect, edge cases (e.g., `IN` on a bool tag), error messages for malformed
queries — all need a grammar definition. The query-builder-as-documentation approach is
great UX but requires a real grammar underneath it.

### Action Runtime Management
Recursion limits, resource caps, timeouts, and error recovery for action execution. Not
pressing for single-user indev, but required before community store ships untrusted code.
What happens when an action hangs? When an action crashes mid-run with half its files
written? (Actions don't call actions, so self-recursion is not a concern — but unbounded
loops within a single action still need enforcement.)

### Global Search
"Find any item, block, entity, tag, view, blueprint, or file by name across the whole
profile" — there's no specified way to do this. Filter bars are per-view. A global
search / command palette (Ctrl+Shift+P pattern — fuzzy search over every action, entity,
and setting in the app) would be essential for a tool at this complexity level.

### Per-Key Ownership Edge Cases
Key rename in Monaco: user renames a key, parser sees delete-old + insert-new. Does
ownership transfer? Is the old key's ownership orphaned? What if it was action-owned?
Also: the Monaco edit-interception UX for action-owned ranges (block keystroke? revert after?
allow with pending-review banner?). Needs an explicit decision.

### Undo Scope
Ctrl+Z in a view — does undo cross tabs? Cross sessions? What about undoing a tag
definition change that cascaded to hundreds of unset assignments? The current per-view
EditStack is specified but cross-view and destructive-cascade undo is not.

### Settings / Preferences
Beyond `max_packdump_snapshot_count`, there's no user-settings system discussed. Themes,
keybinds, default behaviors, font size, etc. Not architecturally complex but needs a
design pass.

### Packaging and Distribution
How do users install PackSmith? PyInstaller bundle? Standard installer? How does it
update? How does the Forge mod version stay in sync with GUI changes?

### Community Sharing (Post-MVP)
The community store handles packages (which bundle actions). What about sharing blueprint
schemas, view configs, tag definitions, or standalone jobs? A unified store for packages,
plugins, schemas, jobs, and other shareable artifacts. Not MVP, but the sharing surface
is wider than just packages.

### Testing Strategy
How does PackSmith get tested? The ownership model, action API, round-trip parsers, and
blueprint system all have complex invariants. Needs at minimum a strategy sketch — unit
tests, integration tests, what gets mocked vs. real.

### Package Version Resolution and Conflict Handling

Packages declare dependencies with version ranges. Two installed packages might depend
on different incompatible versions of a third — standard dependency-hell territory.
Needs a resolution strategy (single-version resolution with conflict errors vs.
side-by-side versioning), plus "left-pad"-style protection (pinning, vendoring,
bundle-vs-dependency choice at publish time) before the community store ships.

### Public API vs. Package Internals

For MVP, every symbol a package ships is importable from other packages. This means
package authors are on the hook for their own semver discipline even on symbols they
consider private. Needs a post-MVP `[exports]` manifest section to formalize the
public surface, and a decision on whether unexported symbols are genuinely private
(load-time error) or just soft-deprecated.

### Non-Interactive `ask` Policy

The `ask` conflict policy requires user presence to resolve. A non-interactive run
(scheduled execution, CLI invocation, future automation) with unresolved `ask`-policy
conflicts cannot proceed. Current assumption: auto-fail with a clear message. Needs
confirmation, and the error message needs to explain what the user can do (switch policy,
pre-resolve conflicts, run interactively).

## 8. Underspecified Sections

> Sections of the design that exist as concepts but lack enough detail to implement from.
> These need dedicated design passes before building.

- **Blueprint Viewer (§4.8)** — Central to the architecture, currently a one-paragraph
  placeholder. What does it look like to see a 4-level-nested StoneType schema with 15
  instances? Grid? Tree? Tabbed instances with a shared schema header?
- **File Browser (§4.5)** — Smart-mode/honest-mode toggle is a good concept but the
  mechanics are vague. How does file creation work in smart mode? What about files that
  don't fit any category?
- **KubeJS Integration (§4.7)** — Currently just "we have the registry so we can do
  ProbeJS's job." Monaco language server integration is a real project. Is this
  Monaco-native IntelliSense or a full LSP?
- **Packdump Workflow** — Error recovery for the packdump import/blessing workflow. What
  happens on a corrupt dump? Mid-load failure? Partial registry data?
- **Per-Key Ownership Monaco UX** — The decoration and edit-interception model is sketched
  but the actual user interaction flow (what happens keystroke-by-keystroke when you try to
  edit an action-owned range) needs a concrete decision.
